# 非Cursor引擎主进程续接产品需求文档

> **变更 ID**：`20260712113332-非Cursor引擎主进程续接`
> **来源**：kb-propose
> **类型**：建议「可靠性」（待闸门确认）
> **优先级**：建议 P1（待闸门确认）
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景与问题

续接 **S7** 仅 Cursor 在主进程重启后有 recover：持久化活跃 Run、resume 生命周期、继续执行。Claude Code、Codex、OpenCode 仅有 SDK 内 sessionId 续聊，无主进程重启对等续接，形成「重启就丢会话」体验裂口。

## 二、用户可见症状

- CC/Codex/OpenCode 重启后会话断裂
- Cursor 可续接，其他引擎须手动重发
- 无提示时用户以为仍在执行
- 活跃 Run 记录存在但未恢复

## 三、目标与非目标

**目标**：三引擎提供与 Cursor S7 对等的续接；成功继续、失败一次 IM 告知；符合 RunLifecycle 终态契约。

**非目标**：不改 file-queue、合并卡、Daemon 路由全量持久化；不写实现模块名。

## 四、用户与场景

Electron 重启 Daemon 仍运行；续接成功无需重发 IM；失败有引导；四引擎策略可对照验收；终态通知仍统一。

## 五、功能需求

| 编号 | 需求 |
|------|------|
| R1 | 三引擎主进程重启触发 recover |
| R2 | 续接前重置生命周期门控（与 S7 一致） |
| R3 | 失败一次用户可感知通知 |
| R4 | 活跃 Run 持久化覆盖三引擎 |
| R5 | 不改变 Port 六能力与 dispatch 成功路径 |

## 六、验收标准

1. 三引擎各一条：重启→续接成功或明确失败（可重复）
2. 成功路径无需手动重发 IM
3. 失败仅通知一次
4. Cursor S7 无回归
5. 四引擎终态 IM 符合 Port 契约

## 七、范围边界

**在范围**：三引擎 recover、续接通知。**不在范围**：队列、合并卡、Daemon 路由 T4、微信。

## 八、风险与依赖

- **依赖** Engine Port 终态稳定
- **引擎差异** 续接粒度须文档化
- **双跑** recover 与 dispatch 防重复
- **独立** 与队列重入队可并行

## 九、知识库影响初评

CC/Codex/OpenCode §九（高）；Cursor S7 对照（中）；SDK 上下文保护（中）。
