# Cursor SDK 本地配置来源对齐产品需求文档

## 一、背景

cursor-claw 的 Cursor 执行引擎承担飞书 IM、任务与工作流中的智能体对话能力。官方 Cursor SDK 已定义清晰的**本地配置来源**模型：用户与项目可在标准目录放置 MCP、子智能体、规则、钩子、插件等配置，SDK 按既定优先级自动加载。其中**规则（rules）**、**钩子（hooks）**、**插件（plugins）**与 MCP、子智能体同属官方配置体系，共同决定智能体在会话中的行为边界与可用能力。

当前产品内，部分能力仍依赖与官方模型不一致的加载方式，导致用户在同一工作区已配置 MCP、规则、钩子、插件或子智能体后，经 cursor-claw 发起的 SDK 会话**未必**与 Cursor IDE 中表现一致。管理员与高级用户期望：**在项目 `.cursor/` 与用户 `~/.cursor/` 中维护的配置，应成为 Cursor 执行引擎的唯一可信来源**，IM 路径须与 IDE 一致，无需额外隐式行为或重复维护多套配置。

设置界面已提供 Rules、Skills 等配置维护入口，MCP 亦可通过 IM 与相关面板管理；但上述界面能力在展示口径、项目级与用户级区分、以及与 Cursor 执行引擎实际加载来源的一致性上，尚未与 SDK 配置来源模型完全对齐，易造成「设置已保存、IM 路径未生效」或状态误判。

## 二、目标

1. **配置来源统一**：Cursor 执行引擎的 MCP、子智能体、**规则（rules）**、**钩子（hooks）**、**插件（plugins）**等能力，统一从**项目本地**（工作区 `.cursor/`）与**用户本地**（`~/.cursor/`）加载，与官方 SDK「配置来源一览」一致。
2. **优先级一致**：当同一配置在多处存在时，遵循官方文档约定的覆盖顺序（内联配置优先于项目级，项目级优先于用户级），避免「后加载覆盖先加载」的意外行为。
3. **体验不退化**：飞书长对话、任务调度、工作流触发等现有入口的行为与响应质量保持可用；短任务、单轮问答等轻量场景不应因配置对齐而变慢或失败增多。
4. **设置界面与配置来源对齐**：设置界面中 Rules、Skills、MCP、Plugin 的配置展示与管理口径与 SDK 配置来源（项目级、用户级、插件层）一致；用户通过设置界面维护的配置应在 Cursor 执行引擎（含飞书 IM、任务、工作流等路径）中生效，而非仅停留在界面层或 IDE 专属路径。

## 三、非目标

- 不改动 Claude Code、Codex、OpenCode 等其他执行引擎的配置加载逻辑。
- 不追求大规模界面视觉改版；可在既有设置界面内做与配置来源对齐的**必要调整**（含 Rules、Skills、MCP、Plugin 相关能力与说明），不另起全新设置体系或独立可视化配置编辑器产品。
- 不改动飞书/微信等 IM 入口、消息格式或 Presentation 展示规则。
- 不强制用户迁移既有配置格式；在官方支持的本地文件形态下应开箱可用。

## 四、用户故事

### 4.1 飞书长对话用户

作为在飞书与 cursor-claw 进行多轮对话的用户，我希望工作区 `.cursor/mcp.json` 中声明的 MCP 服务在对话中可直接调用，以便与我在 Cursor IDE 中调试同一项目时获得一致的工具能力，无需为 IM 单独再配一套。

### 4.2 任务与工作流用户

作为通过任务或工作流触发 Cursor 执行引擎的用户，我希望项目级与用户级本地配置在每次执行时自动生效，以便自动化场景下的智能体行为与手动在 IDE 中运行时的能力边界一致。

### 4.3 管理员与配置维护者

作为为团队维护 MCP、钩子、规则或自定义子智能体定义的管理员，我希望只需在标准的项目 `.cursor/` 或用户 `~/.cursor/` 目录维护一份配置，cursor-claw 的 Cursor 路径即会识别并应用，以便降低运维成本并减少「IDE 能用、IM 不能用」的排查困惑。

### 4.4 规则维护者

作为为项目或团队编写 Cursor 规则（如工作区 `.cursor/rules` 下的项目级规则）的维护者，我希望经 cursor-claw 发起的 SDK 会话能自动遵循这些规则约束，以便飞书 IM、任务与工作流中的智能体行为与 IDE 内调试时一致，无需为 IM 路径单独复制或改写规则。

### 4.5 依赖插件 MCP 的用户

作为在 Cursor IDE 中通过官方插件获得额外 MCP 或工具能力的用户，我希望经 cursor-claw 发起的 SDK 会话同样可使用这些插件层配置，以便依赖插件提供的检索、工作流或第三方集成的场景在 IM 与自动化入口中不被降级为「仅 IDE 可用」。

### 4.6 设置界面使用者

作为在设置界面维护 rule、skill、mcp、plugin 的用户，我希望在设置中所做的增删改与 SDK 认可的配置来源一致，并在飞书 IM、任务与工作流等 Cursor 执行引擎路径中同样生效，以便无需在设置与文件系统之间重复维护或产生「设置已保存但 IM 不生效」的困惑。

- **项目级维护场景**：当我为当前工作区在设置中维护 Rules 或项目级 MCP 时，期望变更落盘至工作区 `.cursor/` 对应路径，且后续 IM 会话按项目级口径加载。
- **用户级维护场景**：当我为个人全局能力在设置中维护 Skills 或用户级 MCP 时，期望变更落盘至 `~/.cursor/` 对应路径，且在无项目级覆盖时于各工作区的 Cursor 执行引擎路径中可用。
- **插件层说明场景**：当某项能力仅能通过官方插件或插件层配置提供时，期望设置界面能说明其生效边界与在 IM 路径下的启用方式，避免将「仅 IDE 可用」误展示为「已在 cursor-claw 生效」。

## 五、范围说明

**在范围内**

- Cursor 执行引擎对 MCP、子智能体（agents）、**规则（rules）**、**钩子（hooks）**、**插件（plugins）**等官方 SDK 支持的本地配置项的加载与生效。
- 项目级与用户级配置的合并与优先级，与官方文档一致。
- 与现有 IM、任务、工作流链路的兼容性验证。
- **设置界面（Rules / Skills / MCP / Plugin 相关能力）的调整与对齐**：包括展示口径、维护入口、项目级与用户级来源区分、保存后与 SDK 加载口径一致，以及 Plugin 等能力在界面上的可理解说明。

**不在范围内**

- 其他执行引擎、Daemon 队列逻辑、通道连接与消息路由（除非因 Cursor 配置加载直接受影响且无法隔离）。

## 六、验收标准

1. **项目级 MCP 可用**：在工作区 `.cursor/` 中按官方格式配置的 MCP 服务，经 cursor-claw 发起的 Cursor SDK 会话中可被调用；工具列表与调用结果与同一工作区在 Cursor IDE 中的预期一致（在官方 SDK 能力边界内）。
2. **用户级 MCP 可用**：在 `~/.cursor/` 中配置的用户级 MCP 服务，在无项目级冲突或未覆盖时，于 SDK 会话中可用。
3. **项目级规则生效**：工作区 `.cursor/rules`（或官方等价路径）下的项目级规则，在 Cursor SDK 会话中按官方语义生效；智能体行为应体现规则约束，与同一工作区在 IDE 中的预期一致。
4. **用户级与项目级钩子均可触发**：工作区 `.cursor/` 与用户 `~/.cursor/` 中配置的钩子在 Cursor SDK 会话生命周期内按官方语义触发（如会话开始、结束、工具调用前后等官方支持的事件），**不仅限于项目级**；行为可观测、可验证。
5. **插件层配置可用**：官方插件提供的 MCP 等插件层配置，在 cursor-claw 发起的 Cursor SDK 会话中可用；依赖插件工具的场景与 IDE 侧能力对齐（在官方 SDK 能力边界内）。
6. **子智能体文件可被使用**：工作区 `.cursor/agents/`（或官方文档等价路径）下的子智能体定义，在需要时可被 Cursor SDK 会话识别与调度，与 IDE 侧能力对齐。
7. **无重复工具注册**：当同一 MCP 服务既可能由本地配置来源加载、又可能存在历史兼容路径时，会话中**不出现**同名工具或 MCP 的双份注册；用户侧表现为工具列表无重复、调用无异常冲突。
8. **短任务与单轮场景不退化**：轻量问答、单轮 dispatch 等现有高频路径的响应时延与成功率不低于变更前基线；不因配置对齐引入可感知的卡顿或失败率上升。
9. **优先级可验证**：在同一配置项同时存在于项目与用户目录时，生效结果符合官方「项目优先于用户」的约定，可通过对照实验复核。
10. **回归：HTTP 与 stdio 类 MCP**：变更前已通过 cursor-claw 正常使用的 MCP 类型（含远程 HTTP 与本地 stdio），在对齐后仍保持可用；若有官方已知限制，须在交付说明中明确边界而非静默失效。
11. **设置：Rules 与项目来源一致**：在设置中对 Rules 的增删改与项目 `.cursor/rules` 保持一致；保存后经 cursor-claw 发起的 Cursor SDK 会话可感知相应规则约束。
12. **设置：Skills 与用户来源一致**：在设置中对 Skills 的增删改与用户级 skills 目录（`~/.cursor/skills` 或官方等价路径）保持一致；保存后 SDK 会话可感知（在官方 SDK 支持范围内）。
13. **设置：MCP 项目/用户级区分正确**：设置中的 MCP 管理能正确区分并维护项目级与用户级来源，与 SDK 加载口径一致；界面状态展示不误导用户（例如：不把仅 IDE 可用的 plugin MCP 标示为已在 cursor-claw 执行引擎中生效）。
14. **设置：Plugin 可理解入口或说明**：Plugin 相关能力在设置中有可理解的入口或说明；若官方仅支持通过文件或插件层加载，界面须明确告知用户如何在 IM 等 Cursor 执行引擎路径下启用或验证，避免「无处配置、不知是否生效」。

## 七、风险与依赖

- **风险**：完全对齐官方加载模型后，历史上为弥补远程会话限制而采用的变通方式若未妥善收敛，可能导致部分 MCP 短暂不可用或出现重复注册；需在实现阶段明确迁移与去重策略。
- **风险（规则与插件）**：规则或插件配置存在语法错误、路径不可达或版本不兼容时，会话可能部分能力缺失或行为与 IDE 不一致；产品须在业务层面明确**可观测边界**（如会话启动或执行过程中能否识别「某类配置未成功加载」、是否影响其余能力继续可用），避免用户误以为「已配置即已生效」却无法排查。
- **风险（设置界面与运行时）**：设置界面展示的配置来源、生效状态与 Cursor 执行引擎实际加载结果不一致时，用户可能误判「已在设置中配置即已在 IM 路径生效」；须在业务层面明确各配置项的维护层级（项目/用户/插件）与可达路径，状态展示须与运行时加载口径一致，避免误导。
- **依赖**：以官方 Cursor SDK 当前版本的「配置来源一览」与本地文件格式为权威参考；后续 SDK 升级若调整优先级或路径，需同步评估本产品行为。
- **知识库**：完成后需更新 Agent 调度域中 Cursor SDK 执行引擎相关说明，使文档与产品行为一致。
