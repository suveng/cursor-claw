## 一、问题陈述

cursor-claw 现已支持四种 Agent 执行引擎（Cursor SDK、Claude Code、Codex、OpenCode），且同一应用实例可配置多个消息通道，各通道可绑定不同类型的 Agent 资源。然而，设置界面中的 **Rules**、**Skills**、**MCP** 等配置类标签页仍以 Cursor SDK 为唯一口径呈现：例如 MCP 区域标题固定为「Cursor SDK 执行引擎」、Rules/Skills 的说明与路径均指向 Cursor 用户目录，整体给用户造成「设置里只有 Cursor」的感知，与多引擎、多通道的产品能力不匹配。

Agent 资源与消息通道一一绑定：每个通道通过其绑定的 Agent 资源类型，决定该通道会话实际使用的执行引擎。设置页作为用户维护 Agent 相关配置的主入口，理应在**运行时**反映当前已配置通道所实际绑定的引擎类型，展示对应引擎的配置入口、路径说明与操作范围，而不是无论通道如何绑定都只呈现 Cursor SDK 视角。

此外，部分引导文案（如 Dashboard）仍偏 Cursor SDK 口径，进一步强化了单一引擎的心智，与 Agent 标签页已按四类资源分块管理的现状不一致。

## 二、目标用户

- 在 cursor-claw 中配置多个 IM 通道、并为不同通道绑定不同执行引擎的运维者与团队管理员；
- 使用 Claude Code、Codex、OpenCode 等非 Cursor SDK 引擎，需要在设置中查看与维护对应引擎 Rules/Skills/MCP 等配置的用户；
- 仅使用 Cursor SDK 但希望设置界面口径与通道绑定关系一致、避免误导的开发者；
- 在设置页统一维护 Agent 生态配置、期望「绑什么引擎、就看到什么引擎的配置入口」的产品使用者。

## 三、用户故事

### 3.1 单通道单引擎（仅 Cursor SDK）

作为只配置了一个消息通道且绑定 Cursor SDK 的用户，我打开设置中的 Rules、Skills、MCP 等标签页时，应看到与 Cursor SDK 相关的说明与配置入口，且文案不再与其他引擎的配置项混杂或产生歧义。

### 3.2 单通道单引擎（仅非 Cursor 引擎）

作为只配置了一个通道且绑定 Claude Code（或 Codex、OpenCode）的用户，我进入设置时，Rules/Skills/MCP 等区域应展示**该引擎**对应的配置说明与入口，而不是仍提示我去 `~/.cursor/` 维护 Cursor 专属配置；我能理解「当前通道用的是 Claude Code，所以这里管的是 Claude Code 的配置」。

### 3.3 多通道多引擎

作为同时配置了飞书通道（绑定 Cursor SDK）与另一通道（绑定 Codex）的用户，我希望设置页能体现**当前实例实际在用哪些引擎**——例如按引擎类型分块展示各引擎的配置区，或明确标注「以下配置适用于已绑定 Codex 的通道」，避免我误以为所有通道都走 Cursor SDK 路径。

### 3.4 未配置任何通道

作为尚未创建消息通道的新用户，我打开设置时，Agent 相关配置区应给出清晰引导：说明需先配置通道并绑定 Agent 资源后，对应引擎的配置入口才会生效；不应默认铺满 Cursor SDK 专属文案却无任何通道上下文。

### 3.5 仅配置某一类引擎

作为只绑定了 OpenCode 引擎、未使用 Cursor SDK 的用户，设置页不应强制展示大量 Cursor 专属标题与路径；未绑定引擎类型相关的配置区块应隐藏或折叠，并说明「当前无通道使用此类引擎」。

### 3.6 切换通道绑定后

作为调整了某通道 Agent 资源绑定（例如从 Cursor SDK 改为 Claude Code）的用户，我再次打开设置时，应能看到展示内容已随绑定关系更新，与变更前通道所用引擎一致，无需重启应用或手动刷新才能感知差异（具体刷新时机以实现为准，本 PRD 要求用户可感知的一致性）。

### 3.7 与 Agent 标签页心智对齐

作为已在 **Agent** 标签页按四类资源分块管理 Profile 的用户，我希望 Rules、Skills、MCP 等标签页在「按引擎区分」上与 Agent 标签页的分块心智一致，降低「Agent 里分了四类、别的标签却只有 Cursor」的割裂感。

## 四、功能范围

**在范围内**

1. **运行时引擎感知**：设置页根据当前已配置消息通道及其绑定的 Agent 资源类型，确定应展示的引擎集合；展示内容随通道绑定关系变化而更新。
2. **Rules 标签页**：按实际涉及的引擎类型，动态呈现各引擎对应的规则配置入口、路径说明与操作范围；文案与标题不再统一写死为 Cursor SDK 口径。
3. **Skills 标签页**：同上，按绑定引擎动态展示对应 Skills 配置入口与说明；与 Cursor 专属路径解耦当用户未绑定 Cursor SDK 时。
4. **MCP 标签页**：标题与分组不再固定为「Cursor SDK 执行引擎」单一视角；按各引擎差异化展示 MCP 配置入口（含 global/project 等既有分组心智的延续）。
5. **多引擎并存时的信息架构**：当实例同时绑定多种引擎时，采用分块、分组或等价清晰结构区分各引擎配置，避免混排导致误操作。
6. **未绑定引擎的显隐**：某类引擎当前无任何通道绑定时，相关配置区块应隐藏或明确标注不可用，而非展示误导性 Cursor 默认文案。
7. **引导文案口径**：Dashboard 及其他设置相关引导中，与 Agent 配置强相关的表述应改为多引擎友好，不再默认「只有 Cursor SDK」。
8. **沿用现有 UI 范式**：在现有设置页标签结构与视觉风格上演进，可参考 Agent 标签页四类资源分块、MCP 标签页 global/project 分组、通道编辑时按资源类型联动的既有交互模式，不引入全新页面形态。

**不在范围内**

- 不改变各执行引擎本身的配置存储位置、格式或官方语义（仅调整设置页的展示与入口口径）；
- 不涉及 Daemon、IM 侧（飞书/微信等）的配置协议或管理入口改造；
- 不新增第五类执行引擎的接入（仅限已支持的四种）；
- 不强制统一 Session 面板与设置面板的每一句文案（Session 侧已有差异化展示可保持，本变更聚焦**设置页**）；
- 不改变消息通道创建、Agent 资源 CRUD 的核心业务流程，仅调整配置类标签页的呈现逻辑；
- **项目级 Skills 来源补齐**的专项能力见并行变更「项目级 Skills 未显示」，本变更不重复其验收条目（见第五节边界说明）。

## 五、与「项目级 Skills 未显示」变更的边界

进行中变更 `20260702120631-项目级Skills未显示` 聚焦 **Skills 标签页**补齐**项目级**来源（`.cursor/skills/`）的可见性与可管理性，解决「后台可能已加载、设置里看不见」的 Cursor SDK Skills 专项问题。

本变更范围更广，覆盖设置页 **Rules、Skills、MCP** 及关联引导在**多引擎、多通道**场景下的整体产品口径：

| 维度 | 本变更 | 项目级 Skills 未显示 |
|------|--------|----------------------|
| 核心问题 | 设置页默认 Cursor SDK 单一视角，与通道绑定引擎不符 | Skills 仅展示用户级，缺项目级来源 |
| 引擎范围 | 四种引擎动态展示 | 主要面向 Cursor SDK Skills |
| 标签页 | Rules、Skills、MCP、引导文案等 |  primarily Skills |
| 关系 | 上层产品口径 | 可视为本变更在 Cursor SDK Skills 维度的子集或并行依赖 |

实施时两者可并行：本变更确立「按通道绑定引擎动态展示」的整体框架；Skills 项目级能力可在该框架下作为 Cursor SDK 区块的增强项合入，避免重复设计两套 Skills 信息架构。

## 六、与现有 UI 演进原则

1. **不新增页面形态**：在现有设置页标签（Agent、Rules、Skills、MCP 等）内演进，不另起独立「引擎选择」全屏向导。
2. **分块优于平铺**：多引擎并存时，优先采用与 Agent 标签页类似的**按引擎/资源类型分块**展示，每块含标题、简短说明与对应操作入口。
3. **分组心智延续**：MCP 等已有 global/project 分组的标签页，在按引擎分块后仍保留组内分组逻辑，避免用户重新学习结构。
4. **通道编辑联动一致**：通道编辑里「选 Agent 资源类型 → 相关字段联动」的模式，应在设置只读展示侧形成呼应：用户能理解「我在通道里绑了什么，设置里就出现什么」。
5. **无 Figma 原型**：在现有组件与间距体系上迭代，不引入全新视觉语言；具体布局在 design 阶段结合现有面板模式细化。

## 七、验收标准

1. **单通道 Cursor SDK**：仅绑定 Cursor SDK 时，Rules/Skills/MCP 展示 Cursor 相关入口与说明，且无其他引擎的空白占位块。
2. **单通道非 Cursor**：仅绑定 Claude Code（或 Codex、OpenCode）时，上述标签页不出现「Cursor SDK 执行引擎」等专属标题作为主口径，主展示内容为该引擎对应配置。
3. **多通道多引擎**：同时绑定至少两种引擎时，用户能在设置内区分各引擎的配置区域，并理解各区域适用于哪些通道绑定关系。
4. **未配置通道**：无任何消息通道时，配置类标签页有明确引导（非 Cursor 默认满屏），说明需先配置通道与 Agent 资源。
5. **引擎未绑定显隐**：某引擎无任何通道绑定时，不展示该引擎的误导性 Cursor 式默认文案；隐藏或标注「当前无通道使用」。
6. **绑定变更可感知**：修改通道 Agent 资源绑定后，再次进入设置，展示内容与新区绑定关系一致（用户可手工验证：改绑前后对比）。
7. **MCP 标题口径**：MCP 标签页标题/副标题不再在无 Cursor 绑定时仍固定为「Cursor SDK 执行引擎」唯一表述。
8. **Rules/Skills 路径说明**：路径与目录说明与当前展示引擎一致；仅 Cursor 绑定时出现 `~/.cursor/` 类说明，仅 Codex 绑定时不应强推 Cursor 路径。
9. **Agent 标签页一致性**：用户主观感受上，Agent 标签页「四类资源分块」与 Rules/Skills/MCP「按引擎分块」心智一致，无「Agent 很全、别的很窄」的割裂。
10. **Dashboard 引导**：Dashboard 上与 Agent 配置相关的引导文案不再默认假设用户只使用 Cursor SDK（可手工抽查至少一处相关文案）。
