# 多会话并发调度产品需求文档

> **来源**：kb-propose
> **类型**：功能
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无
> **依赖**：`20260712170438-Daemon批二拆分`（建议在 Daemon 批二拆分后实现，便于在清晰模块边界上演进；不阻断本 propose）

## 一、背景与问题陈述

Cursor Claw 通过 IM（飞书、微信等）接入多会话用户任务：不同群聊、不同私聊各自入队后，由本机 Daemon 编排进程领取并交给 Agent 执行。

既有注释与产品债中，Daemon 对 Agent 的调度被记为**「单条顺序 dispatch」**：全局层面一次只推进一条待办，多会话同时有待处理消息时容易**串行排队**。典型后果：

1. **跨会话互相拖累**：A 群 Agent 正在忙或处于合并等待时，B 私聊/另一群的新消息也要等前序会话跑完才开始处理。
2. **高峰等待感明显**：用户侧已收到「已收到」类即时反馈，但 Agent 真正开始处理要等很久，误以为系统卡住或丢消息。
3. **多群并行场景体验差**：运维/开发者同时盯多个群或私聊时，后到会话的响应延迟不可接受，与「各会话独立 Agent 工作区」的产品心智不一致。

相邻变更「Daemon 批二拆分」聚焦枢纽文件 queue/channel/logging **结构拆分**，**明确不做**调度并发模型改造；本提案专门解决**跨会话并行推进**的产品能力，与批二正交、可串行落地。

已归档的「dispatch 失败重入队与 ack 策略」等可靠性变更保障**单条任务失败不丢、可有限重试**；本变更不替代该语义，而是在**多会话并存**时避免「一个会话忙就拖死全体」。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 跨会话长时间阻塞 | A 会话 Agent 执行中或合并卡等待中，B 会话消息迟迟不开始处理 |
| 「已收到」与执行脱节 | 即时反馈已到，但排队/执行启动间隔过长，高峰更明显 |
| 多群并行体感差 | 同时维护多个群聊或私聊时，后到的会话像被「插队失败」 |
| 单会话内仍应有序 | 同一会话短时间多条消息仍须合并/顺序正确，不得因并发引入乱序（用户未感知到合并则视为缺陷） |

## 三、目标与非目标

### 目标（必须达成）

1. **跨会话可并行**：不同会话（以 sessionKey 等业务会话标识区分）的待办可同时进入执行或并行推进，互不长时间阻塞。
2. **同会话顺序与合并不变**：同一会话内仍保持既有顺序语义与 MergeBatch 门控；短时间多条仍正确合并，禁止乱序交付给 Agent。
3. **门控不拖死他人**：单会话 busy、合并中、等待用户点合并卡等门控，只影响该会话，不得阻塞其他会话的调度与执行启动。
4. **可靠性语义不弱化**：失败重试、ack、合并卡交互、有限重试耗尽等行为与现网产品预期一致，不因引入并发而回退。
5. **可验收的并行体感**：两个及以上独立会话同时有待办时，可观察到并行启动/处理，产品验收口径为「不再互相长时间阻塞」（不要求本期给出严格吞吐数字）。

### 非目标（明确不做）

- **不改**飞书/微信出站协议、卡片版式或通道侧消息格式。
- **不做**跨机器分布式队列或多实例协同调度。
- **不拆** Daemon 枢纽巨型文件（属「Daemon 批二拆分」范围；本变更可在批二之后落地，见依赖说明）。
- **不在 propose 阶段**绑定具体类名、文件路径、锁模型、线程/协程方案等技术细节（归属 `/kb-design`）。
- **不扩大**为全通道 UI redesign 或新配置项强制用户迁移。

## 四、用户与场景

### 用户

- **飞书 / 微信终端用户**：在多群、多私聊并行使用时，期望各会话任务相对独立推进，不被无关会话长时间挡住。
- **管理员 / 运维**：高峰时需判断「是单会话忙还是全局调度卡住」；并发后应能区分会话级 busy 与跨会话正常并行。
- **工程协作者**：在 Daemon 模块边界清晰后（批二后更佳）演进调度能力，降低后续功能与可靠性改动互相牵连的风险。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 双会话并行** | 两个独立会话几乎同时有待处理消息；两路均可启动处理，不必等一方完全结束另一方才开始。 |
| **S2 单会话 busy 隔离** | 会话 A 的 Agent 忙或合并门控中；会话 B 新消息仍可按既有规则领取并执行，不被 A 拖住。 |
| **S3 同会话合并与顺序** | 同一会话短时间连发多条；仍触发合并批次与顺序语义，与并发改造前用户感知一致。 |
| **S4 合并卡门控** | 某会话处于合并卡等待用户操作；仅该会话相关推进暂停，其他会话不受影响。 |
| **S5 失败重试与 ack** | 某会话 dispatch 失败进入重试或有限重试耗尽；重入队、ack、日志关键字等可靠性行为不退化，且不误伤其他会话并行。 |
| **S6 成功路径一致** | 单会话成功执行、确认移除、展示出站等与现网一致，不因并发引入重复执行或漏执行。 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | **跨 sessionKey 并发调度**：不同会话的待办可同时被推进，避免全局单条串行排队导致的长等待。 |
| R2 | **同会话顺序保持**：同一会话内消息处理顺序与现网一致，不得乱序交给 Agent。 |
| R3 | **MergeBatch 门控保持**：同会话合并批次、合并预览与合并卡相关门控语义不变，仅作用域限于该会话。 |
| R4 | **会话级 busy 隔离**：单会话 busy/执行中/合并等待不阻塞其他会话的领取与启动。 |
| R5 | **可靠性不弱化**：失败重试、ack、有限重试耗尽、合并卡行为与相邻可靠性变更口径一致。 |
| R6 | **可观测**：运维可区分「某会话忙」与「全局调度停滞」；既有诊断关键字（如 dispatch、merge、busy、重试相关）仍可用于排障，不因并发而整体失效。 |
| R7 | **与批二边界清晰**：结构拆分（queue/channel/logging）由批二负责；本变更只改调度并发产品语义，不借机扩大批二范围。 |

## 六、验收标准

### 6.1 主路径（产品可感知）

1. **双会话并行**：两个独立会话同时入队后，可观察到两路并行启动/处理；验收口径为「不再互相长时间阻塞」，不要求严格吞吐基准数字。
2. **同会话合并与顺序**：同一会话短时间多条仍正确合并与顺序处理，无乱序、无错误跳过合并门控。
3. **busy 隔离**：一会话 busy 或合并卡等待中，另一会话新任务仍可正常推进。
4. **可靠性保持**：失败重入队、有限重试、ack 与合并卡相关行为仍可用；日志中仍可用既有类关键字检索 busy/失败/重试事件（具体关键字由设计阶段对照现网清单，本期验收以「行为不退化」为准）。

### 6.2 与相邻变更边界

1. 「Daemon 批二拆分」完成后结构更清晰，但本变更验收**不依赖**批二必须先归档——若并行开发，须避免与批二同一枢纽大段冲突，设计阶段划清文件与职责。
2. 「dispatch 失败重入队与 ack 策略」已闭环的「失败不丢、可重试」语义须保持；本变更不得回退为「因并发导致失败任务静默丢失或无限双跑」。
3. 飞书/微信出站展示与协议不在本变更验收范围。

### 6.3 非功能

1. 变更代码含中文注释，单文件不超过 300 行（超限须拆分，属实现阶段约束）。
2. 不引入跨机器分布式队列；单机多会话并发即可满足本期产品目标。

## 七、范围边界

### 在范围内

- Daemon 编排侧：跨 sessionKey 的并发调度能力；同会话顺序与 MergeBatch 门控保持。
- 与失败重试、ack、合并卡、busy 门控的产品语义对齐与回归。
- 归档阶段同步 Agent 调度 / Daemon 概览中「单条顺序 dispatch」类限制描述（若有）。

### 不在范围内

- 飞书/微信出站协议与 UI 改版。
- 跨机器分布式队列、多 Daemon 实例协同。
- Daemon 枢纽 queue/channel/logging 巨型文件拆分（见依赖变更）。
- 新 IM 通道接入或通道专属视觉改造。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 与 Daemon 批二并行 | 批二拆 queue/合并/通道，本变更动调度并发，可能触及相邻模块 | `depends_on` 建议批二后实现；设计阶段文件白名单与合并策略 |
| 同会话乱序 / 双跑 | 并发后若边界不清，可能同会话重复执行或乱序 | 验收强调 S3、S6；设计阶段明确「会话内串行、会话间并行」 |
| 全局锁误用 | 若沿用全局单锁，可能仍串行 | 设计阶段以 sessionKey 为调度粒度验收 R4 |
| 可靠性回归 | 重试与 ack 与并发交织易出边界 bug | 对照已归档 dispatch 重入队验收矩阵做回归 |
| 产品债 T7 | 源码注释登记「T7 单条顺序 dispatch」为既有债 | 本变更目标即关闭该类产品债；archive 时更新知识库限制描述 |

## 九、知识库影响初评

| 文档 | 影响 |
|------|------|
| Daemon 守护进程概览（若记载单条顺序 dispatch / T7 债） | 高：归档时改写并发调度产品语义与剩余限制 |
| Agent 调度相关（多会话模型、dispatch 行为） | 中：补充「会话间并行、会话内顺序」说明 |
| 消息桥接 / 消息队列与路由（若涉及领取与门控描述） | 低～中：与合并、busy 门控交叉处划界 |
| Daemon 批二拆分归档结论 | 低：本变更与批二范围正交，summary 中勾销 T7 类债时注明依赖关系 |

初评结论：本变更为 **Agent 调度并发能力（功能）**；产品侧核心是跨会话并行与同会话顺序/合并不变，知识库以 Daemon / Agent 调度概览中「单条顺序 dispatch」债更新为主，细节在 `/kb-design` 与 archive 定稿。
