## 背景与问题

cursor-claw 支持多种 Agent 执行引擎（含 **Cursor SDK** 与 **Claude Code**），用户可通过飞书私聊、群聊等即时通讯通道与 Agent 交互，并在运行期间收到过程通知，以理解 Agent 正在做什么。

近期已在 **Cursor SDK** 路径上逐步建立较完整的飞书过程通知规范，包括：

- **工具调用通知分级**（`20260704183752-SDK工具调用通知分级`）：高频只读探查默认静默，命令执行、写文件、删除、子任务派发等关键动手类过程继续通知。
- **命令与子任务开始态信息增强**（`20260704212612-SDK shell started 携带具体命令`、`20260704212706-SDK开始态飞书通知携带描述`）：用户可在「开始执行」阶段看到具体命令或子任务描述，而非占位文案。
- **过程与结论时序编排**（进行中 `20260704190748-IM通知消息顺序与流式推送优化`）：过程通知与助手答复的呈现顺序可预期。
- **思考过程飞书静默**（关联 `20260704212716-think不再发送飞书消息`）：飞书侧不再推送思考类过程消息，但桌面端仍可观测，且过程编排闩锁机制保持正常。

然而，当用户切换为 **Claude Code** 引擎时，飞书侧过程通知行为与 Cursor SDK **不一致**，主要体现在：

1. **通知范围不对齐**：只读探查类过程在飞书仍可能大量出现，而 Cursor SDK 已默认静默；关键动手类过程的可见性与文案丰富度也不对称。
2. **开始态信息不足**：命令执行、子任务启动等「开始」里程碑在 Claude Code 路径下，往往缺少与 Cursor SDK 同等可识别的命令摘要或任务描述。
3. **重复与冗余**：同一运行中可能出现重复的过程提示（如相邻相同操作、子任务与工具过程双推），Cursor SDK 已治理而 Claude Code 未对齐。
4. **思考与编排体验割裂**：思考过程在飞书侧的静默策略、以及过程通知与后续答复的编排一致性，在 Claude Code 路径下与 Cursor SDK 存在差异，用户难以形成稳定预期。

多引擎并存的产品目标是：**同一产品、同一通道、同一类过程事件，应遵循统一的用户可感知契约**；Cursor SDK 现行规范应作为多引擎飞书通知的**统一契约基准**，Claude Code 须与之对齐。知识库侧亦缺少「多引擎统一契约」的集中说明（见 `knowledge/业务域/消息桥接/02-飞书通道.md` 缺口）。

## 目标与非目标

### 目标

1. **确立统一契约**：以 Cursor SDK 现行飞书过程通知规范为 SSOT，在 PRD 与设计阶段明确「应通知 / 默认静默 / 开始态文案 / 去重 / 编排」等产品原则，供 Claude Code 对齐及后续引擎扩展引用。
2. **Claude Code 行为对齐**：用户在飞书私聊、群聊下使用 Claude Code 引擎时，过程通知的分级、里程碑文案、开始态信息量、去重与编排体验与 Cursor SDK **一致**。
3. **关键信号可见、噪音可控**：命令执行、写文件、删除、子任务派发等动手类过程继续及时、可理解地通知；读文件、目录匹配等高频只读探查默认不向飞书推送里程碑。
4. **思考不刷屏、编排不断裂**：飞书侧思考过程保持静默（与关联变更策略一致），但不影响 task、关键工具过程与助手答复的时序编排与「过程在上、结论在下」等既有产品目标。
5. **多通道原则一致**：飞书私聊与群聊在分级与文案原则上保持一致；群聊可沿用既有更严格的聚合策略，但不得出现与私聊原则性相反的行为。

### 非目标

- **Codex SDK、OpenCode SDK** 等其他执行引擎的飞书通知对齐**不在本次验收范围**；可在方案中标注为后续扩展，但本 PRD 不承诺交付。
- 不改造 Electron 设置界面、不新增终端用户可配置的「按引擎/按工具开关通知」能力（可作为后续增强）。
- 不改变 Agent 内部推理逻辑、工具调用能力或桌面端完整运行日志的可观测性；本次聚焦**飞书用户侧过程出站**与多引擎一致性。
- 不在本阶段定义具体模块、接口或实现方案（归属 `/kb-design`）。

## 用户故事

### 飞书私聊用户

- 作为在飞书私聊中使用 **Claude Code** 的用户，当 Agent 多次读取文件或搜索代码库时，我不希望收到大量「正在读取…」「正在搜索…」类提示；这与我用 Cursor SDK 时的体验应一致。
- 作为同一用户，当 Agent 开始执行命令或启动子任务时，我希望过程通知里能看到**可识别的命令或任务描述**，而不是笼统占位文案，且与 Cursor SDK 路径对称。
- 作为关注进度的用户，我希望思考过程**不再**在飞书刷屏，但子任务、命令执行等关键里程碑仍及时出现，且与最终答复的顺序清晰、不混乱。

### 飞书群聊用户

- 作为在群聊中 @ Agent 且使用 Claude Code 的用户，我希望过程通知遵循与 Cursor SDK 相同的分级原则：探查类默认静默，动手类可见；群聊可在呈现形态上更克制，但不应比私聊「更吵」或「更缺关键信息」。
- 作为围观群成员，我不希望看到同一操作的重复开始提示或子任务与工具过程的双推，避免干扰阅读。

### 多引擎切换用户

- 作为会在不同会话间切换 Cursor SDK 与 Claude Code 的用户，我希望在飞书侧对「什么会通知、什么默认静默、开始态写什么」形成**一套稳定预期**，不因引擎切换而突然刷屏或突然沉默。

### 运维与管理员

- 作为处理「飞书通知不一致」投诉的支持人员，我希望 Claude Code 与 Cursor SDK 在飞书过程通知上可对照同一套产品规范文档验收，减少引擎差异带来的解释成本。

## 功能需求

### F1 工具过程通知分级（与 Cursor SDK 契约一致）

| 编号 | 需求描述 |
|------|----------|
| F1.1 | **默认通知**：思考以外的动手类过程——命令执行、写文件、删除、子任务派发等——在 Claude Code 飞书路径下**须**与 Cursor SDK 一样向用户推送可理解的过程通知。 |
| F1.2 | **默认静默**：读文件、目录/模式匹配探查及同类高频只读探查，在 Claude Code 飞书路径下**默认不**向用户推送过程里程碑，与 Cursor SDK 分级原则一致。 |
| F1.3 | **桌面端完整记录保留**：默认静默仅指出站面向飞书用户的过程推送；桌面端运行界面与日志仍应保留完整过程可观测性，不因飞书静默而丢失排障信息。 |

### F2 开始态里程碑文案（命令与子任务）

| 编号 | 需求描述 |
|------|----------|
| F2.1 | **命令执行开始**：当 Agent 开始执行系统命令且属于应通知范围时，飞书过程通知的「开始」文案**须包含可识别的具体命令**（允许合理截断），与 Cursor SDK 已开始态体验对称。 |
| F2.2 | **子任务开始**：当 Agent 启动子任务且属于应通知范围时，飞书过程通知的「开始」文案**须包含可理解的子任务描述**（允许合理截断），与 Cursor SDK 已开始态体验对称。 |
| F2.3 | **降级可预期**：无法解析出命令或描述时，须有明确、用户可理解的降级文案，避免空白或仅显示内部占位词。 |

### F3 去重与冗余治理

| 编号 | 需求描述 |
|------|----------|
| F3.1 | **相邻重复抑制**：同一运行中，内容实质相同的相邻「进行中」过程提示不应重复推送，行为与 Cursor SDK 一致。 |
| F3.2 | **子任务与工具过程不双推**：子任务里程碑与等价工具过程不应在同一节点向用户重复呈现两次，与 Cursor SDK 治理原则一致。 |

### F4 思考过程与过程编排

| 编号 | 需求描述 |
|------|----------|
| F4.1 | **飞书思考静默**：思考类过程**不得**向飞书发送卡片、里程碑文本或等价通知，与关联变更 `20260704212716-think不再发送飞书消息` 的产品策略一致。 |
| F4.2 | **编排闩锁正常**：在思考静默前提下，task、关键工具过程与助手答复的时序编排仍须正常，不因 Claude Code 对齐而破坏进行中 ordering 变更所追求的过程/结论顺序目标。 |
| F4.3 | **其他过程通知不受影响**：task、notify 级工具开始态等飞书过程通知不在思考静默范围内，继续按分级与文案规范出站。 |

### F5 多引擎统一契约（知识库）

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 设计阶段须在知识库中补充「多引擎飞书过程通知统一契约」说明，明确 Cursor SDK 为基准、Claude Code 为本次对齐对象、其他引擎为后续范围。 |
| F5.2 | Claude Code 引擎说明文档须体现分级、开始态字段、禁止通道侧过早丢弃过程事件等产品约束，与统一契约一致。 |

## 边界与后续范围

- **本次验收引擎**：仅 **Claude Code** 对齐 Cursor SDK 飞书过程通知契约。
- **后续范围（非本次验收）**：**Codex SDK**、**OpenCode SDK** 等引擎存在类似的飞书抑制与全量出站问题，列入后续单独立项，本 PRD 仅作范围标注。
- **微信等其他 IM 通道**：若当前与飞书策略不一致，不在本单强制统一，除非设计阶段发现必须联动；默认以飞书对齐为主战场。

## 验收标准

1. **分级一致**：在典型多步任务（含多次读文件、目录匹配与多次命令/写入）中，使用 **Claude Code** 引擎时，飞书私聊与群聊过程流**不出现**针对只读探查类的逐条里程碑；命令执行、写文件、删除、子任务派发等动手类过程在合理时延内**能收到**可理解通知，且与 **Cursor SDK** 同任务对比行为一致。
2. **开始态文案对称**：Claude Code 路径下，命令执行开始通知**含可识别命令摘要**；子任务开始通知**含可理解任务描述**；与 Cursor SDK 同场景并排验收时，信息量与语义层级对称（允许通道排版差异，不允许一方仅有占位、另一方有摘要）。
3. **思考不刷屏、编排正常**：飞书侧**零**思考类过程出站；同一运行中 task、关键工具过程与助手答复的呈现顺序符合 ordering 产品目标，无因对齐引入的乱序或长期沉默。
4. **去重有效**：相邻实质相同的「进行中」提示不重复推送；子任务与等价工具过程不双推；与 Cursor SDK 同场景对比，冗余条数显著减少且原则一致。
5. **多引擎用户预期**：同一用户在飞书私聊/群聊间切换 Cursor SDK 与 Claude Code 时，对「哪些过程会通知、哪些默认静默、开始态写什么」无原则性反差；支持人员可依据统一契约文档逐项验收 Claude Code。
6. **知识库可追溯**：`02-design` 须将本 PRD 的 F1–F5 与验收项映射至统一契约说明及 Claude Code 对齐落点；**Codex/OpenCode** 仅出现在「后续范围」，不纳入本次工程验收清单。
