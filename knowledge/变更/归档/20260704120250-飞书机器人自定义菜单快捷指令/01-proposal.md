## 一、背景与问题

cursor-claw 已通过飞书私聊支持文本斜杠指令（如 `/help`、`/status`、`/reset`、`/stop` 及管理员专用指令），用户发送指令后系统执行并回复结果。与 Cursor 客户端不同，**飞书 IM 输入框不支持输入 `/` 后自动补全斜杠命令**，用户必须完整记忆并手动输入指令文本。

飞书官方推荐的替代方案是：**在机器人私聊会话中配置「自定义菜单」**，用户点击菜单项即可触发预设动作；配合服务端对菜单事件的解析与交互卡片回复，可在不依赖输入框补全的前提下，提供与斜杠指令等价的快捷操作体验。

当前 cursor-claw 的指令能力已较完整，但**可发现性不足**：新用户进入私聊后不知道有哪些指令、如何分组、哪些需要管理员权限；老用户也需反复查阅文档或记忆长指令（如 `/chat new`、`/workspace` 等）。本变更旨在通过飞书机器人自定义菜单与进入私聊时的帮助引导，降低指令使用门槛，与现有文本斜杠指令体系**并存、语义一致**，而非另建一套控制逻辑。

此外，自定义菜单与进入私聊帮助依赖飞书开放平台上的**应用权限与事件订阅**。对于**已接入 cursor-claw 的飞书通道**（应用已创建、凭证已配置），管理员若需开通菜单相关能力，目前只能自行登录飞书开发者后台逐项查找、申请权限与事件，流程繁琐且易漏配。设置页虽支持「一键创建新应用」，但**未覆盖对已有应用增量补开权限**的场景，导致存量用户启用本变更所需能力的门槛偏高。

## 二、目标用户

| 用户类型 | 说明 |
|--------|------|
| **主用户 / 管理员** | 在飞书私聊中管理 cursor-claw 会话、工作区、模型、任务与工作流；需快速触达管理员级指令 |
| **普通私聊用户** | 在授权范围内使用 cursor-claw；仅需常用会话控制（状态查询、停止、重置、帮助） |
| **新用户 / 低频用户** | 首次或与机器人建立私聊关系时，需要明确知道「能做什么、从哪里点」 |

**首期范围**：飞书**私聊**场景；不涉及群聊自定义菜单（受飞书平台能力限制）。

## 三、用户故事与使用场景

### 3.1 新用户首次进入私聊

作为第一次打开与 cursor-claw 机器人私聊的用户，我希望在进入会话时自动收到一张**指令帮助卡片**，列出常用操作说明与「点击输入框旁菜单可快捷执行」的引导，而不必先去查文档或试错输入 `/help`。

### 3.2 普通用户快捷查状态或停任务

作为普通私聊用户，我不想记忆 `/status`、`/stop` 等文本格式。我点击私聊输入框旁的**基础指令菜单**（如「查看状态」「停止当前任务」「重置会话」「帮助」），即可得到与手动发送对应斜杠指令**一致的结果与权限边界**。

### 3.3 管理员快捷管理配置与会话

作为管理员（主用户），除基础指令外，我还需要**管理员指令菜单**分组，一键触达工作区切换、模型切换、新建临时会话等高频管理操作；点击后行为与现有管理员斜杠指令一致，非管理员不应看到或无法成功执行这些菜单项。

### 3.4 菜单点击的可靠触发

作为用户，我点击菜单项时期望**稳定、低延迟**的响应。无论菜单在飞书侧配置为「推送事件」还是「发送文字消息」，我感知到的结果应相同：系统正确识别我的意图并执行对应指令、在私聊中给出明确反馈；不应出现「点了菜单但系统无反应」或「仅发出一段用户可见的占位文字而未真正执行」的情况。

### 3.5 与现有 CardKit 控制并存

作为已在使用合并预览卡片、流式回复等能力的用户，我希望菜单快捷指令**补充**而非取代现有卡片内控制（如合并预览编辑、后续卡片按钮控制）。菜单解决的是「指令发现与一键触发」，CardKit 控制解决的是「会话内结构化操作」。

### 3.6 管理员为已有通道扫码补开权限

作为已配置飞书通道的管理员，我不希望为了开通菜单与进入私聊帮助而去飞书开发者后台逐项摸索权限名称。我希望在 cursor-claw **设置页**对当前已有通道发起「扫码更新权限」，系统预置本次菜单能力所需的权限与事件清单，我扫码确认后权限即生效，从而尽快启用自定义菜单与相关事件，而无需重新创建应用或手动对照文档逐项勾选。

## 四、功能需求

### 4.1 机器人自定义菜单（私聊）

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 在飞书机器人**私聊**会话中提供**自定义菜单**，用户可通过输入框旁菜单入口访问，无需手动输入斜杠文本 |
| F1.2 | **基础指令分组**（所有授权私聊用户可见、可点）：覆盖与现有体系等价的 `/help`、`/status`、`/reset`、`/stop`；各菜单项展示名称与简短说明，用户可理解点击后会发生什么 |
| F1.3 | **管理员指令分组**（仅管理员可见或可成功执行）：覆盖现有管理员斜杠能力中的高频项，至少包括工作区相关（`/workspace`）、模型相关（`/model`）、新建临时会话（`/chat new`）等；具体菜单项清单可在设计阶段与现有指令表对齐，但权限模型须与现有一致 |
| F1.4 | 菜单点击后，系统执行与对应斜杠指令**相同语义**的操作，并在私聊中返回与文本指令路径**一致类型**的反馈（如状态摘要、确认文案、错误提示） |
| F1.5 | 支持飞书「**推送事件**」类菜单响应：用户点击后由服务端根据菜单标识处理，**不依赖**「向会话发送一段用户可见文字再由系统二次解析」作为唯一路径；首期须将推送事件菜单作为一等能力验收 |
| F1.6 | 若部分菜单项在飞书侧配置为「发送文字消息」形式，用户感知结果仍须与 F1.4 一致（即最终仍执行对应指令逻辑，而非仅停留在展示一条静态文本） |
| F1.7 | 非管理员点击管理员菜单项时，须给出**明确、可理解**的无权限提示，不得静默失败或误执行 |

### 4.2 进入私聊时的帮助卡片

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 当用户**进入与机器人的私聊**（首次打开或重新进入会话的 product 语义以飞书「进入私聊」事件为准）时，系统自动推送一张**指令帮助交互卡片** |
| F2.2 | 帮助卡片须包含：常用基础指令说明、管理员指令入口说明（对非管理员可省略或标注「仅管理员」）、**自定义菜单位置与用法**的简短引导 |
| F2.3 | 帮助卡片内容应与 `/help` 及菜单项语义**一致**，避免三套互相矛盾的文案 |
| F2.4 | 须考虑**重复进入私聊**时的体验：避免每次进入都刷屏；产品规则可为「首次进入 / 距上次帮助超过一定间隔 / 用户主动请求帮助时再推」，具体策略在设计阶段定稿，但验收须覆盖「不会无限重复骚扰」与「新用户能收到引导」两点 |

### 4.3 权限与安全

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 菜单可见性与可执行性遵循现有斜杠指令**二分权限模型**：管理员（主用户）与普通私聊用户 |
| F3.2 | 普通用户可用范围：`/help`、`/status`、`/reset`、`/stop`（本会话）及对应菜单项 |
| F3.3 | 管理员额外可用：工作区、模型、会话管理、任务与工作流等现有管理员指令及对应菜单项 |
| F3.4 | 权限变更（如主用户配置调整）后，菜单展示与执行结果须与最新权限一致，不得长期缓存错误可见性 |

### 4.4 设置页扫码更新飞书权限

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 在飞书通道**设置页**提供「**扫码更新权限**」入口，面向**已绑定应用**的存量通道；与现有「一键创建应用」**并存**，互不替代——新建应用走创建流程，已有应用走扫码补开 |
| F4.2 | 发起扫码更新时，系统**预置**本变更所需的权限与事件清单，至少覆盖：机器人自定义菜单写入、菜单点击事件接收、用户进入机器人私聊事件接收；管理员无需自行查阅飞书文档拼清单 |
| F4.3 | 管理员使用飞书客户端扫码并确认后，所缺权限与事件**增量开通**至当前通道对应的应用；已开通项保持不变，流程以「补全缺口」为目标 |
| F4.4 | 扫码**失败、超时或用户取消**时，设置页须给出**可理解**的提示（如未完成授权、已取消、网络异常等），并说明可重试；不得静默无反馈 |
| F4.5 | 扫码更新权限**不修改**应用凭证（App ID、App Secret 等）；仅变更开放平台侧权限与事件订阅范围 |

## 五、非目标

| 编号 | 说明 |
|------|------|
| NG1 | **不做**飞书输入框内输入 `/` 的实时补全或斜杠命令联想（飞书 IM 不支持，亦非本变更范围） |
| NG2 | **不做**群聊场景的机器人自定义菜单（飞书平台对群聊菜单能力有限制，首期仅私聊） |
| NG3 | **不替代**现有 CardKit 合并预览卡、流式卡片及卡片内编辑/控制（如合并预览回复修改、后续卡片按钮控制）；菜单与卡片控制互补 |
| NG4 | **不新增**与现有斜杠指令语义冲突的平行指令体系；菜单是指令的**触达方式**，不是新业务能力 |
| NG5 | **不在本期**重构全部管理员指令为菜单（首期覆盖高频子集即可，其余仍可通过文本斜杠使用） |
| NG6 | **不在 PRD 阶段**定义实现细节、接口或模块落点（归属后续设计） |
| NG7 | **扫码更新权限不能替代**飞书开发者后台中自定义菜单的**结构与内容配置**（菜单分组、项名称、事件标识等）；扫码仅解决权限与事件订阅，菜单 UI 仍须在飞书侧维护 |

## 六、验收标准

以下标准均可通过飞书私聊**实际操作**验证，且关注**用户可感知**结果。

### 6.1 自定义菜单 — 基础指令

1. 普通私聊用户打开与机器人私聊，可在输入框旁看到**基础指令菜单**，且包含帮助、状态、重置、停止等等价入口。
2. 点击「查看状态」类菜单项后，私聊中出现与发送 `/status` **语义一致**的状态反馈。
3. 点击「停止」类菜单项后，行为与 `/stop` 一致：普通用户停止本会话，管理员停止范围与现网一致。
4. 点击「重置」与「帮助」后，结果分别与 `/reset`、`/help` 一致。

### 6.2 自定义菜单 — 管理员指令

5. 管理员私聊中可见**管理员指令分组**（或等价入口），可一键触发工作区、模型、新建临时会话等首期纳入的管理员操作。
6. 非管理员**看不到**管理员分组，或点击后收到清晰无权限提示，且**未**发生管理员级副作用。
7. 管理员点击菜单项后，执行结果与手动发送对应斜杠指令一致（含成功确认与失败说明）。

### 6.3 推送事件菜单

8. 至少一项菜单通过飞书「推送事件」方式配置并验收：用户点击后，**无需**依赖「机器人在会话中发出一条待解析的用户可见文字」作为唯一触发手段，系统仍能正确执行并回复。
9. 推送事件菜单与「发送文字消息」类菜单（若存在）在用户感知上**结果一致**，无「一种能用、另一种只发字不执行」的分裂体验。

### 6.4 进入私聊帮助卡片

10. 新用户（或符合产品规则的再次进入场景）进入机器人私聊时，收到**指令帮助卡片**，内容涵盖常用指令与菜单使用说明。
11. 帮助卡片与 `/help`、菜单项文案**无矛盾**；用户读完能知道如何点击菜单完成操作。
12. 重复进入私聊时**不会**无节制重复推送帮助卡片（具体节流规则以实现阶段产品决策为准，但须可验收）。

### 6.5 与现有能力共存

13. 用户仍可通过**手动输入**斜杠指令完成全部已有操作；菜单上线后文本路径**不被破坏**。
14. 合并预览、流式回复、CardKit 相关体验**不因**本变更而回退或冲突。

### 6.6 扫码更新飞书权限

15. 管理员在飞书通道设置页可见「扫码更新权限」入口；对**已绑定应用**的通道发起后，能展示扫码引导，且预置清单覆盖菜单写入、菜单事件、进入私聊事件等本变更所需项。
16. 管理员扫码并确认后，飞书开发者后台中对应应用已**新增**上述权限与事件订阅（与扫码前对比可感知）；应用原有凭证与通道配置**未被重置或替换**。
17. 扫码取消或失败时，设置页出现**明确、可理解**的提示，管理员可再次发起；「一键创建应用」入口仍可用，两者互不遮挡。

## 七、风险与依赖

| 类别 | 说明 |
|------|------|
| **飞书平台能力** | 自定义菜单、推送事件（`application.bot.menu_v6`）、进入私聊事件（`im.chat.access_event.bot_p2p_chat_entered_v1`）依赖飞书开放平台配置与事件订阅；菜单结构变更需经飞书侧发布生效 |
| **客户端版本** | 部分菜单或卡片能力可能受飞书客户端版本影响；须在验收环境注明最低客户端版本或给出降级说明 |
| **菜单配置与发布** | 菜单项名称、分组、事件标识需在飞书开发者后台维护；配置错误可能导致点击无响应或映射到错误指令，需有发布核对清单 |
| **权限一致性** | 菜单可见性与服务端执行权限须双重一致；仅隐藏菜单但服务端不校验会导致越权风险 |
| **文案与指令表同步** | 现有斜杠指令表演进时，菜单与帮助卡片须同步更新，避免「菜单写的是 A、执行的是 B」 |
| **与控制层演进关系** | 与「飞书作为 Cursor 展示与控制层」方向一致：菜单属于**控制触达**补充，与 CardKit 卡片按钮控制并行规划，避免重复建设相同入口 |
| **扫码更新仅增量叠加** | 飞书侧扫码更新权限**仅支持增量开通**，不能通过该流程收回或替换已开通权限；敏感配置（如事件订阅方式、回调地址等）仍须在开发者后台按既有方式维护，不能指望扫码一并完成 |
| **菜单 UI 仍须后台配置** | 即使权限与事件已通过扫码补齐，自定义菜单的**分组、项名称、图标与事件标识**仍须在飞书开发者后台手动配置并发布；产品与验收须区分「权限就绪」与「菜单已上线」两个阶段 |
| **版本发布与管理员审批** | 部分权限或能力变更可能仍需在飞书后台**发布应用版本**并经企业管理员审批后全量生效；扫码完成授权不保证即时在全企业可用，须预留说明与验收缓冲 |

## 八、与现有能力的关系

- **远程斜杠指令体系**：本变更不改变指令语义与权限划分，仅增加**菜单点击**与**进入私聊帮助**两种触达方式。
- **飞书消息桥接**：菜单事件与帮助卡片均发生在飞书私聊通道内，须与现有入站消息、出站回复体验协调（如不刷屏、错误可理解）。
- **CardKit 控制**：合并预览编辑、后续卡片按钮等仍按既有规划演进；本变更不占用其验收范围。
- **飞书应用注册与设置页**：「一键创建应用」继续服务新用户；「扫码更新权限」扩展服务存量通道，共同降低开通菜单相关开放平台能力的手动成本，但不改变菜单结构与凭证管理的主责边界。
