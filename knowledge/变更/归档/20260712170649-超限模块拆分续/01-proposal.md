## 一、背景与问题陈述

项目工程规范要求**单个源码文件不超过 300 行**（见仓库 AGENTS 规范）。**巨型单体拆分（批 1）** 已完成 Daemon 侧 HTTP 管理面、编排调度衔接、展示出站等部分垂直切分；**file-queue** 等模块亦已部分拆分。但核心链路中仍有多处**严重超限**文件，体量远超可读性与评审门槛，阻碍后续迭代与 Code Review 效率。

当前仍待清偿的主要超限模块（行数截至 propose 阶段核实）：

| 模块 | 约行数 | 主要职责 |
|------|--------|----------|
| 飞书桥接核心 | ~1190 | CardKit 渲染、流式卡片、工具进度卡、合并卡、事件连接与出站发送 |
| 设置页 | ~962 | 多 Tab 设置 UI、引擎/MCP/通道/工作流等配置入口 |
| 通道面板 | ~687 | 各 IM 通道配置表单与辅助说明 |
| 斜杠指令处理 | ~750 | Electron 侧斜杠指令解析与执行分发 |
| 配置更新器 | ~864 | 应用配置热更新与持久化逻辑 |

上述文件已在多轮变更中被标注为 **accepted_debt**（如合并卡飞书按钮变更 D1、`ChannelPanel` 微信入队变更 R-01 等），本轮为**续拆清偿**，非重复立项。

**本变更明确不做**：`daemon.ts`、`daemon-manager.ts`（归 **Daemon批二拆分** 及后续批次）；不做任何用户可见功能行为变更。

现状带来的产品侧与协作侧影响：

1. **定位成本高**：排查飞书流式/合并卡异常、设置页字段回归、斜杠指令失败等问题时，协作者需在超长文件中全文检索，排障与回归范围难以界定。
2. **变更风险大**：设置页与通道面板任一字段演进、飞书出站逻辑微调，均易牵动同一巨型文件，增加无意耦合与 UI/IM 行为回归概率。
3. **规范不可持续**：若不继续拆分，后续功能迭代将持续违反单文件行数约束，技术债滚雪球。
4. **与批 1  backlog 不一致**：巨型单体拆分归档已将 `lark-core` 拆分为 **T13 deferred**；Daemon 批二非目标亦排除 lark-core——本变更承接该 backlog 的**桥接/UI/配置**续拆。

## 三、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 短期无直接 UI 变化 | 飞书流式/合并卡/工具卡、设置页 Tab 与字段、通道面板表单与拆分前一致 |
| 排障与修复变慢 | 飞书出站或设置字段故障需通读超长文件，定位与验证周期长 |
| 演进易引入回归 | 局部改动易误伤相邻 CardKit/流式/表单逻辑，抬高 IM 展示错误或配置保存异常风险 |
| 评审成本高 | 单次 PR 动辄数百行同文件 diff，Review 难以聚焦职责边界 |

## 四、目标与非目标

### 目标（必须达成）

1. **分期拆分至合规**：按依赖与风险分三期，将纳入范围的各源码文件拆分后**单文件 ≤300 行**。
2. **一期 — 飞书桥接**：`lark-core` 按 **CardKit 渲染 / 流式发送 / 出站与连接** 等职责垂直切分；用户不可见，飞书主路径行为等价。
3. **二期 — 设置 UI**：`Settings` 与 `ChannelPanel` 按 Tab/子面板/纯展示块拆分；**布局与交互字段不变**。
4. **三期 — 配置与指令（可选）**：`command-handler`、`updater` 按职责拆分；PRD 标为后续批次，design 阶段可 defer 至单独 archive 轮次。
5. **降低回归成本**：拆分后设置页、通道面板、飞书出站各有清晰落点，便于后续功能变更做小范围 PR。

### 非目标（明确不做）

- **不改** `daemon.ts`、`daemon-manager.ts` 及 Daemon 批二 queue/channel/logging 范围。
- **不做** 飞书卡片版式、合并策略、流式时序、设置默认值或新增配置项等产品语义变更。
- **不做** 调度并发模型、T7 统一调度、日志双写统一等架构改造。
- **不在 propose 阶段** 绑定具体文件名、类名、内部接口签名（归属 `/kb-design`）。

## 五、用户与场景

### 用户

- **飞书 / 微信终端用户（间接）**：依赖流式回复、合并卡、工具进度卡与通道配置正确性；本轮不改变可见行为。
- **桌面端用户**：在设置页调整引擎、MCP、通道、工作流等配置；本轮不改变 Tab 结构、字段集合与保存语义。
- **运维 / 开发者**：通过斜杠指令与配置热更新维护系统；三期范围内行为与拆分前一致。
- **工程协作者**：需要在合规体量、清晰模块边界下安全迭代桥接层与设置 UI。

### 场景

| 场景 | 简述 | 期次 |
|------|------|------|
| **S1 飞书流式回复** | Agent 产出经桥接层流式 PATCH/终态展示，时序与内容粒度与拆分前一致 | 一期 |
| **S2 合并卡与工具卡** | 合并批次 CardKit、工具进度卡、按钮回调（若已启用）行为不退化 | 一期 |
| **S3 设置页读写** | 各 Tab 加载、编辑、保存配置与拆分前一致，无字段丢失或错位 | 二期 |
| **S4 通道面板** | 飞书/微信等通道表单项、下拉与辅助说明与拆分前一致 | 二期 |
| **S5 斜杠指令** | 授权斜杠解析与执行路径正常（若纳入三期） | 三期（可选） |
| **S6 配置热更新** | 配置变更持久化与热生效路径正常（若纳入三期） | 三期（可选） |
| **S7 结构合规** | 纳入范围各文件 ≤300 行，职责边界可说明 | 全期 |

## 七、验收标准

### 7.1 一期（飞书桥接）

1. 飞书**流式回复**、**合并卡**、**工具进度卡**行为与拆分前一致；无系统性静默失败或卡片空白。
2. `card.action.trigger` 等已启用事件回调链不退化（对照合并卡相关归档验收口径）。
3. 拆分后 lark-core 及新模块**单文件 ≤300 行**。

### 7.2 二期（设置 UI）

1. 设置页各 Tab **交互、字段集合、保存语义**与拆分前一致；通道面板表单与辅助说明不变。
2. 拆分后 Settings、ChannelPanel 及新组件**单文件 ≤300 行**。

### 7.3 三期（可选）

1. 若纳入：斜杠指令与配置热更新主路径与拆分前一致。
2. 拆分后 command-handler、updater 及新模块**单文件 ≤300 行**。

### 7.4 非功能

1. 变更代码含中文注释（与项目规范一致）。
2. 不引入与拆分无关的策略默认值变更。
3. **Figma**：`auto-none` — 无布局/视觉变更，无需设计稿。

## 八、范围边界

### 在范围内

- 一期：`lark-core` 职责拆分与 import 链整理。
- 二期：`Settings`、`ChannelPanel` UI 组件拆分。
- 三期（可选）：`command-handler`、`updater` 拆分；design 阶段可标记 defer。
- 归档阶段同步桥接层 / Electron 桌面应用工程平台知识中模块职责描述（若有失真）。

### 不在范围内

- Daemon 枢纽（`daemon.ts`）、`daemon-manager.ts`、Daemon 批二 queue/channel/logging。
- 用户可见功能、卡片版式、设置项语义变更。
- 调度并发、T7、日志双写统一。

## 九、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| Daemon 批二并行 | 批二改枢纽 import，本变更改 lark-core/设置 UI，可能间接冲突 | `depends_on` 登记批二；并行时 design 划**文件白名单**；建议批二后再动枢纽↔桥接接线 |

| 三期 scope 膨胀 | command-handler/updater 耦合面大 | PRD 标可选；design 阶段可 defer 为独立 archive 轮次 |
| 历史债务勾销 | 多归档 D1/R-01 指向本变更 | archive summary 勾销对应 accepted_debt |
