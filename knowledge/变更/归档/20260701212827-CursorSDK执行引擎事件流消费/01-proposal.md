## 背景与问题

cursor-claw 的 Cursor SDK 执行引擎负责在即时通讯（飞书/微信）、任务面板、工作流等路径上运行 Agent，响应用户消息与自动化任务。

在 Cursor SDK 官方模型中，每次向 Agent 发送一条任务会启动一次「运行」；运行期间会持续产出标准化事件流，其中包括：助手回复内容、思考过程、工具调用与结果、运行生命周期状态、任务阶段里程碑、用量与计费等。这些事件是用户侧实时进度、工具过程展示、运行状态判断与用量感知的**唯一可靠来源**。

**现状问题**：

1. **事件流消费不完整**：部分运行路径未系统化地持续消费上述事件流，而是主要依赖「等待运行结束再取最终结果」。一旦运行耗时较长、需要等待用户确认、或进程发生中断，用户与系统都无法获得完整的过程与状态，即时通讯侧的流式文本与过程展示也会中断或缺失。
2. **进程重启后无法续接**：应用主进程因版本更新重启或意外崩溃后，进行中的运行无法自动续接；用户只能重新发起，此前的沟通背景与执行进度丢失。
3. **长任务易被误判终止**：运行处于正常的长耗时执行或等待用户回复的空闲窗口时，内部的「是否卡住」判断机制可能将其误判为异常，从而强制提前终止本应继续的任务。

用户明确要求：**所有 Cursor SDK 运行路径都必须消费事件流**，不能只依赖一次性等待终态；否则长任务、断线重连、多订阅者补流等场景无法获得完整过程与状态。

## 目标与非目标

### 目标

1. **全路径事件流消费**：即时通讯、任务面板、工作流等所有 Cursor SDK 运行入口，在每次运行期间均持续消费标准化事件流，并据此驱动进度展示、状态判断与收尾逻辑。
2. **过程可观测、可恢复**：运行中的助手输出、思考、工具调用、状态变化、任务里程碑与用量信息能被系统正确接收、分发与持久化关联，为断线重连与多订阅者补流提供基础。
3. **重启后可续接未结束运行**：应用主进程重启或崩溃恢复后，对尚未结束的运行能够继续接收事件并将后续结果正确推送回原会话或任务，用户无需重新发起。
4. **长任务不误杀**：在合理的长耗时与长等待场景下，系统依据事件流中的真实活动与状态进行判断，不因缺少事件消费而误判为卡住并强制终止。
5. **短任务体验不退化**：常见短问答、单步工具调用等轻量场景，响应速度与现有体验保持一致，不因事件流改造引入明显延迟或重复通知。

### 非目标

- 不改变 Claude Code SDK、Codex SDK、OpenCode SDK 等其他执行引擎的事件处理与续接机制（本次仅针对 Cursor SDK 执行引擎）。
- 不向终端用户暴露原始事件类型名称、内部错误堆栈或实现细节；过程展示仍遵循既有「用户可理解」的呈现策略。
- 不追求对超出合理时限的极端长运行无限期保活；超长时限策略留待后续单独评估。
- 不涉及 Electron 设置界面、通道凭据配置等桌面端 UI 改造（除非仅为展示运行状态所必需且与既有呈现一致）。

## 用户故事

### 最终用户

- 作为通过飞书/微信与 Agent 对话的用户，我希望在 Agent 执行多步任务时，能持续看到处理进度与逐步产出的内容，而不是长时间沉默后突然收到一条完整回复或毫无反馈。
- 作为在长任务执行期间隔较长时间才回复的用户，我希望回复后任务能继续正常推进，而不是发现任务早已被系统判定超时取消。
- 作为在应用更新重启后回到原会话的用户，我希望此前进行中的对话或任务能够自动续上，历史沟通与进展不丢失，并能继续收到后续执行结果。
- 作为通过任务面板或工作流触发 Agent 的用户，我希望任务执行过程的状态与产出与 IM 通道一致可追踪，不因入口不同而缺失过程信息。

### 运维与管理员

- 作为负责发布新版本的管理员，我希望版本更新触发的应用重启后，用户手中正在运行的任务能够平滑续接，减少升级对用户体验的影响。
- 作为运维人员，我希望进程崩溃恢复后，能够区分哪些运行成功续接、哪些未能续接，而不是任务无声消失、无从判断状态。
- 作为排查问题的支持人员，我希望能够通过运行期间的事件流判断任务卡在哪个阶段（思考、工具、等待用户等），而非只能看到「处理中」或「已失败」的粗粒度状态。

## 功能需求

### F1 运行期间持续消费事件流

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 每次 Cursor SDK 运行自启动至结束（成功、失败、取消、超时等），执行引擎须**持续订阅并处理**该运行产出的事件流，不得仅阻塞等待最终一次性结果。 |
| F1.2 | 须覆盖的事件类别包括：**助手输出**（含流式文本片段）、**思考过程**（按产品呈现策略）、**工具调用与结果**、**运行生命周期状态**（启动、进行中、结束、异常等）、**任务阶段里程碑**、**用量与计费相关信息**。 |
| F1.3 | 上述消费逻辑须覆盖**即时通讯、任务面板、工作流**三条触发路径，行为一致，不因入口不同而跳过事件流。 |

### F2 基于事件流驱动用户侧呈现

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 助手输出的流式片段须及时传递到消息通道，支持同一条消息内逐步更新（在通道能力允许的场景下）。 |
| F2.2 | 思考过程与工具调用须按既有 Presentation 策略呈现或抑制，与事件流到达时序一致，避免「运行已结束才批量补发过程」。 |
| F2.3 | 运行状态变化须驱动通道侧「处理中 / 完成 / 失败」等用户可理解的三态或等价反馈，与事件流中的生命周期事件对齐。 |

### F3 基于事件流的状态判断与收尾

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 「是否仍在正常执行」的判断须以事件流中的**最近活动与显式状态**为依据，而非仅依赖墙钟时间或缺少事件更新时的静默假设。 |
| F3.2 | 运行进入结束类状态时，须通过事件流感知并触发一致的收尾：释放占用、更新会话为可接收下一条消息、向用户发送可理解的结束或失败提示（沿用既有文案策略）。 |
| F3.3 | 工具执行、子任务委派等可能长时间无助手文本输出但仍属正常活动的阶段，须在事件流层面被识别为「有进展」，避免被空闲超时机制误杀。 |

### F4 进程重启与运行续接

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 应用主进程重启（含版本更新触发）或崩溃恢复后，对重启前尚未结束的 Cursor SDK 运行，系统应尝试**继续接收该运行的事件流**并将后续产出推送回原 IM 会话或任务上下文。 |
| F4.2 | 续接成功后，用户侧看到的历史沟通与任务进展与中断前保持一致，不出现错乱或重复刷屏。 |
| F4.3 | 确实无法续接时，用户须收到**一次**明确、可理解的提示（说明未能自动恢复、可如何继续），而非任务静默消失。 |
| F4.4 | 用户主动停止或放弃会话后，不应再尝试续接该会话下已终止的运行。 |

### F5 短任务与性能

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 单次运行时长在常见短问答范围内的场景，从用户发消息到首段可见反馈的时延与改造前相比**无明显退化**（用户感知层面）。 |
| F5.2 | 事件流消费不得引入与终态等待相比更差的「双倍等待」或明显重复的系统通知。 |

## 边界与例外

| 情形 | 处理方式 |
|------|----------|
| 用户主动点击停止 | 立即停止消费并收尾，按既有停止语义通知用户；不续接该次运行。 |
| 平台侧主动结束运行（如运行时长上限） | 通过事件流感知结束状态，按既有「非用户取消」类友好文案提示，会话恢复为可发新消息。 |
| 通道不支持流式更新 | 可降级为分段发送或完成后一次性回复，但仍须在运行期间消费事件流以驱动内部状态与收尾，不得退化为仅等终态。 |
| 群聊等非优先流式场景 | 入队确认与三态进度仍须与事件流对齐；流式呈现可按既有二期策略降级，但事件消费本身不可省略。 |
| 消息被指令系统拦截、未进入常规定义的处理队列 | 不适用本 PRD 的运行与事件流规则，沿用既有指令反馈逻辑。 |

## 验收标准

1. **全路径消费**：在即时通讯、任务面板、工作流各选至少一条典型路径发起 Cursor SDK 运行，可观察到运行期间持续有事件驱动的进度或流式输出，且运行结束时状态与通道展示一致；**不得**出现「仅运行结束后才一次性出现全部内容、过程中完全无内部状态更新」的情况。
2. **过程事件覆盖**：含多步工具调用的运行中，思考/工具/助手输出（按产品策略可见或抑制）与运行状态变化均与事件到达时序一致，无批量滞后补发。
3. **长任务不误杀**：模拟或真实触发「长时间工具执行」或「长时间等待用户回复后继续」的场景，运行**不应**被空闲类超时机制误判终止；用户回复或工具完成后任务可继续。
4. **重启续接**：在一个进行中的运行尚未结束时重启应用主进程；恢复后用户在原 IM 会话或任务面板中**无需重新发起**即可继续收到后续执行结果；上下文与进展与中断前一致。
5. **续接失败兜底**：在无法续接的场景（如运行已自然结束、会话已主动停止等），用户收到**一次**明确提示，而非静默无响应。
6. **短任务不退化**：短问答类请求的首段可见反馈时延与改造前相比，在人工对比下无明显变慢；无新增重复或矛盾的状态通知。
7. **主动停止不续接**：用户主动停止后重启应用，系统**不应**再向该会话推送已停止运行的后续事件或误导性「仍在处理」状态。
