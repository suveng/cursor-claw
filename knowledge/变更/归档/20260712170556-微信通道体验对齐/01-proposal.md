## 一、背景与问题陈述

飞书为**主通道**：具备合并卡、自定义菜单、Get+CardKit 进行中反馈等能力，用户能较清晰感知「是否在处理」「是否在排队」「能否合并连发」。

微信为**次通道**：群聊 @ 依赖正文启发式（协议无 mention 元数据）；进行中主要依赖 typing；无合并卡与菜单。知识库 [消息桥接概览](../../../业务域/消息桥接/01-概览.md) 已记录主/次通道能力对照表。

前置工程变更 `20260712145946-微信通道入队与进度对齐` 已交付：`wechatGroupEnqueueMode`（`mention_required` | `all`）、typing 4s 续期、`wxc_<clientId>` 出站 track。但用户侧仍易出现：

1. **群过滤不可控感**：启发式 @ 可能误判，用户不知何时该用 `all`、如何理解「该回没回 / 不该回回了」。
2. **进行中难感知**：长任务仅靠 typing，若续期或收尾异常，用户感到「突然没动静」或完成后仍显示处理中。
3. **能力差异不透明**：飞书与微信能做什么、不能做什么，未在设置或帮助中对用户可见说明。

本变更在**不要求微信与飞书 UI 形态完全一致**的前提下，对齐「可感知进度」「群过滤可控」「连发可控（一期仅说明边界，二期实现）」三类体验，使主次通道能力边界对用户透明。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 群聊误触发或漏触发 | 未 @ 仍入队，或已 @ 却被跳过；用户不理解规则 |
| 长任务「像卡死」 | typing 中途消失，长时间无其他反馈 |
| 结束后仍「在处理」 | 任务失败或已完成，typing 未停止 |
| 不知道微信能做什么 | 期望飞书式合并卡/菜单，微信侧无说明而产生落差 |
| 配置不知如何选 | 不清楚 `mention_required` 与 `all` 适用场景 |

## 三、目标与非目标

### 一期目标（必须达成）

1. **群过滤可控**：`wechatGroupEnqueueMode` 与行为符合产品文案；启发式 @ 局限与 `all` 模式适用场景对用户可理解；减少「该回没回 / 不该回回了」。
2. **进行中可感知**：长任务期间 typing 续期使用户能感到仍在处理；**失败或完成时必须停止 typing**。
3. **能力差异可见**：设置或帮助中展示飞书/微信主次通道能力对照（形态可不同，边界须透明）。

### 二期目标（后续，本期不强制）

1. 微信侧**合并连发**或等价「稍后一并回复」能力。
2. **菜单 / 快捷指令**在微信侧的触达（若协议与产品策略允许）。

### 非目标（明确不做）

- **不重写** iLink 协议或微信桥接协议层。
- **不强行**在微信侧实现 CardKit 或飞书卡片形态对等。
- **不改** Daemon 主调度内核、飞书主路径行为。
- **不在 propose 阶段**绑定实现类名、文件路径、内部接口签名（归属 `/kb-design`）。

## 四、用户与场景

### 用户

- **微信群协作者**：需要可预期的入队规则与误判时的补救路径（含 `all` 模式）。
- **微信私聊/群聊使用者**：长任务处理中需要持续「仍在处理」信号；结束或失败需要明确收尾。
- **多通道使用者**：需要理解飞书与微信能力差异，避免错误预期。
- **运维 / 配置者**：通过设置与帮助快速选对群模式并排查「没回复」类问题。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 默认 @ 过滤** | `mention_required` 下，未 @ 机器人不入队；文案说明启发式局限与日志关键字（如 `wechat_group_skip`）供排障。 |
| **S2 全量入队兼容** | `all` 模式下群消息全量入队；设置页说明适用场景（如小群、无稳定 @ 习惯）。 |
| **S3 长任务 typing** | 任务持续数分钟，typing 不中途长时间消失；用户能感知仍在处理。 |
| **S4 终态停 typing** | 任务成功完成、失败或取消后，typing **必须**停止，不得残留。 |
| **S5 能力对照可见** | 用户在设置或帮助入口可查阅飞书/微信能力差异（对照知识库 §九 口径，用户可读表述）。 |
| **S6 飞书不受影响** | 飞书合并卡、菜单、Get+CardKit 等主路径行为不被本变更破坏。 |

## 五、功能需求

### 5.1 一期

| 编号 | 需求描述 |
|------|----------|
| R1 | **群模式文案与行为一致**：`mention_required` / `all` 在设置中的名称、说明与真实入队行为一致。 |
| R2 | **启发式局限说明**：向用户说明微信群 @ 为正文启发式，可能误判；提供明确配置路径（含切换 `all`、可选展示名 `wechatBotDisplayName` 等已有能力的说明）。 |
| R3 | **typing 可感知**：长任务期间 typing 续期策略满足「用户能感到仍在处理」；具体阈值与形态在 design 阶段结合现网 4s 续期联调定稿。 |
| R4 | **终态停 typing**：完成、失败、取消等终态必须调用停止逻辑，不得残留 typing。 |
| R5 | **主次通道能力说明**：在设置和/或帮助中展示飞书（主）与微信（次）能力对照摘要（群过滤、进行中、track、合并/菜单等），与知识库对照表一致、用户可读。 |
| R6 | **不挡主路径**：飞书主通道体验与验收不受破坏。 |

## 六、验收标准

### 6.1 一期主路径

1. **群模式**：`mention_required` 与 `all` 行为与设置/帮助文案一致；用户能根据说明选择模式并理解启发式误判时的补救方式。
2. **typing 长任务**：实机或约定契约下，长任务（建议 ≥2 分钟）期间 typing 不长时间中途消失；用户可感知仍在处理。
3. **typing 终态**：任务完成或失败后 typing 停止，无残留「正在输入」。
4. **能力对照可见**：设置或帮助中可查阅飞书/微信能力差异说明，覆盖群过滤、进行中反馈、合并/菜单等关键项。
5. **飞书回归**：飞书主路径入队、合并、菜单、进度展示行为不退化。

### 6.2 边界

1. 不要求微信 UI 与飞书形态一致；不要求 CardKit、合并卡、菜单在一期落地。
2. 微信 track 仍为 `wxc_<clientId>` 等价语义，不假装等同飞书 `open_message_id`。
3. 二期 R7/R8 不纳入本期验收。

### 6.3 非功能

1. 变更代码含中文注释；单文件 ≤300 行（超限须拆分，属实现阶段约束）。
2. 产品说明与知识库主/次通道对照表保持一致，避免两套口径。

## 七、范围边界

### 在范围内（一期）

- 微信群模式相关设置/帮助文案与行为一致性校验。
- typing 长任务可感知性与终态停 typing 的体验达标（在既有续期能力上联调/补强）。
- 设置或帮助内的主次通道能力对照说明（用户可见）。
- 与前置变更交付能力的体验层验收与说明补全。

### 不在范围内（一期）

- iLink 协议重写；飞书 CardKit 移植。
- 微信合并连发、菜单/快捷指令（二期）。
- Daemon 调度内核改造；工作流微信专属节点。
