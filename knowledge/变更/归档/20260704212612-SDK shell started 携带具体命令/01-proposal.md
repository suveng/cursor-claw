## 背景与问题

cursor-claw 通过飞书、微信等即时通讯通道，让用户与 Cursor Agent 对话并获取运行反馈。当 Agent 需要执行系统命令时，用户会收到「命令开始执行」类的过程通知，帮助判断 Agent 正在做什么、是否在合理范围内操作。

近期已落地两项相关能力：

1. **群聊展示 shell 工具卡片应含命令**（`20260627212713-群聊仅展示Shell工具卡片`）：在卡片形态下，用户可看到 Agent 正在执行的具体命令，提升透明度与信任感。
2. **工具调用通知分级**（`20260704183752-SDK工具调用通知分级`）：命令执行（shell）属于应通知的高价值动手类工具，继续向用户推送过程信息；高频只读探查默认静默。

在上述能力叠加后，用户仍反馈：**命令「开始执行」阶段的通知信息量不足**。部分通道与呈现形态下，用户仅看到「shell 执行中」或「shell: started」等占位文案，**无法识别 Agent 实际在跑哪条命令**——例如是 `git status` 还是 `rm -rf`，透明度严重不足。

这与「群聊展示 shell 工具卡片应含命令」的产品预期不一致，也与用户对「命令执行过程应可审计、可理解」的普遍期望相悖。完成或失败阶段往往能看到更多上下文，但**started 作为用户最早感知「Agent 已动手」的节点，恰恰最缺关键信息**，在运维排查、群聊围观、私聊监督等场景下尤为突出。

## 目标与非目标

### 目标

1. **started 阶段可识别命令**：当 Agent 开始执行系统命令且向用户推送过程通知时，**started 阶段的用户可见文案须包含可识别的具体命令**（允许合理截断，但核心语义须可读）。
2. **完成态不退化**：命令执行完成（completed）或失败（failed）阶段的既有展示能力保持不变，不因本次优化而丢失命令、结果摘要或其他已具备的信息。
3. **多通道体验一致**：飞书私聊、群聊里程碑文本、卡片形态等不同呈现路径，在「started 须带命令」这一产品原则上保持一致；允许按通道能力在排版与截断策略上差异化，但不得出现「某通道有命令、某通道只有占位」的割裂体验。
4. **与工具分级协调**：仅对分级后仍应通知的命令执行类过程生效；已默认静默的只读探查类工具**不**因本次变更重新推送或改变静默策略。
5. **降级可预期**：当无法解析出具体命令时，须有明确、用户可理解的降级文案，避免空白或误导性占位。

### 非目标

- **不**改变 Agent 是否调用命令执行工具、调用频率或命令内容本身；本次仅优化**用户侧 started 过程通知的信息量**。
- **不**扩展至非命令执行类工具（如读文件、写文件、搜索等）的 started 文案改造；本次聚焦 **shell 命令开始执行** 这一场景。
- **不**扩展至 Claude Code SDK、Codex SDK、OpenCode SDK 等其他执行引擎的实现改造（可作为对比说明用户期望一致性，但不在本 PRD 承诺范围内）。
- **不**在本阶段定义具体实现方案、数据结构或模块划分（归属 `/kb-design`）。
- **不**为终端用户提供「自定义命令展示格式」的配置能力（可作为后续增强）。
- **不**改造 Electron 设置界面或通道凭据配置等桌面端 UI（除非后续单独立项）。

## 用户故事

### 飞书私聊用户

- 作为通过飞书私聊与 Agent 对话的用户，当 Agent 开始执行命令时，我希望**第一时间**在过程通知里看到具体命令（如 `npm test`），而不是只有「shell 执行中」，以便判断 Agent 是否在按预期操作。
- 作为关注安全与权限的用户，当 Agent 执行敏感或破坏性命令时，我希望 started 通知能让我**在命令跑完之前**就识别出风险，必要时及时中止或追问。

### 飞书群聊用户

- 作为在群聊中 @ Agent 的用户，当 Agent 开始执行命令时，我希望群聊过程里程碑或等价通知**与私聊、卡片形态一样能展示具体命令**，避免群成员只看到无意义的「shell: started」而无法判断 Agent 在做什么。
- 作为群聊中的其他成员，我希望过程通知简洁但信息充分，长命令可被合理截断，仍能看出核心意图，不刷屏也不空洞。

### 运维与排查场景

- 作为根据用户投诉排查「Agent 乱执行命令」的支持人员，我希望用户截图或转发的 started 通知**自带命令文本**，便于对照会话时间线还原当时 Agent 的实际操作，减少「用户说不清、支持猜不出」的沟通成本。
- 作为负责版本发布的管理员，我希望本次优化不增加消息条数、不破坏工具分级与过程时序等既有体验约束。

## 功能需求

### F1 started 须携带具体命令

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 当命令执行工具进入 **started（开始执行）** 阶段且按分级规则应向用户推送过程通知时，通知正文**必须包含**本次待执行的具体命令文本（与用户可理解的「命令行」语义一致）。 |
| F1.2 | 命令文本应嵌入 started 通知的主文案中，使用户无需点开二级详情或等待完成态，即可识别 Agent 正在执行什么。 |
| F1.3 | 同一次命令执行的 started 通知，在不同通道（私聊里程碑、群聊里程碑、卡片首屏等）上，**命令信息不得缺失**；呈现形式可按通道规范调整，但命令语义须一致。 |

### F2 命令过长时的截断与可读性

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 当命令文本超过通道或版式允许的展示长度时，须进行**合理截断**：保留命令开头或最能体现意图的核心片段，并以省略示意（如「…」）表明后续被截断。 |
| F2.2 | 截断后的文案仍须让用户能区分不同命令（例如能分辨是 `git` 类还是 `npm` 类操作），不得截到只剩无区分度的通用词。 |
| F2.3 | 截断策略须在 started、completed、failed 各阶段保持协调，避免 started 截断方式与完成态展示方式矛盾导致用户困惑。 |

### F3 无命令可解析时的降级文案

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 当系统无法从本次调用中解析出具体命令文本时（极端异常或数据缺失），started 通知**不得**仅显示「shell: started」「shell 执行中」等无信息占位。 |
| F3.2 | 降级文案须明确告知用户「命令执行已开始，但具体命令暂不可展示」，并可选附带简短原因类别（如「命令信息缺失」），避免用户误以为系统正常展示却故意隐瞒。 |
| F3.3 | 降级场景应极少发生；若频繁出现，应视为缺陷而非预期体验（归属验收与后续修复，本 PRD 定义产品预期为「绝大多数正常调用须展示命令」）。 |

### F4 与工具调用通知分级协调

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 本次优化**仅适用于**分级规则下仍应通知的命令执行（shell）类过程；已默认静默的只读探查类工具**不**推送 started 通知，行为与分级 PRD 一致。 |
| F4.2 | 不得因补充命令信息而将只读探查类工具重新纳入过程通知，避免刷屏回退。 |
| F4.3 | think、task 等其他过程通知类型不受本次变更影响，保持既有展示逻辑。 |

### F5 多通道体验一致原则

| 编号 | 需求描述 |
|------|----------|
| F5.1 | **里程碑文本路径**（如群聊等以简短过程文案呈现的通道）与 **卡片路径**（如私聊等以卡片呈现命令详情的通道），在 started 阶段均须满足 F1「携带具体命令」；不得出现卡片有命令、里程碑仅「shell: started」的体验割裂。 |
| F5.2 | 微信等其他 IM 通道若支持命令执行过程通知，遵循同一产品原则；若某通道暂不支持过程通知，不强行扩展，但已支持通道须对齐。 |
| F5.3 | 与「过程在上、结论在下」等既有呈现时序原则兼容：补充命令信息不改变过程消息相对助手答复的排序语义。 |

## 验收标准

以下条目须可测试、用户可感知，作为 `/kb-design` 与实现验收的输入：

1. **私聊 started 含命令**：在飞书私聊中触发 Agent 执行一条可识别命令（如 `echo hello`），用户收到的**开始执行**过程通知中须包含该命令（或截断后仍可识别的核心片段），不得仅为「shell 执行中」类占位。
2. **群聊里程碑 started 含命令**：在飞书群聊中触发同类命令执行，群聊过程里程碑（或非卡片形态的 started 文案）须同样展示具体命令，体验与「群聊 shell 卡片应含命令」的产品预期一致。
3. **长命令截断可读**：触发一条明显超长命令（如带多个参数的安装脚本），started 通知须截断展示且保留可区分意图的开头片段，不出现整段撑破版式或截断后完全不可读。
4. **完成/失败不退化**：同一次命令执行在完成或失败后，用户仍能获取与变更前相当或更优的命令与结果信息；不得出现 started 有命令而完成态反而丢失命令的倒退。
5. **只读工具仍静默**：触发多次只读探查（如读文件、搜索目录）且按分级规则应静默时，用户**不**收到这些工具的 started 通知；仅命令执行类 started 行为发生变化。
6. **降级文案可理解**：在模拟或构造「命令信息缺失」的异常场景下，started 通知须展示 F3 定义的业务降级文案，不得回退为无信息占位。
7. **多命令顺序可区分**：一次运行内连续执行多条不同命令时，各条 started 通知须能让用户区分不同命令，不得多条均显示相同无信息占位。

## 边界与例外

- **其他执行引擎**：若 Codex 等路径已在 started 阶段展示命令，可作为用户期望一致性的参考；本 PRD 验收范围以 **Cursor SDK** 经 IM 通道的呈现为准。
- **安全与敏感信息**：命令展示须遵循既有「用户可理解、不过度暴露内部实现」原则；本 PRD 不新增脱敏规则，但若既有策略对特定命令有脱敏要求，started 阶段须与完成态协调一致。
- **静默与抑制策略**：群聊对非 shell 工具的抑制、thinking 展示策略等既有规则保持不变，本次仅在 shell started 文案信息量上补强。
