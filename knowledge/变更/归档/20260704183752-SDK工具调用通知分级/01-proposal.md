# SDK 工具调用通知分级产品需求文档

> **来源**：kb-propose
> **类型**：体验优化
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无

## 背景与问题

cursor-claw 通过飞书、微信、群聊等即时通讯通道，以及任务面板等入口，让用户与 Cursor Agent 对话并执行自动化任务。运行期间，系统会向用户推送过程通知，帮助用户理解 Agent 正在做什么，而非长时间面对沉默等待。

近期已落地「SDK think 与 task 事件实时通知」能力：思考过程与子任务里程碑已能较早、稳定地呈现，用户对「Agent 在推理、在推进子步骤」的感知明显改善。但用户仍普遍反馈：**工具调用类过程通知过于频繁，严重刷屏**，干扰阅读助手正文与过程里程碑，反而降低可用性。

经归纳，当前痛点主要集中在：

1. **工具调用全量出站**：Agent 运行期间每一次工具调用（含大量只读探查）几乎都会转化为用户侧推送，消息密度远高于用户实际需要。
2. **高频低价值通知淹没高价值信号**：「正在读取文件」「正在搜索目录」等只读探查类提示反复出现，挤占 think、task、命令执行、写文件、删除、子 Agent 派发等更能体现「正在动手做事、分工协作」的过程信息，用户难以抓住重点。
3. **与既有过程增强的叠加效应**：think 与 task 实时性提升后，用户更能感知 Agent 在工作；与此同时 tool_call 仍全量推送，整体通知量进一步上升，体验从「沉默」转为「嘈杂」。

用户明确期望：**保留对理解执行进展有价值的过程通知，默认静默高频、低价值的只读探查类工具调用**，在「有过程感」与「不被刷屏」之间取得平衡。

## 目标与非目标

### 目标

1. **建立工具调用通知分级原则**：对用户可感知的出站过程通知，按工具行为价值区分「应通知」与「默认不通知」，减少无意义刷屏。
2. **保障关键动手信号可见**：思考（think）、子任务里程碑（task）、命令执行（shell）、写文件（write）、删除文件/资源、子 Agent 派发（启动子任务代理）等对用户理解「Agent 正在执行、产出结果、变更环境或分工协作」有价值的过程，继续稳定、及时地通知。
3. **默认静默高频只读探查**：用户明确点名的 read、glob 及同类高频只读探查（如文本搜索、语义搜索、列目录等），默认不向终端用户推送过程通知。
4. **与既有呈现协调**：与 think/task 实时通知、助手正文流式、处理中/完成/失败三态等机制配合，避免重复、冲突或时序混乱。
5. **多通道一致的产品原则**：飞书、微信、群聊等通道可按各自能力差异化呈现形式，但遵循同一套分级原则——该静默的静默、该通知的通知。

### 非目标

- 不扩展至 Claude Code SDK、Codex SDK、OpenCode SDK 等其他执行引擎；本次仅针对 **Cursor SDK** 运行路径。
- 不向终端用户暴露原始工具内部名称、参数细节或实现层级信息；过程展示仍遵循「用户可理解」的呈现策略。
- 不改造 Electron 设置界面、通道凭据配置等桌面端 UI（除非后续单独立项）。
- 不在本阶段为终端用户提供「按工具类型自定义通知开关」的配置能力（可作为后续增强，本 PRD 不承诺）。
- 不取消或削弱 think、task 的实时过程通知能力；本次是**在既有基础上对 tool_call 出站做减法与分级**，不是回退过程可见性。
- 不要求终端用户侧保留每一次工具调用的完整记录；完整记录归属见「边界与例外」中的开发者/运维场景。

## 用户故事

### 即时通讯用户

- 作为通过飞书与 Agent 对话的用户，当 Agent 需要多次读取文件、搜索代码库时，我不希望收到大量「正在读…」「正在搜索…」的重复提示，但仍希望看到「正在执行命令」「正在写入文件」「正在删除…」「正在启动子任务…」等说明 Agent 在动手改动、分工协作的信号。
- 作为在微信中与 Agent 交互的用户，我希望 think、子任务里程碑与关键写操作、命令执行、删除、子 Agent 派发的过程通知保留，让我知道 Agent 没卡住，又不会被探查类消息刷屏。
- 作为在群聊中 @ Agent 的用户，我希望过程通知遵循群聊既有策略（适度聚合、少打扰他人），且探查类工具默认不出现在群聊过程流中，避免刷屏影响他人阅读。

### 任务面板用户

- 作为通过任务面板触发 Agent 的用户，我希望任务执行期间的过程通知与 IM 通道遵循同一分级原则，不因入口不同而对只读探查全量推送。
- 作为查看任务进度的用户，我希望过程流中突出子任务推进与关键操作（含命令执行、写入、删除、子 Agent 派发），而非被大量探查步骤淹没。

### 运维与管理员

- 作为排查「通知太多」投诉的支持人员，我希望用户侧默认不再收到 read、glob 类过程推送，同时 shell、write、删除、子 Agent 派发仍可见，便于区分「Agent 在探查」与「Agent 在执行/写入/删除/分工协作」。
- 作为负责版本发布的管理员，我希望分级后整体出站消息量明显下降，长任务、多步任务场景下仍保持可接受的推送节奏，不触发通道限流风险上升。

## 功能需求

### F1 应通知的过程信息（高价值、默认出站）

| 编号 | 需求描述 |
|------|----------|
| F1.1 | **思考过程（think）**：Agent 进入推理、规划阶段时，继续按既有产品策略及时呈现可理解的思考类提示；本次分级不得削弱 think 的可见性与实时性。 |
| F1.2 | **子任务里程碑（task）**：子任务启动、进行中、完成等用户可理解的状态变化，继续及时推送里程碑提示；本次分级不得削弱 task 的可见性与实时性。 |
| F1.3 | **命令执行（shell）**：当 Agent 执行终端命令、运行脚本等等价「在环境中动手执行」的操作时，用户侧**必须**收到可理解的过程通知（如「正在执行命令…」及适度摘要），使用户感知 Agent 正在对环境产生作用。 |
| F1.4 | **写文件（write）**：当 Agent 创建或修改文件、写入内容等等价「产出或变更产物」的操作时，用户侧**必须**收到可理解的过程通知（如「正在写入…」及适度摘要），使用户感知 Agent 正在产生可交付结果。 |
| F1.5 | **删除文件/资源（delete）**：当 Agent 删除文件、资源或等价「移除产物、清理环境」的操作时，用户侧**必须**收到可理解的过程通知（如「正在删除…」及适度摘要），使用户感知 Agent 正在对环境产生不可逆或高影响变更。 |
| F1.6 | **子 Agent 派发（启动子任务代理）**：当 Agent 启动子任务代理、委派独立子 Agent 执行专项工作时，用户侧**必须**收到可理解的过程通知（如「正在启动子任务…」及适度摘要），使用户感知 Agent 正在分工协作、推进并行或专项子步骤。 |
| F1.7 | 上述过程通知的文案与呈现须符合既有通道策略，用户无需了解内部工具分类即可理解 Agent 在做什么。 |

### F2 默认不通知的过程信息（高频只读探查、默认静默）

| 编号 | 需求描述 |
|------|----------|
| F2.1 | **读取文件（read）**：Agent 为理解上下文而读取单个或多个文件时，**默认不向终端用户推送**过程通知；用户明确点名须默认静默。 |
| F2.2 | **目录/模式匹配探查（glob）**：Agent 为定位资源而列举、匹配文件路径时，**默认不向终端用户推送**过程通知；用户明确点名须默认静默。 |
| F2.3 | **同类高频只读探查**：与 read、glob 性质相同、以获取信息为目的且通常高频发生的只读操作（如全文搜索、语义搜索、列目录、读取配置片段等），遵循同一产品原则——**默认静默**，不在用户侧过程流中逐条呈现。 |
| F2.4 | 默认静默仅指出站面向终端用户的过程推送；不改变 Agent 实际执行能力，也不表示 Agent 未执行这些步骤。 |
| F2.5 | 若某次只读探查在特定场景下具有极高用户可感知价值（罕见），是否例外通知由设计阶段分级表与产品原则约束，**不得**以恢复 read/glob 全量推送作为默认方案。 |

### F3 其他工具的分级与灰度边界

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 除 F1、F2 已明确者外，其余工具类型（如网络请求、专用领域工具、外部集成调用等）须在**设计阶段**给出完整分级表：标注「默认通知 / 默认静默 / 按场景」及判定依据。 |
| F3.2 | 分级表须可追溯至本产品原则：对用户理解「动手执行、产出结果、子任务推进、环境变更、分工协作」有价值的倾向通知；对「反复探查、收集信息」的倾向静默。 |
| F3.3 | 灰度发布策略、按通道差异化节流、同类通知聚合等细节在设计阶段细化；PRD 层约束为：**read/glob 必须默认静默，shell/write/delete/子 Agent 派发必须通知**，其余以设计分级表为准。 |

### F4 与 think/task 实时通知、正文流式及三态的协调

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 工具调用分级不得导致 think、task 通知明显延迟、丢失或被错误抑制；过程流的优先级为：用户可理解的思考与子任务信号 > 关键动手类 tool 通知 > 静默探查类。 |
| F4.2 | 助手正文流式输出与过程通知的时序关系保持清晰：分级后用户仍应在合理时间内看到首包过程反馈（think 或等价提示），短任务不因减少 tool 通知而回退为长时间沉默。 |
| F4.3 | 与「处理中 / 完成 / 失败」三态、停止操作、失败提示等既有机制配合：分级不改变终态语义，不引入「已完成却仍大量过程推送」或「处理中却完全无过程信号」的矛盾体验。 |
| F4.4 | 飞书、微信、群聊等通道在卡片、文本、里程碑等呈现形式上可不同，但**分级判定一致**：同一运行事件在任通道上不应出现「A 通道静默、B 通道刷屏」的原则性分裂（除非群聊另有既定的更严格聚合策略，且仍遵守 F2 默认静默）。 |

## 边界与例外

### 开发者与运维侧完整记录

- 面向**开发者、运维或支持人员**的调试视图、运行日志、任务详情页（若产品已提供或后续提供）**可保留完整工具调用记录**，包括默认静默的 read、glob 等，便于排障与审计。
- 该完整记录**不作为**向普通终端用户 IM 过程流默认推送的内容；终端用户侧以分级后的过程通知为准。

### 范围与一致性

- 本次分级仅作用于 **Cursor SDK** 运行路径下的用户侧过程出站，与上一变更「SDK think 与 task 事件实时通知」范围一致。
- 历史任务、归档会话的展示策略若与实时运行不同，须在实现时明确是否回溯应用分级；默认对**新产生的运行**应用本分级原则。

### 异常与失败

- shell、write、delete、子 Agent 派发类操作若失败，用户仍应通过既有失败提示、助手正文或三态机制得知，不得因「过程通知分级」而丢失错误可见性。
- 长时间仅含只读探查、无 F1 类通知的运行，用户仍应能通过 think、task 或处理中状态感知 Agent 在工作，避免误以为系统无响应。

## 验收标准

1. **read / glob 默认静默**：在典型多步任务（含多次读文件、多次目录匹配）中，终端用户 IM 过程流**不出现**针对 read、glob 的逐条过程推送（或等价「正在读取…」「正在 glob…」类用户可见提示）。
2. **shell / write / delete / 子 Agent 派发必须通知**：Agent 执行命令、写入或修改文件、删除文件/资源、启动子任务代理时，终端用户在合理时延内**能收到**可理解的对应过程通知，且通知语义能区分「执行命令」「写入文件」「删除」与「启动子任务」。
3. **think / task 不回归**：思考过程与子任务里程碑的及时性与既有「SDK think 与 task 事件实时通知」验收水平一致，不因本次分级而明显变差。
4. **刷屏显著缓解**：与变更前同一类任务相比，用户侧过程通知条数明显下降，用户主观反馈「通知过多、干扰阅读」类问题缓解；高价值信号（think、task、shell、write、delete、子 Agent 派发）仍清晰可见。
5. **多通道原则一致**：飞书私聊、微信、群聊（在各自既有呈现策略下）对 read/glob 均默认静默，对 shell/write/delete/子 Agent 派发均保持通知；不出现通道间原则性相反行为。
6. **与正文流式、三态协调**：短任务首包过程反馈不明显退化；运行结束后的完成/失败三态与助手正文时序正常，无新增重复或冲突提示。
7. **设计阶段交付物**：`02-design` 须包含完整工具分级表及 read/glob/shell/write/delete/子 Agent 派发的判定说明，本 PRD 的 F1–F4 均可追溯覆盖。
