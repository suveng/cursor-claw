# 微信通道入队与进度对齐产品需求文档

> **变更 ID**：`20260712145946-微信通道入队与进度对齐`
> **来源**：kb-propose
> **类型**：功能
> **优先级**：P3
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无
> **依赖**：不挡飞书主路径；宜在控制面/队列稳态（HTTP dispatch 失败重入队对齐、消息队列模块拆分）之后再做

## 一、背景与问题陈述

微信是产品的**次通道**：飞书主路径在群聊 @ 过滤、进度/表情与消息跟踪上已较完整，微信侧体验明显落后。

当前次通道痛点：

- **群聊噪声入队**：群消息无 @ 过滤，非面向机器人的闲聊也会入队，浪费 Agent 配额并制造误触发。
- **进度与表情弱**：无 Get/DONE 等表情反馈；进行中主要依赖 typing，时效与可感知性待联调，与飞书进度体验不对齐。
- **消息无法 track**：出站 `send-text` 无 message_id（或等价标识），无法像飞书路径那样跟踪消息会话状态。

本变更专责把微信入队门槛与进度/跟踪能力，在**微信协议能力边界内**尽量向飞书主路径对齐，但不追求飞书功能全集。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 群聊误触发 | 群内未 @ 机器人的消息仍被当作任务入队并消耗配额 |
| 无进度反馈 | 处理中几乎感觉不到「正在处理」，或 typing 很快消失、难以感知 |
| 无法对齐飞书状态 | 缺少 Get/DONE 等表情或等价状态，与飞书主路径体验落差大 |
| 消息难跟踪 | 出站消息无法关联会话/进度状态，排障与状态对齐困难 |

## 三、目标与非目标

### 目标（必须达成）

1. **群聊 @ 过滤（或可配置）**：非 @ 机器人的群消息默认不入队；允许配置开关（若产品需要兼容「全量入队」历史行为）。
2. **进度可感知**：在微信能力边界内提供进行中/完成或等价状态反馈，尽量对齐飞书「用户能感知进度」的体验（不必形态一致）。
3. **发送可 track**：出站发送具备 message_id 或等价跟踪能力；若协议/能力不可行，须在产品/运维说明中写清**不可行边界**，不得静默假装可 track。
4. **不挡主路径**：飞书主路径行为与验收不受本变更破坏。

### 非目标（明确不做）

- **不做**飞书功能全集移植（卡片、菜单、合并预览、CardKit 等不在本变更范围）。
- **不改** Daemon 主调度策略本体（入队门槛与通道侧进度/track 对齐，不重做调度内核）。
- **不做**工作流微信专属节点。
- **不在 propose 阶段**绑定实现类名、文件路径、内部接口签名（归属 `/kb-design`）。

## 四、用户与场景

### 用户

- **微信群协作者**：期望只有 @ 到机器人（或明确开启全量入队）才触发 Agent，避免闲聊误触发。
- **私聊使用者**：期望处理中有可感知进度，完成后有明确结束感（表情或等价）。
- **排障 / 运维**：期望出站消息可跟踪，或明确知道微信侧不可 track 的边界。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 群聊默认过滤** | 群内未 @ 机器人的消息默认不入队；@ 后正常入队处理。 |
| **S2 可配置全量入队** | 若保留兼容开关：开启后行为可回到「群消息全量入队」；默认应为过滤。 |
| **S3 进度可感知** | 任务进行中用户能感知「处理中」；结束时有完成/停止感（表情或等价，受协议能力约束）。 |
| **S4 发送可 track** | 出站消息有 message_id 或等价；不可行时文档说明边界，产品侧不假装可跟踪。 |
| **S5 飞书主路径不受影响** | 本变更上线后，飞书 @ 过滤、进度/表情与 track 行为保持既有验收。 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | 微信群聊：非 @ 机器人消息默认可过滤、不入队。 |
| R2 | 过滤策略可配置（若需要兼容历史「全量入队」）；默认策略为过滤。 |
| R3 | 进度/完成反馈在微信能力边界内尽量对齐飞书「可感知」目标；无 Get/DONE 时须有等价方案或明确降级说明。 |
| R4 | 出站发送具备 track 能力（message_id 或等价），或文档写清不可行边界。 |
| R5 | typing 等时效相关行为须可联调验证，避免「闪一下就没了」且无说明。 |
| R6 | 不挡飞书主路径；不做飞书全集、不改 Daemon 主调度、不做工作流微信专属节点。 |

## 六、验收标准

### 6.1 主路径

1. **非 @ 默认可过滤**：微信群内未 @ 机器人的消息默认不入队；@ 后可正常入队。
2. **进度可感知**：进行中用户能感知处理状态；结束有明确停止/完成感（形态可不同于飞书）。
3. **track 或边界说明**：具备 message_id/等价 track，**或**产品/运维文档明确写清不可行边界（二选一须落地，不得静默缺失）。

### 6.2 边界

1. 飞书主路径既有入队、进度、表情、track 行为不被本变更破坏。
2. 不引入工作流微信专属节点；不要求飞书卡片/菜单/合并预览等能力在微信侧对等实现。
3. 若协议无法提供 message_id：验收以「文档说明不可行边界」为准，而非强行伪造 track。

### 6.3 非功能

1. 减少群聊噪声导致的 Agent 配额浪费。
2. 次通道体验与飞书主路径的落差可解释、可预期（能力边界透明）。
3. 工程规范：变更代码含中文注释；单文件不超过 300 行（超限须拆分，属实现阶段约束）。

## 七、范围边界

### 在范围内

- 微信群聊 @ 过滤（及可选配置）。
- 进度/表情或等价状态，在微信能力边界内对齐「可感知」。
- 出站 send 的 track 能力，或不可行边界的文档说明。
- typing 时效相关的可联调与可感知验收。

### 不在范围内

- 飞书功能全集移植。
- Daemon 主调度内核改造。
- 工作流微信专属节点。
- 控制面 HTTP 化、队列拆分本身（属依赖变更，本变更消费其稳态后再做）。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 协议能力上限 | 无 Get/DONE、send 无 message_id 等可能无法与飞书形态一致 | 验收允许「等价方案」或「文档说明不可行边界」 |
| typing 时效 | typing 可能短时消失，联调前难定体验 | 验收强调可感知；联调结论写入设计/知识库 |
| 依赖队列/控制面稳态 | HTTP dispatch 与队列拆分未稳时改入队门槛易 interleave | 依赖写入头部；建议其后实施 |
| 历史全量入队习惯 | 部分群可能依赖「无 @ 也入队」 | 默过滤 + 可配置兼容 |
| 飞书回归 | 改共享入队/进度路径可能误伤主通道 | 验收强制飞书主路径不受影响 |
