# 渲染端与 Daemon 目录语义对齐产品需求文档

> **变更 ID**：`20260702120154-渲染端与Daemon目录语义对齐`
> **来源**：kb-propose
> **类型**：refactor / 工程结构
> **优先级**：P1（工程可维护性）
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景

cursor-claw 的 `src/` 目录同时承载独立 Daemon 守护进程、消息桥接（飞书 / 微信 / 文件队列）、工作流引擎、以及 Electron 渲染端界面等能力。知识库已按业务域（**消息桥接**、**工作流**、**Agent 调度**）与工程平台（**Daemon 守护进程**、**Electron 桌面应用 / 渲染端**）建立编号子模块与源码锚点表；各 README 维护「关键源码」或「源码入口」路径，供排查与 onboarding 使用。

当前 `src/` 约 54 个文件，**根目录扁平堆叠** Daemon 入口、编排路由、队列、工作流、微信管理等模块（如 `daemon.ts`、`daemon-entry.ts`、`file-queue.ts`、`wechat-manager.ts`、`workflow-*.ts`、`server-*.ts`、`builtin-workflows.ts`、`daemon-scheduled-tasks.ts` 等），另有 `shared/`、`wechat/`、`renderer/` 子目录。目录语义与知识库分区**不对齐**。带来的问题包括：

1. **定位困难**：维护者难以按「消息桥接 / 工作流 / Daemon 服务 / 渲染端」快速进入对应源码，排查 IM 入队、编排 dispatch、工作流 MCP 等问题时依赖记忆或全文搜索。
2. **映射脱节**：知识库「源码锚点」「关键源码」表与真实目录不一致（如消息桥接、工作流、Daemon 入口分散在根目录），文档导航价值下降。
3. **边界模糊**：`src/AGENTS.md` 目前主要为 Daemon 编排与 Presentation 约定（篇幅较长），缺少根索引与分层 `AGENTS.md`，不利于区分 Daemon 维护者与渲染端维护者的阅读入口。
4. **与主进程变更割裂**：平行变更 `20260702112559-Electron主进程目录语义对齐` 已完成 `electron/` 语义子目录重组（stage=reviewed），其非目标明确**不改动 `src/renderer/`**；`src/` 其余部分仍待对齐，形成「主进程已分区、Daemon 与渲染端仍扁平」的不一致体验。

本变更为**纯工程结构**调整，不涉及用户可见界面或产品行为变更；旨在使 `src/` 目录树与知识库语义一致，并与已完成的 `electron/` 平行变更形成对称的工程可维护性提升。

## 二、目标

1. **语义对齐**：将 `src/` 源码按子目录组织，与知识库 **消息桥接**、**工作流**、**Agent 调度**（Daemon 侧编排）、**Daemon 守护进程**、**Electron 渲染端** 等分区语义一致；子目录命名采用英文（与 TypeScript 工程惯例一致），含义对应知识库中文子模块。
2. **入口保留**：`daemon-entry.ts` 等 Daemon 打包构建入口继续保留在 `src/` 根目录（类比 `electron/main.ts` 保留策略），不因目录重组而迁移打包配置所依赖的入口路径。
3. **AGENTS 分层**：`src/AGENTS.md` 升级为根索引并链到各语义子目录 `AGENTS.md`；将现有 Daemon 编排约定下沉至对应子目录文档，避免单文件过长、职责混杂。
4. **文档同步**：更新知识库中与 `src/` 相关的源码锚点表，至少覆盖：
   - `knowledge/业务域/消息桥接/00-README.md`
   - `knowledge/业务域/工作流/00-README.md`
   - `knowledge/业务域/Agent调度/00-README.md`（Daemon 侧 orchestrator / dispatch 锚点）
   - `knowledge/工程平台/Daemon守护进程/00-README.md` 及相关子模块
   - `knowledge/工程平台/Electron桌面应用/03-渲染端界面.md` 所引用的渲染端路径（若存在硬编码路径）
5. **行为不变**：重组后 Daemon HTTP API、与 Electron 的协作契约、IM / 工作流 / 渲染端功能与变更前一致；用户无感知。

## 三、非目标

- **不改动** `electron/` 主进程目录（由平行变更 `20260702112559` 已处理）。
- **不改变** Daemon HTTP API 路径与语义、与 Electron 之间的 IPC / 转发契约、Daemon 监听端口与进程模型行为。
- **不合并或拆分** 业务逻辑（除为满足既有「单文件 ≤300 行」规范而已存在的拆分延续外，本变更不做额外逻辑重构）。
- **不处理** 超大文件行数治理（如数千行的 `daemon.ts`）；此类治理另开变更，本变更仅做目录迁移与 import 路径更新。
- **不改动** 构建脚本的核心打包策略（除因 import 路径变化而必须调整的引用外）。

## 四、用户故事

### 4.1 Daemon 维护者

作为维护 Daemon 守护进程与消息桥接的开发者，我希望按「飞书 / 微信 / 队列与路由 / HTTP 服务 / 编排调度」等业务语义进入对应子目录，以便快速定位源码、减少在扁平根目录中误改无关模块。

### 4.2 知识库读者

作为阅读消息桥接、工作流或 Daemon 工程平台文档的维护者，我希望知识库「源码锚点」「关键源码」表中的路径与仓库实际目录一一对应，以便从文档直达代码，无需在根目录文件名中猜测模块归属。

### 4.3 Code Review 参与者

作为审查 `src/` 改动的协作者，我希望目录结构本身表达模块边界（消息桥接 vs 工作流 vs Daemon 平台 vs 渲染端），以便在 PR 中一眼识别改动所属业务域，并与已重组的 `electron/` 形成一致的 review 心智模型。

## 五、范围说明

**在范围内**

- `src/` 目录重组：将根目录扁平 TS 文件及既有子目录（`shared/`、`wechat/`、`renderer/` 等）迁移或归并至语义化子目录（`renderer/` 在 PRD 层保持与「渲染端界面」文档一致，细节在 design 阶段定稿）。
- 全仓 import 路径更新（含 `electron/` 对 `src/` 的引用、`scripts/` 打包配置、`resources/` 模板引用等），确保构建与类型检查通过。
- `src/AGENTS.md` 及子目录 `AGENTS.md` 分层维护。
- 上述知识库 README / 子模块文档中的 `src/` 源码锚点表更新。

**不在范围内**

- `electron/` 主进程目录与逻辑（平行变更已覆盖）。
- 功能行为、HTTP API 契约、配置格式、用户界面交互变更。
- 超大文件拆分与行数治理（另开变更）。
- 独立 npm 包拆分或 Daemon 与渲染端工程物理分离。

## 六、预期成果（目录草案）

以下为与知识库语义对齐的**预期目录形态**（英文目录名；细节与文件—目录对照表在 design 阶段落盘）：

```
src/
├── daemon-entry.ts              # Daemon 打包入口，保留根目录
├── AGENTS.md                    # 根索引，链到子目录 AGENTS.md
├── bridge/                      # 业务域：消息桥接（飞书 / 微信 / 队列 / 路由）
│   ├── wechat/                  # 微信通道（自既有 wechat/ 归位或保留）
│   └── …                        # 飞书核心、通道类型、队列、微信管理、入站路由等
├── workflow/                    # 业务域：工作流（引擎 / 存储 / MCP / 内置模板）
├── daemon/                      # 工程平台：Daemon（HTTP/MCP 服务、编排调度、定时任务、进程主逻辑）
├── renderer/                    # 工程平台：Electron 渲染端（与 03-渲染端界面 一致）
│   ├── components/
│   ├── pages/
│   └── …
└── shared/                      # 跨模块共享能力（类型、常量、解析、展示门控等）
                                 # 归属原则：仅放被 ≥2 个语义子目录引用的代码；
                                 # 单域专属逻辑不得长期滞留 shared/
```

**shared/ 归属原则（产品层）**

- 跨消息桥接与工作流共用的类型 / 解析 / 常量可保留在 `shared/`。
- 仅被单一业务域使用的模块应迁入对应子目录，避免 `shared/` 成为「第二扁平根目录」。
- 渲染端专属工具与组件保留在 `renderer/` 内，不上浮至 `shared/`（除非确有跨端复用且 design 阶段登记）。

验收时以 design 文档中的**对照表**为权威依据，本处仅表达产品层「结构应与知识库分区一致」的预期。

## 七、验收标准

1. **目录树一致**：`src/` 实际目录树与 design 阶段「文件—目录对照表」一致，无遗漏、无未登记文件仍滞留根目录（`daemon-entry.ts`、`AGENTS.md` 等 design 登记的入口文件除外）。
2. **构建通过**：`npm run build` 及 Daemon 打包路径（如 `scripts/bundle-daemon.cjs` 所依赖流程）完整通过，无编译或打包错误。
3. **无旧路径残留**：全仓不存在指向已迁移旧路径的 import（可通过全文检索验收，零命中或仅 design / 变更文档中的历史说明）。
4. **知识库同步**：第五节所列知识库文档中的 `src/` 源码锚点 / 关键源码表已更新，路径与新目录一致。
5. **AGENTS 分层**：`src/AGENTS.md` 为根索引，各语义子目录具备对应 `AGENTS.md` 且链接正确；Daemon 编排细约定下沉至子目录，根索引仅保留导航与全局约束。
6. **行为回归**：现有 IM 入队与出站、合并批次、编排 dispatch、工作流 MCP、渲染端 Dashboard / Settings、Daemon 启动与 HTTP API 相关手动冒烟路径行为与变更前一致；无新增运行时错误或跨进程通信失败。
7. **与 electron 平行变更协调**：不破坏 `20260702112559-Electron主进程目录语义对齐` 已落盘的 `electron/` 目录与知识库同步；若工作区存在未合并冲突，须在 rebase 后再执行 `src/` 迁移；`electron/` 对 `src/` 的引用须一并更新。

## 八、风险与依赖

- **风险（并行变更）**：`electron/` 平行变更可能仍在合并或 archive 阶段；本变更实现前须确认其 stage 或完成 rebase，避免 `electron/` 与 `src/` 两侧同时大规模 `git mv` 导致冲突难以解。
- **风险（import 全仓更新）**：`daemon.ts` 等枢纽文件被 `electron/`、`scripts/`、测试与知识库多处引用；遗漏任一引用将导致构建或运行时失败。实现前须在 design 阶段梳理依赖图与迁移顺序。
- **风险（超大文件）**：`daemon.ts` 等文件远超 300 行规范上限；本变更**仅迁移路径**（或在 design 阶段按子模块切分文件但**不改变行为**），不做业务逻辑重构；行数治理依赖后续独立变更。
- **依赖（design/plan）**：实现前须在 design 阶段产出完整文件—目录对照表、`shared/` 归属判定与迁移顺序，避免循环依赖或遗漏。
- **依赖（迁移方式）**：目录迁移须使用版本控制保留历史的移动方式（如 `git mv`），便于 review 与回滚。
- **用户可见性**：无直接 UI 变更；changelog 与版本号 bump 可在 archive 阶段按团队规范决定是否记录（纯内部工程结构）。
