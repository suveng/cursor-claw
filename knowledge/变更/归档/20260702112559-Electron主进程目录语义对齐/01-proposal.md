# Electron 主进程目录语义对齐产品需求文档

> **变更 ID**：`20260702112559-Electron主进程目录语义对齐`
> **来源**：kb-propose
> **类型**：refactor / 工程结构
> **优先级**：P1（工程可维护性）
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景

cursor-claw 的 Electron 主进程承载桌面应用生命周期、多会话 Agent 调度、四引擎 SDK 执行、MCP 管理、工作流与 Daemon 桥接等核心能力。知识库已按业务域（Agent 调度、工作流）与工程平台（Electron 桌面应用、Daemon 守护进程）建立编号子模块与阅读路径；`knowledge/业务域/Agent调度/00-README.md` 亦维护「关键源码」对照表，供排查与 onboarding 使用。

当前 `electron/` 目录约 80 余个 TypeScript 文件**扁平堆放在根目录**，文件名前缀混杂（如 agent-sdk、sdk-run、agent-cc、agent-codex、agent-opencode、mcp、context、session 等），与知识库子模块语义**不对齐**。带来的问题包括：

1. **定位困难**：开发者难以按业务域或工程平台分区快速找到相关源码，排查 IM、SDK、MCP、定时任务等问题时依赖记忆或全文搜索。
2. **映射脱节**：知识库「关键源码」表与真实目录结构不一致，文档导航价值下降，新人 onboarding 成本偏高。
3. **边界模糊**：扁平目录不利于形成模块边界认知，跨引擎共享能力与单引擎专属逻辑混在同一层级，增加误改与 review 负担。

本变更为**纯工程结构**调整，不涉及用户可见界面或产品行为变更；旨在使主进程目录树与知识库语义一致，提升长期可维护性。

## 二、目标

1. **语义对齐**：将 `electron/` 主进程源码按子目录组织，与知识库 **Agent 调度**、**Electron 桌面应用**、**Daemon 守护进程**、**工作流** 等分区语义一致；子目录命名采用英文（与 TypeScript 工程惯例一致），含义对应知识库中文子模块。
2. **入口保留**：`main.ts`、`preload.ts` 继续保留在 `electron/` 根目录，作为构建与打包入口，不因目录重组而迁移。
3. **文档同步**：`electron/AGENTS.md` 升级为根索引并链到各子目录 `AGENTS.md`；`knowledge/业务域/Agent调度/00-README.md`「关键源码」表更新为与新目录一致。
4. **行为不变**：重组后应用功能、IPC 契约、对外 API 与变更前一致；用户无感知。

## 三、非目标

- **不改动** `src/renderer/` 渲染端目录结构。
- **不改动** 独立 Daemon 包目录（若存在与主进程分离的 daemon 工程）。
- **不改变** 公共 API 命名、IPC 通道契约或对外导出符号。
- **不合并或拆分** 业务逻辑（除为满足既有「单文件 ≤300 行」规范而已存在的拆分延续外，本变更不做额外逻辑重构）。
- **不处理** 超大文件行数治理（如数千行的管理类文件）；此类治理另开变更，本变更仅做目录迁移与 import 路径更新。
- **不并入** 以下正交进行中变更的主题与 manifest：`Cursor SDK 本地配置来源对齐`、`CursorSDK执行引擎事件流消费`；实现阶段须与上述变更协调，避免破坏其未提交逻辑。

## 四、用户故事

### 4.1 主进程开发者

作为维护 Electron 主进程的开发者，我希望按「会话调度 / Cursor SDK / MCP / 配置与更新」等业务语义进入对应子目录，以便快速定位源码、减少误改无关模块。

### 4.2 知识库读者

作为阅读 Agent 调度或 Electron 工程平台文档的维护者，我希望知识库「关键源码」表中的路径与仓库实际目录一一对应，以便从文档直达代码，无需在扁平列表中猜测文件名前缀含义。

### 4.3 Code Review 参与者

作为审查主进程改动的协作者，我希望目录结构本身表达模块边界，以便在 PR 中一眼识别改动所属业务域，降低跨域耦合的 review 成本。

## 五、范围说明

**在范围内**

- `electron/` 主进程目录重组：将现有扁平 TS 文件迁移至语义化子目录。
- 全仓 import 路径更新，确保构建与类型检查通过。
- `electron/AGENTS.md` 及子目录 `AGENTS.md` 分层维护。
- `knowledge/业务域/Agent调度/00-README.md`「关键源码」表更新。

**不在范围内**

- 渲染端、Daemon 独立包、构建脚本行为变更（除因 import 路径变化而必须调整的引用外）。
- 功能行为、IPC 契约、配置格式、用户界面变更。
- 超大文件拆分与行数治理（另开变更）。

## 六、预期成果（目录草案）

以下为与知识库语义对齐的**预期目录形态**（英文目录名；细节与文件—目录对照表在 design 阶段落盘）：

```
electron/
├── main.ts, preload.ts          # 构建入口，保留根目录
├── AGENTS.md                    # 根索引，链到子目录 AGENTS.md
├── app/                         # 工程平台：窗口/托盘/日志
├── config/                      # 工程平台：配置与更新
├── daemon/                      # 工程平台：Daemon 桥接
├── session/                     # Agent调度：多会话/调度/MCP 展示
├── scheduling/                  # Agent调度：定时任务 + 远程指令
├── agent/
│   ├── shared/                  # 跨引擎：launcher、guard、crash-archive 等
│   ├── cursor-sdk/              # 06-CursorSDK
│   ├── claude-code/             # 07-ClaudeCodeSDK
│   ├── codex/                   # 08-CodexSDK
│   └── opencode/                # 09-OpenCodeSDK
├── mcp/                         # MCP 管理（跨引擎）
└── workflow/                    # 工作流域
```

验收时以 design 文档中的**对照表**为权威依据，本处仅表达产品层「结构应与知识库分区一致」的预期。

## 七、验收标准

1. **目录树一致**：`electron/` 实际目录树与 design 阶段「文件—目录对照表」一致，无遗漏、无未登记文件仍滞留根目录（`main.ts`、`preload.ts`、`AGENTS.md` 除外）。
2. **构建通过**：`npm run build` 完整通过，无编译或打包错误。
3. **无旧路径残留**：全仓不存在指向已迁移旧路径的 import（可通过全文检索验收，零命中或仅 design 文档中的历史说明）。
4. **知识库同步**：`knowledge/业务域/Agent调度/00-README.md`「关键源码」表已更新，路径与新目录一致。
5. **AGENTS 分层**：`electron/AGENTS.md` 为根索引，各语义子目录具备对应 `AGENTS.md` 且链接正确。
6. **行为回归**：现有 IM、任务、工作流、四引擎 SDK、MCP、Daemon 相关手动冒烟路径行为与变更前一致；无新增运行时错误或 IPC 失败。
7. **正交变更协调**：不破坏进行中 `Cursor SDK 本地配置来源对齐`、`CursorSDK执行引擎事件流消费` 相关文件的既有逻辑；若与其工作区冲突，须在合并或 rebase 后再执行迁移。

## 八、风险与依赖

- **风险（并行变更）**：另两个进行中 SDK 相关变更可能同时修改 `electron/` 下文件；本变更实现前须确认其 stage 或完成 rebase，避免 `git mv` 与逻辑改动交织导致冲突难以解。
- **风险（超大文件）**：部分文件远超 300 行规范上限；本变更**仅迁移路径**，不做拆分；行数治理依赖后续独立变更。
- **依赖（design/plan）**：实现前须在 design 阶段用依赖分析工具梳理 import 关系，产出完整对照表与迁移顺序，避免循环依赖或遗漏。
- **依赖（迁移方式）**：目录迁移须使用版本控制保留历史的移动方式（如 `git mv`），便于 review 与回滚。
- **用户可见性**：无直接 UI 变更；changelog 与版本号 bump 可在 archive 阶段按团队规范决定是否记录（纯内部工程结构）。
