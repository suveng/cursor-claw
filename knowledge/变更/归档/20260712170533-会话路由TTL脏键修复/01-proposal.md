> **优先级**：P0
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无
> **依赖**：`20260712113356-Agent标识跨重启持久化`（跨重启持久化已落地，本变更为其运行期 TTL 语义纠偏）

## 一、背景与问题陈述

**Agent 标识跨重启持久化**已落地：Daemon 在会话映射变更时会将路由快照写盘，并在冷启动时加载、按 TTL 清理过期条目，使用户在 Daemon 重启后仍能续聊同一会话与工作区。

然而当前写盘行为存在**语义偏差**：每次持久化快照时，会把**所有在册会话**的「最后触达时间」统一刷新为同一时刻，而非仅更新本轮真正发生触达或映射变更的会话。

由此带来的运维与产品侧影响：

1. **空闲会话被误续命**：同进程内只要有任一活跃会话触发写盘，长期无消息的空闲会话也会被写入「刚刚触达」的时间戳，运行期 TTL 清理会推迟判定其过期。
2. **磁盘与路由表膨胀风险**：本应已超 TTL 的映射条目可能长期滞留，路由表与持久化文件体积缓慢膨胀，与「仅活跃会话应续期」的产品预期不符。
3. **冷启动与运行期行为不一致**：重启加载后的 prune 仍按磁盘上记录的时间正确清理；但运行中 6 小时级（或既定 TTL）清理可能明显滞后，运维难以用单一口径解释「为何某会话仍未被清掉」。
4. **与持久化设计意图背离**：跨重启持久化的初衷是「映射变更时落盘、按真实活跃度过期」；全量刷新触达时间使 TTL 退化为「最后一次任意会话写盘时间」，削弱清理机制可信度。

本变更为**技术债修复（P0）**：在**不改变 TTL 时长、路由键格式与工作流 sessionKey** 前提下，使写盘时的触达时间更新与「仅真正被触达/变更的条目才续期」语义一致，并保证冷启动 load+prune 不退化。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 空闲会话长期残留 | 用户或运维观察到某 chat 长期无消息，但会话路由映射仍未被清理，路由表条目偏多 |
| TTL 清理滞后 | 运行期 prune 未在预期空闲窗口后剔除映射；重启 Daemon 后同类条目反而被正确清掉 |
| 磁盘占用缓增 | 持久化路由文件随在册会话数缓慢增大，旧映射因误续期难以及时回收 |
| 运维口径分裂 | 「运行中应过期」与「重启后已清理」现象并存，排障时需额外解释写盘刷新行为 |

## 三、目标与非目标

### 目标（必须达成）

1. **触达时间精准更新**：只有本轮真正被触达或映射发生变更的会话条目，才更新其最后触达时间；未参与本轮变更的条目保持原有时间戳。
2. **运行期 TTL 可信**：运行期 prune 依据真实最后活跃度判定过期，空闲超过 TTL 的会话仍能在进程存活期间被剔除，不被其他会话的写盘「连带续命」。
3. **冷启动行为不退化**：Daemon 冷启动后的加载与 prune 结果与现状一致或更准确（不误删活跃映射、不遗漏应清理条目）。
4. **持久化语义一致**：写盘行为与「映射变更时更新」的产品语义对齐，运维可预期「无活动即按 TTL 过期」。

### 非目标（明确不做）

- **不改** TTL 时长、过期窗口或清理周期配置。
- **不改** 会话路由键格式、路由文件版本或字段命名契约（除非设计阶段发现必须的最小兼容调整，须单独说明）。
- **不改** 工作流 `sessionKey` 生成与存储统一方案（属独立变更范围）。
- **不做** 全量会话库、IM 协议或用户可见卡片/文案改造。
- **不在 propose 阶段** 绑定具体模块名、函数名或写盘实现细节（归属 `/kb-design`）。

## 四、用户与场景

### 用户

- **飞书 / 微信终端用户（间接）**：长期不用某 chat 时，期望旧 Agent 绑定不会无限期占用资源；续聊活跃会话时行为与现网一致。
- **运维 / 开发者**：需要运行期与冷启动对 TTL 判定口径一致，便于解释「何时清理、为何清理」；关注路由表规模与磁盘占用可控。
- **工程协作者**：在 Agent 标识持久化已落地基础上，修复脏键续期问题，避免后续功能在错误 TTL 语义上叠加。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 单会话活跃写盘** | 仅会话 A 有消息触达并写盘；会话 B、C 长期空闲。写盘后 B、C 的最后触达时间应保持写盘前原值。 |
| **S2 运行期 TTL 清理** | 会话 B 空闲时间已超过既定 TTL，且期间仅有其他会话触发写盘；运行期 prune 仍应剔除 B，不得因他人写盘而续命。 |
| **S3 冷启动 load+prune** | Daemon 重启后加载持久化文件并 prune；行为与现状一致或更准确，不误删活跃映射、不遗漏应过期条目。 |
| **S4 映射变更续期** | 会话 A 发生映射变更（如工作区切换、新 Agent 绑定）并写盘；仅 A 的触达时间更新，其余条目不变。 |
| **S5 多会话交错活跃** | 多 chat 轮流有消息；各会话触达时间仅在其自身活跃时更新，互不污染。 |
| **S6 运维可预期性** | 运维可依据「最后真实触达 + TTL」解释映射何时过期，无需区分「运行中」与「重启后」两套隐性规则。 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | **增量触达更新**：写盘快照时，仅对本轮被触达或映射变更的会话条目刷新最后触达时间。 |
| R2 | **未变更条目保真**：未参与本轮变更的条目，触达时间与写盘前内存/磁盘状态一致，不得批量覆盖为同一时刻。 |
| R3 | **运行期 prune 有效**：空闲超过 TTL 的会话在进程存活期间仍能被运行期清理剔除，不因其他会话写盘而延迟过期。 |
| R4 | **冷启动不退化**：加载持久化文件后的 prune 结果与现状一致或更准确；活跃映射不被误删。 |
| R5 | **契约不变**：TTL 时长、路由键格式、工作流 sessionKey 口径保持现状。 |
| R6 | **可观测保留**：清理、写盘、加载失败等既有运维可检索信号不退化（具体关键字由设计阶段对照现网）。 |

## 六、验收标准

### 6.1 主路径（产品/运维可感知）

1. **空闲不被连带续期**：仅活跃会话触发写盘时，其他空闲会话的最后触达时间不变（对照写盘前后或等价观测手段）。
2. **运行期过期仍成立**：空闲超过 TTL 的会话，在仅有其他会话写盘的情况下，仍能在运行期 prune 中被剔除。
3. **冷启动一致或更准**：Daemon 冷启动 load+prune 与现状一致或更准确；不误删当前活跃映射。

### 6.2 边界与回归

1. 映射发生变更的会话，其触达时间应正确更新为变更时刻（或等价语义）。
2. 多会话交错活跃时，各会话触达时间独立更新，互不影响。
3. 不引入 TTL 时长、路由键、sessionKey 的无意变更。

### 6.3 非功能

1. 变更代码含中文注释（与项目规范一致）。
2. 不扩大持久化写盘频率或引入与 TTL 修复无关的策略变更。

## 七、范围边界

### 在范围内

- 会话路由持久化写盘时「最后触达时间」的更新语义纠偏。
- 运行期 TTL prune 与写盘语义对齐的回归验证。
- 冷启动 load+prune 行为不退化的验证。
- 归档阶段同步 Daemon 会话路由相关工程平台知识（若 TTL/写盘语义描述失真）。

### 不在范围内

- TTL 时长、清理周期、路由文件 schema 版本升级（无必要则不碰）。
- 路由键格式、工作流 sessionKey 统一或双写清偿。
- IM 通道、合并卡、用户可见文案改造。
- 全量会话库或跨进程会话状态新产品能力。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 上游持久化已归档 | 本修复建立在 `Agent标识跨重启持久化` 行为之上 | 对照其验收口径，明确本变更为语义纠偏而非重做持久化 |
| 触达判定边界 | 「触达」与「仅映射字段变更」的边界若定义不清，可能漏更新或仍误刷 | 设计阶段列出触达/变更事件清单，与 01 验收逐条映射 |
| 运行期与冷启动双路径 | load、runtime prune、写盘三条路径须语义一致 | 验收覆盖 S1～S3；设计阶段标注状态机 |
| 并行变更 | Daemon 批二拆分等可能触及邻近模块 | 设计阶段标注文件白名单，必要时串行合并 |
| 历史脏数据 | 已写入磁盘的统一时间戳无法回溯真实触达 | 修复后 forward 行为正确；是否在加载时纠偏历史脏键由设计阶段评估 |
