## 背景与问题

cursor-claw 通过飞书、微信等即时通讯通道，让用户与 Cursor Agent 对话并获取运行反馈。近期已依次落地三项体验增强：

1. **展示时序编排**（`20260627210352-飞书Presentation展示时序编排`）：确立「过程在上、结论在下」的产品心智，含工具调用的单轮任务中，过程类信息应整体位于助手最终回答之上。
2. **think 与 task 实时通知**（`20260704174846-SDK think与task事件实时通知`）：思考过程与子任务里程碑可较早、稳定地转化为用户可感知的过程通知。
3. **工具调用通知分级**（`20260704183752-SDK工具调用通知分级`）：高价值动手类工具（如命令执行、写文件、删除、子 Agent 派发）继续通知，高频只读探查（如 read、glob）默认静默，减轻刷屏。

在上述能力叠加后，用户仍普遍反馈：**最终答复往往在会话中率先出现并持续流式更新，而 think、task、关键工具等过程通知反而出现在其后**。阅读时像「Agent 已经完整回复了，思考与执行才发生在后面」，与「过程在上、结论在下」的心智相悖，也削弱了过程通知带来的透明度与信任感。

经归纳，当前缺口并非「缺少过程通知」，而是 **IM 通道上多条出站消息的呈现顺序与流式首包时机未与真实发生顺序对齐**：用户既要保留最终答复的流式增长体验，又要求过程序列按时间先后、在结论之前完整可见，且整体呈现符合逻辑、美观可读。

## 目标与非目标

### 目标

1. **时序正确性**：在 IM 通道上，think、task、关键工具过程通知等应用户可见的过程消息，按实际发生顺序呈现，且**整体位于助手最终答复的首条可见内容之前**（或与之协调的等价呈现，见功能需求 F1）。
2. **保留流式体验**：助手最终答复仍支持流式更新与单条消息内持续增长；用户无需为纠正顺序而牺牲「边看边长」的流畅感。
3. **多过程事件有序**：一次运行内多个 think 更新、子任务里程碑、关键工具通知依次出现时，会话中的阅读顺序稳定、可预期，不颠倒、不穿插错乱。
4. **与工具分级协调**：仅对「应通知」的过程信息参与时序编排；已分级为默认静默的只读探查不出站，不因本变更重新全量推送或破坏分级原则。
5. **通道差异可接受**：飞书里程碑文本、CardKit 卡片等不同呈现形态可按通道能力差异化，但**同一产品原则**——过程先于结论、顺序符合直觉——须一致成立。
6. **短任务不退化**：纯对话、无实质过程的单轮短问答，首条可见反馈时延不得因「等待过程序列」而明显变差。
7. **与三态协调**：过程通知与「处理中 / 完成 / 失败」宏观状态、停止与失败提示语义不冲突，结束时用户能清晰感知任务已收尾。

### 非目标

- **不**改变 Agent 内部的推理顺序、工具调用顺序或模型行为；本次仅优化**用户侧 IM 出站消息的呈现时序与流式首包时机**。
- **不**扩展至 Claude Code SDK、Codex SDK、OpenCode SDK 等其他执行引擎；本次针对 **Cursor SDK** 经 IM 通道的呈现路径。
- **不**在本阶段定义具体模块、接口、数据结构或实现方案（归属 `/kb-design`）。
- **不**为终端用户提供「自定义消息排序策略」的配置能力（可作为后续增强）。
- **不**回退 think/task 实时性与工具分级成果；本次是在既有过程可见性基础上的**顺序与流式协调**优化。
- **不**改造 Electron 设置界面或通道凭据配置等桌面端 UI（除非后续单独立项）。

## 用户故事

### 即时通讯用户

- 作为通过飞书私聊与 Agent 对话的用户，当 Agent 先思考、再执行命令、最后给出完整回答时，我希望自上而下依次看到思考提示、命令执行提示，**最后**才看到流式增长的最终答复，而不是答复先顶在上方、过程消息堆在下方。
- 作为在微信中与 Agent 交互的用户，我希望最终答复仍能边生成边更新，但该答复**首次出现在会话中的时机**不得早于应展示的过程序列，避免「结论先行、过程补票」的违和感。
- 作为触发含子任务与写文件操作的长任务用户，我希望各里程碑与关键操作通知按发生顺序排列在最终答复之上，滚动阅读时逻辑连贯、美观自然。

### 任务面板与多入口用户

- 作为通过任务面板触发 Agent 的用户，我希望 IM 关联消息或等价出站呈现的时序原则与私聊一致，不因入口不同而出现「过程在后、结论在前」的颠倒。

### 运维与管理员

- 作为排查「消息顺序错乱」投诉的支持人员，我希望用户侧会话时间轴与 Agent 实际推进阶段一致，便于区分呈现问题与执行卡顿。
- 作为负责版本发布的管理员，我希望顺序优化不显著增加消息条数或触发通道限流，短问答场景首包体验不退化。

## 功能需求

### F1 过程先于结论的时序正确性

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 当一次运行内存在应用户可见的过程通知（think、task 里程碑、分级后仍出站的关键工具过程等）且最终将产出助手答复时，这些过程消息的**会话呈现顺序**须与其实际发生顺序一致，且**整体位于**助手最终答复的**首条用户可见呈现**之前。 |
| F1.2 | 「首条用户可见呈现」指用户第一次在所用通道看到该次运行的助手答复内容（含流式首包、首段 PATCH 或等价形态），不得因流式策略而早于应展示的过程序列抢先占位。 |
| F1.3 | 若运行期间仅有过程通知、尚无实质答复内容，过程消息按发生顺序正常呈现；答复首包到达后，答复须落在已有过程序列之下（或通道支持的等价「过程在上」布局），不得插入过程序列中间造成阅读错乱。 |
| F1.4 | 纯对话、无应出站过程通知的运行，不受「等待过程」策略影响，答复可按既有流式路径及时首包呈现（见 F5）。 |

### F2 最终答复流式体验保留

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 助手最终答复仍须支持流式更新：用户可在单条（或通道约定的等价）消息内看到内容持续增长，体验与变更前「有流式」场景相比不劣化。 |
| F2.2 | 含应出站过程序列的运行：assistant **首条 IM 出站**（首建 CardKit 或等价流式消息）须在**本次 Run 过程全部结束之后**才发生（见 F8）；首建后仍须以流式 PATCH 持续增长至 final，**不是**一次性下发完整长文。禁止的是「无流式的一次性全文」与「过程未结束即 mid-run 首建/更新 assistant IM」，**不是**禁止在 Run 收尾首建后流式更新。无实质过程场景按 F5 及时首包，不受本条延迟约束。 |
| F2.3 | 流式更新过程中，已呈现的过程消息位置应保持稳定，不应因答复流式增长而被顶到不合理位置或反复跳动，保证阅读美观。 |
| F2.4 | 答复流式结束时，用户应能在一目了然的位置看到完整结论，且其上方过程序列完整、顺序正确。 |

### F3 多过程事件的有序呈现

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 一次运行内连续的 think 更新、多个 task 里程碑、多个关键工具过程通知，须按**发生先后顺序**在会话中排列，不得后发生的过程出现在先发生的过程之上。 |
| F3.2 | 短时间内的同类过程更新（如思考阶段延续）可按既有策略合并或更新呈现，但**不得**破坏整体时间轴：用户仍能感知「先发生了什么、后发生了什么」。 |
| F3.3 | 子任务串行或并行时，里程碑通知顺序须可读：用户能分辨推进阶段，又不过度刷屏；顺序错乱视为缺陷。 |
| F3.4 | 过程通知条数应继续受工具分级与既有抑制策略约束，本变更**不**以增加消息数量为代价换取顺序。 |

### F4 与工具调用通知分级的协调

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 参与时序编排的过程消息范围与工具分级一致：think、task、shell、write、delete、子 Agent 派发等**应通知**类过程纳入顺序规则；read、glob 等**默认静默**类过程不参与出站，也不因本变更被重新推送。 |
| F4.2 | 当运行仅含静默类探查、无应出站过程时，答复流式首包时机按 F5 短任务规则处理，不因「无过程可排」而引入不合理延迟。 |
| F4.3 | 含关键工具过程的任务中，该工具的过程通知须出现在对应答复内容之前，且与 think、task 通知按实际发生顺序交错排列，不得整体被答复流式抢先。 |

### F5 短任务与无过程场景不退化

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 典型单轮短问答（无实质 think/task/关键工具过程通知或过程极短可省略）从用户发消息到首条可见助手内容的时延，与变更前同场景相比**无明显劣化**。 |
| F5.2 | 不得为一律满足「过程在上」而对所有运行强制引入可感知等待；仅当存在应出站且尚未完整呈现的过程序列时，才协调答复首包时机。 |
| F5.3 | 极短运行可按既有策略省略部分过程通知，但须同时满足顺序原则（若有过程则仍在结论之上）与首包不退化。 |

### F6 通道差异与呈现形态

| 编号 | 需求描述 |
|------|----------|
| F6.1 | 飞书等通道若对 tool/thinking 采用里程碑文本、对 assistant 采用 CardKit 流式卡片等不同形态，各形态仍须服从「过程在上、结论在下」的**会话级顺序**，不得因形态不同而颠倒时间轴。 |
| F6.2 | 微信、群聊等通道按既有能力与策略呈现，但**顺序原则**与私聊一致；呈现形式可降级，不得因降级而将结论整体置于过程之上。 |
| F6.3 | 群聊场景须兼顾不打扰他人：在遵循群聊抑制与聚合规则的前提下，触发者侧的过程—结论顺序仍须正确。 |
| F6.4 | 通道异常、发送失败时的重试与丢失策略与既有消息投递一致，不单独引入不可恢复的乱序状态。 |

### F7 与处理中三态、停止、失败的协调

| 编号 | 需求描述 |
|------|----------|
| F7.1 | 过程通知与「处理中 / 完成 / 失败」三态并存时，用户能区分「仍在运行」与「已结束」；顺序优化不得使结束态早于结论或过程呈现矛盾。 |
| F7.2 | 用户主动停止运行时，进行中的过程与流式答复应停止更新，结束反馈尽快呈现，且会话内已展示的过程—结论相对位置保持合理。 |
| F7.3 | 运行失败时，失败提示按既有策略优先呈现；过程序列可作为辅助上下文，但不得掩盖失败原因或造成「失败后结论仍流式顶置」的错觉。 |
| F7.4 | 运行正常结束时，最后可见的助手答复（含流式完结态）位于应展示的过程序列之下，用户滚到底即可读到完整结论。 |

### F8 过程实时、答复收尾流式（Rev2）

| 编号 | 需求描述 |
|------|----------|
| F8.1 | **过程（thinking / task / notify 级工具）**：继续**实时**推送到飞书（里程碑或等价过程通知），不因本 Rev 削弱 think/task 实时性与工具分级原则（F4）。 |
| F8.2 | **assistant 答复（含工具 Run）**：在**本次 Run 过程尚未全部结束前**，**不得**向飞书发送任何 assistant IM 内容——禁止 mid-run `release`、禁止 non-final `stream-text` 首建或更新；Run 期间仅允许在本地/Electron 侧累积 buffer。 |
| F8.3 | **Run 收尾**：`streamRunEvents` 结束、过程全部完成后，**才**首建飞书 CardKit（或等价流式消息），并以流式 PATCH 持续增长至 `final`；单 Run **仅一条** assistant IM 消息，杜绝相同文案重复出站。 |
| F8.4 | **无实质过程短问答（F5）**：仍允许 preamble 短窗或无过程时及时首包，不强制等到 Run 末尾才出字。 |
| F8.5 | **与 F2 关系**：「最后才发送」指**首条 IM 出站时机**在过程结束之后；首建后仍须流式更新，**不是**一次性长文。 |

## 边界与例外

1. **仅过程、无答复**：若运行结束时尚未产出助手答复（如仅执行操作、失败提前终止），以过程通知与三态/失败提示为准，不适用「结论在下」但须保证过程顺序正确。
2. **通道限流**：外部平台限流时可降级或聚合，限流解除或运行结束后用户仍须能获知最终结果与宏观状态，且尽量不遗留永久乱序。
3. **合并批次与连发消息**：用户连发、合并预览等场景须不回归既有 reply 锚定与排队行为；时序规则在合并场景下仍尽量成立，细节在设计阶段与 NF 协同项对齐。
4. **隐私与敏感内容**：过程或答复若含不宜展示的内容，按既有策略摘要或抑制，但仍须满足最低可见性与顺序原则（在可见范围内正确排序）。
5. **非 Cursor SDK 路径**：其他引擎或通道不在本次范围；混用场景下仅 Cursor SDK 经 IM 的呈现路径享受本次优化。

## 验收标准

1. **含关键工具的过程在结论之上**：在 Cursor SDK 路径、IM 通道上，模拟「思考 → 关键工具过程（如命令执行或写文件）→ 助手答复」的运行，用户会话中**自上而下**应先看到思考类提示、再看到关键工具过程通知，**最后**才看到助手答复的首条可见内容；答复可流式增长，但其首包不得早于上述过程序列的首次呈现。
2. **多过程事件顺序正确**：模拟含至少 2 次 task 里程碑与 1 次以上关键工具过程的运行，各过程通知在会话中的先后顺序与发生顺序一致，无「后发生的出现在上方」案例。
3. **结论仍流式**：上述场景中，助手答复须在用户可见后支持流式更新（内容持续增长），主观体验不低于变更前有流式的同类型任务；不得变为全程无流式、仅在末尾一次性出现完整长文（除非该任务本身无流式产出）。
4. **工具分级不破坏**：同场景下 read、glob 类只读探查仍默认不出站过程通知；不应为修顺序而恢复全量 tool 刷屏。
5. **短问答首包不退化**：对典型单轮短问答（无实质过程通知），从用户发消息到首条可见助手内容的时延与变更前相比无明显劣化，无新增「长时间完全空白」或「无故等待过程」案例。
6. **纯对话不劣化**：无工具、无子任务的轻量问答，流式首包仍应在合理时间内可见，不因本变更强制延迟。
7. **三态与结束协调**：运行结束、停止、失败场景下，用户能明确感知任务已收尾；不出现「处理中仍显示但结论已完整顶置」或「失败后结论流式覆盖失败提示」的矛盾呈现。
8. **飞书私聊抽检**：主用户飞书私聊 SDK 路径至少 2 个场景（含工具长任务 + 短问答各 1）通过上述 1～7 项；微信/群聊若已配置各至少 1 个场景验证顺序原则成立或合理降级。
9. **阅读美观**：过程序列与流式结论并存时，滚动阅读无频繁跳动、过程被答复顶到会话最上方等明显违和布局（允许通道形态差异，但不允许逻辑颠倒）。
10. **含工具 Run 过程结束前无 assistant IM 出站**（Rev2 / F8）：在含 thinking、task 或 notify 级工具过程的运行中，从首个过程通知呈现至 Run 过程全部结束之前，飞书会话**不得**出现 assistant 答复的首建或 PATCH 更新；assistant 首条 IM 仅出现在 Run 收尾之后，且首建后须流式增长（F8.2/F8.3）。
11. **单 Run 单条 assistant、无重复文案**（Rev2 / F8.3）：同一 Run 在飞书侧仅 **1 条** assistant 消息；不得出现内容完全相同的 assistant 答复重复发送（与 08-verify-issue E10 对齐）。
