## 背景与问题

cursor-claw 通过飞书等即时通讯通道，让用户与 Cursor Agent 对话并执行自动化任务。运行期间，系统会向用户推送过程通知，帮助用户理解 Agent 正在做什么，而非长时间面对沉默等待。

近期已陆续落地多项过程通知能力：思考与子任务里程碑可较早出站；工具调用按价值分级，命令执行、写文件、删除、子 Agent 派发等关键操作保留通知；飞书等通道在部分场景下对工具类过程通知采用更轻量的文本里程碑呈现，以控制刷屏与平台能力差异。

在上述能力基础上，用户仍反馈：**两类「开始执行」态的飞书过程通知信息不足**，难以判断 Agent 具体在做什么：

1. **命令执行开始**：当 Agent 开始执行一条 shell 命令时，飞书用户常见到仅含「命令工具已开始」一类泛化文案，**看不出即将执行的具体命令内容**。部分呈现路径虽能展示命令摘要，但在飞书统一采用文本里程碑降级时，开始态文案往往退化为「工具名 + 状态」，缺少可读的命令说明。
2. **子任务开始**：当 Agent 启动子任务或子步骤时，飞书用户常见到「子任务进行中…」等兜底文案，**看不出该子任务的具体目的或步骤描述**。运行事件侧通常带有可理解的描述信息，但开始态通知未充分转化为用户可读的具体说明。

此外，思考（think）类过程在飞书侧若继续推送，易与正文、子任务里程碑叠加造成噪音；用户期望 **飞书通道不再单独推送思考过程通知**，把可见性留给更有步骤感的开始态与关键操作信号。

本次变更聚焦：**在 Cursor SDK 运行路径上，补强飞书通道「开始态」过程通知的可理解性**（命令执行携带命令摘要、子任务开始携带描述），并与既有分级、里程碑、消息顺序等能力协调；同时收敛飞书侧思考过程推送。

**关联背景**：即时通讯消息顺序与流式推送优化（`20260704190748`，已归档 v1.13.4）中 assistant 流式、task/tool 过程顺序等目标仍有效；本变更**取代**其中「飞书 thinking 须继续实时里程碑」条款，与其余 ordering 目标协调验收。

## 目标与非目标

### 目标

1. **命令执行开始态可读**：Agent 开始执行 shell 命令时，飞书用户应在开始态过程通知中看到**可理解的命令摘要**，而非仅「某工具已开始」的泛化提示。
2. **子任务开始态可读**：Agent 启动子任务或等价步骤时，飞书用户应在开始态过程通知中看到**该子任务的具体描述或目的说明**，而非仅「子任务进行中」等兜底文案。
3. **与既有分级原则一致**：补强开始态文案不得破坏工具调用通知分级——只读探查类工具仍默认静默；本次仅针对已纳入通知白名单且用户需感知的操作（含命令执行、子任务派发等）的开始态呈现。
4. **通道与降级一致**：飞书在文本里程碑、卡片抑制降级等不同呈现路径下，开始态信息应**同等可理解**；不因呈现形式切换而丢失命令或子任务描述。
5. **收敛飞书思考推送**：飞书通道不再向用户单独推送思考过程通知，降低与正文、子任务、关键工具通知的叠加噪音；其他通道按既有产品策略处理，不在本 PRD 强制统一。
6. **桌面端思考可观测性保留**：飞书静默思考过程不得删除或削弱桌面 SDK 运行界面中的思考日志可见性。
7. **与消息时序协调**：开始态通知的增强不得破坏用户已感知的消息顺序与流式阅读体验；thinking 不再参与飞书出站后，assistant 与 task/tool 过程的「过程在上、结论在下」仍须可验收。

### 非目标

- 不扩展至 Claude Code SDK、Codex SDK、OpenCode SDK 等其他执行引擎；本次仅针对 **Cursor SDK** 运行路径。
- 不向终端用户暴露原始事件类型名、内部错误堆栈、完整敏感参数或实现层级细节；命令与描述展示须遵循既有「用户可理解 + 安全摘要」策略。
- 不改造 Electron 设置界面、飞书凭据配置等桌面端 UI（除非后续单独立项）。
- 不在本阶段为终端用户提供「按工具/子任务自定义开始态文案格式」的配置能力。
- 不追求对命令执行、子任务的**完成态、失败态**做全面改版；但须保证完成/失败阶段**不退化**（见 F1.6、验收 9）。
- 不替代助手正文流式输出；过程通知仍是补充可见性，不是用过程提示代替最终回答。

## 用户故事

### 飞书私聊用户

- 作为通过飞书与 Agent 对话的用户，当 Agent 开始执行一条 shell 命令时，我希望在开始通知里看到**正在执行什么命令**（或可读摘要），而不是只看到「shell 已开始」而无法判断是在装依赖还是在跑测试。
- 作为等待多步子任务完成的用户，当 Agent 启动一个新的子步骤时，我希望看到**这一步在做什么**（如「正在检查终端状态」「正在搜索相关代码」），而不是笼统的「子任务进行中」。
- 作为长任务用户，我希望飞书不再频繁弹出「正在思考」类提示，让我能更专注地阅读子任务与关键操作的开始态说明和助手正文。

### 群聊与多通道用户

- 作为在群聊中 @ Agent 的用户，我希望开始态通知在遵循群聊既有抑制策略的前提下，仍能让**触发者**看清命令或子任务描述摘要，便于判断 Agent 是否在执行预期操作。
- 作为同时使用微信等其他通道的用户，我理解飞书侧对思考推送的收敛可能与其他通道策略不同；但命令与子任务开始态「带描述」的产品原则应在各通道尽量一致（呈现形式可按平台能力差异）。

### 运维与管理员

- 作为排查「用户不知道 Agent 在跑什么命令」投诉的支持人员，我希望飞书开始态通知已包含足够摘要，便于区分误操作、长耗时命令与正常推进。
- 作为负责版本发布的管理员，我希望开始态文案补强不会显著增加消息长度触发限流，且不会对只读探查类工具重新打开全量通知。

## 功能需求

### F1 命令执行（shell）开始态携带命令摘要

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 当 Cursor SDK 运行中 Agent **开始执行**一条 shell 命令且该操作属于应向用户通知的过程时，飞书侧开始态过程通知须包含**可读的命令摘要**，使用户能判断正在执行何种操作。 |
| F1.2 | 命令摘要应简洁、单行或短段可读；过长命令、含敏感信息的命令须按既有产品策略截断、脱敏或替换为安全摘要，但不得退化为仅「命令工具已开始」而无任何实质说明。 |
| F1.3 | 飞书在文本里程碑呈现路径下，开始态须与「能展示命令摘要」的其他呈现路径**信息等价**；不得因呈现降级而仅保留「工具名 + 开始」的泛化文案。 |
| F1.4 | 同一条命令的开始态通知应在合理时延内发出（通常与命令实际启动同步，数秒内可感知），不得明显滞后到命令已结束才出现开始提示。 |
| F1.5 | 当无法解析出具体命令文本时，started 通知不得仅显示「shell: started」等无信息占位，须使用明确降级文案（如「命令执行已开始，但具体命令暂不可展示」）。 |
| F1.6 | 命令执行完成或失败阶段的既有展示能力不得因本次 started 补强而退化；不得出现 started 有命令摘要而完成态反而丢失命令信息的倒退。 |

### F2 子任务（task）开始态携带描述

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 当 Cursor SDK 运行中 Agent **启动**子任务、子代理或等价任务单元且该里程碑属于应向用户通知的过程时，飞书侧开始态过程通知须包含**该子任务的可理解描述或目的说明**（来源于运行过程提供的描述或等价用户向信息）。 |
| F2.2 | 若描述过长，须摘要为短句仍保留核心意图；若描述缺失，应使用不低于当前体验的业务兜底（如步骤序号 + 简短动作说明），**不得**长期固定为无信息量的「子任务进行中…」一类文案。 |
| F2.3 | 多个子任务连续启动时，每条开始态通知应能区分不同步骤（描述或序号可读），用户能分辨当前展开的是哪一步。 |
| F2.4 | 子任务开始态与后续进行中、完成类里程碑在语义上衔接自然，开始态描述不为后续状态重复刷屏。 |

### F3 与既有分级、里程碑、消息顺序协调

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 开始态补强须遵守工具调用通知分级：只读探查类工具默认仍不推送；仅对已通知白名单内的操作（含命令执行、子任务派发等）增强开始态文案。 |
| F3.2 | 与 think、task、工具调用、助手正文、处理中/完成/失败三态等既有过程信号协调，避免同一语义在短时间内重复推送多条开始态消息。 |
| F3.3 | 与即时通讯消息顺序、流式推送等并行优化方向一致：开始态通知插入位置与更新节奏应符合用户阅读顺序直觉，不得造成「先看到完成、后看到开始」等明显错乱（在平台能力允许范围内）。 |
| F3.4 | 用户主动停止或运行失败时，进行中的开始态相关展示应停止更新，并与结束反馈一致。 |

### F4 飞书通道呈现与降级一致

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 飞书私聊、群聊（在触发者可见范围内）均适用开始态携带描述的原则；群聊仍遵循既有抑制与聚合规则，但**不得**因群聊策略把开始态完全削成无信息泛化句。 |
| F4.2 | 当飞书对工具类过程通知采用文本里程碑而非富卡片时，开始态仍须满足 F1、F2 的可读性要求。 |
| F4.3 | 发送失败、限流或平台约束导致降级时，应优先保留命令或子任务描述的**核心摘要**；完全无法展示时，行为与既有消息投递与重试策略一致。 |
| F4.4 | 开始态文案长度与频率须控制在可接受范围，避免单条消息过长或连续多条超长摘要影响阅读。 |

### F5 飞书通道收敛思考（think）过程推送

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 飞书通道**不再**向用户单独推送思考（think）类过程通知；思考阶段可见性由助手正文、子任务里程碑、关键工具开始态等其它信号承担。 |
| F5.2 | 收敛思考推送不得导致飞书用户在运行开始后长时间完全无任何可见反馈；在正文尚未产出时，仍应能通过处理中态、子任务或关键操作开始态等既有机制感知 Agent 在工作。 |
| F5.3 | 其他即时通讯通道是否推送思考过程，维持既有产品策略，本变更不强制与飞书完全一致。 |
| F5.4 | thinking 不再飞书出站后，参与 ordering 编排的飞书过程序列仅含 task、notify 级工具等仍出站的过程；无 task/tool 的短问答不因已不存在的 thinking 飞书占位而引入不合理延迟。 |

## 边界与例外

1. **极短命令或极短子步骤**：若命令或子任务在极短时间内结束，开始态可与完成态按策略合并呈现，但用户仍应能获知「执行了什么」而非仅看到结束句。
2. **描述或命令不可用**：当运行过程未提供可用描述、或命令内容不宜展示时，采用安全兜底摘要，并满足 F1.2、F2.2 的最低可读性要求。
3. **隐私与安全**：含密钥、令牌、个人隐私的命令或描述须脱敏；不得因「携带描述」而泄露敏感信息。
4. **通道限流**：平台限流时可缩短摘要或延迟非关键开始态，但须在运行结束或限流解除后保证用户仍能获知宏观结果与关键步骤。
5. **与其他引擎并存**：非 Cursor SDK 路径不在本次范围。

## 验收标准

1. **shell 开始态带命令摘要（飞书私聊）**：模拟 Agent 开始执行一条可读的 shell 命令（如安装依赖、运行测试脚本），飞书用户在开始态过程通知中应能看到**明确指向该命令的摘要**，而非仅「shell 已开始」或等价无信息文案；抽检至少 3 条不同命令。
2. **shell 开始态在文本里程碑路径一致**：在飞书对工具类通知走文本里程碑呈现的场景下，上述开始态仍须包含命令摘要，与能展示摘要的其他呈现方式**信息等价**（允许措辞差异，不允许摘要缺失）。
3. **task 开始态带描述（飞书私聊）**：模拟含至少 2 个可区分描述的子任务启动的运行，飞书用户应能在各子任务**开始态**通知中看到对应描述或可读目的说明，而非长期固定为「子任务进行中…」等兜底句。
4. **分级不被破坏**：对 read、glob 等默认静默的只读探查类工具，飞书侧仍**不应**因本次变更而出现开始态过程通知；对 shell、task（子 Agent 派发）等白名单操作，开始态增强正常生效。
5. **飞书不再推送 think**：在 Cursor SDK 路径上触发含思考阶段的运行，飞书用户**不应**再收到独立的思考过程通知；同时运行开始后 10 秒内仍应有处理中态、正文首包、子任务或关键操作开始态等**至少一种**可见反馈，不得出现完全沉默空白。
6. **长命令与长描述**：对超过展示长度阈值的命令或子任务描述，飞书开始态应呈现截断/摘要后的可读文本，且核心意图可辨认；敏感内容按策略脱敏。
7. **群聊抽检（若已配置）**：群聊中 @ Agent 触发含 shell 开始与子任务开始的运行，触发者可见的开始态通知应仍含命令或描述摘要，并符合群聊既有抑制规则。
8. **与顺序/流式无显著倒退**：与变更前相比，同一运行内飞书消息阅读顺序不出现「完成先于开始」等明显错乱案例（可与 ordering 变更共同验收，以用户可感知为准）。
9. **命令完成/失败不退化**：同一次命令执行在完成或失败后，用户仍能获取与变更前相当或更优的命令与结果信息。
10. **桌面端思考日志**：飞书 thinking 零消息场景下，桌面 SDK 运行日志中仍可查阅当次运行的思考记录。
