## 一、问题陈述

cursor-claw 设置界面的 **Skills** 标签页目前仅展示并管理**用户级** Skills（个人目录下的技能包）。当开发者在当前主工作区仓库的 `.cursor/skills/` 中放置了**项目级** Skills 时，设置界面**完全不可见**，也无法在应用内查看、编辑或删除这些技能。

这与用户预期及 Cursor 官方能力模型不一致：官方同时支持 Personal（用户级）与 Project（项目级）两类 Skills。同一设置界面中，**Rules** 标签页已支持主工作区项目级规则的查看与管理，**MCP** 标签页亦区分 global 与 project 来源；**Skills** 在来源区分与项目级可管性上明显不对称，易造成以下困扰：

1. 团队在仓库内维护共享技能包，却在设置里「找不到」；
2. 用户误以为项目级 Skills 未生效，或重复在用户级目录创建同名技能；
3. 文档与界面口径将 Skills 描述为「仅用户级」，与官方及 Rules/MCP 的项目级心智不一致。

此外，通过 cursor-claw 发起的 Cursor 执行引擎会话在运行时可能已加载项目级 Skills，但设置界面无法反映这一事实，形成「后台可能已用、前台不可见不可管」的体验断层。

## 二、目标用户

- 使用 cursor-claw 管理 Agent 配置、在仓库 `.cursor/skills/` 中维护**团队共享技能**的开发者与维护者；
- 需要在个人用户级 Skills 与当前主工作区项目级 Skills 之间清晰区分、分别维护的用户；
- 依赖设置界面统一维护 Rules / MCP / Skills，期望三类配置来源口径一致的产品使用者。

## 三、用户故事

### 3.1 查看项目级 Skills

作为在仓库中配置了 `.cursor/skills/` 的开发者，我希望在设置 **Skills** 标签页中能看到这些项目级技能及其内容概要，以便确认团队技能已就绪、无需到文件管理器或外部工具核对。

### 3.2 区分来源

作为同时使用个人技能与项目技能的用户，我希望列表或详情中能明确标识每条 Skill 来自**项目级**还是**用户级**（呈现方式可与 MCP 的 global/project 或 Rules 的项目级提示保持同一心智），避免误改或误删错误来源的技能。

### 3.3 管理项目级 Skills

作为项目维护者，当主工作区已正确配置时，我希望能在设置中对项目级 Skills 进行与用户级一致的增删改操作（新建、编辑、重命名、删除等），使团队技能维护闭环在应用内完成。

### 3.4 未配置主工作区时的引导

作为尚未在 cursor-claw 中配置主工作区的用户，当我打开 Skills 标签页并尝试管理项目级技能时，期望相关操作被禁用并看到明确说明（与 Rules 标签页在未配置主工作区时的行为对齐），而不是空白列表或无声失败。

### 3.5 保留用户级能力

作为依赖个人 Skills 的用户，我希望现有用户级 Skills 的查看与管理能力保持不变，不受项目级能力补齐的影响。

### 3.6 理解作用域

作为使用者，我希望界面或帮助文案说明：项目级 Skills **仅作用于当前主工作区**；若某次 SDK 会话的工作目录与主工作区不一致，加载范围可能与设置中展示的项目级技能不完全相同（口径与 Rules 标签页关于主工作区的作用域说明一致）。

## 四、功能范围

**在范围内**

1. **展示**：设置 **Skills** 标签页应能列出主工作区 `.cursor/skills/` 下的项目级 Skills，并与用户级 Skills 一并呈现（或分区域/带来源标识呈现）。
2. **来源区分**：每条 Skill 须可辨识为「项目级」或「用户级」；文案与交互心智向 Rules、MCP 的项目级/global 区分对齐，降低学习成本。
3. **项目级增删改**：在主工作区已配置且可写的前提下，支持项目级 Skills 的新增、编辑、重命名、删除及目录内文件维护；能力粒度与用户级现有操作对齐。
4. **未配置主工作区**：无主工作区或路径不可用时，项目级相关操作禁用并提示原因与配置入口指引，行为对齐 Rules 标签页。
5. **用户级保持**：用户级 Skills 现有列表、编辑、保存提示与使用说明保持可用；保存成功后的反馈应继续明确指向用户级目录语义。
6. **作用域说明**：在 Skills 标签页说明区域补充或调整文案，阐明项目级仅绑定主工作区、与用户级全局可用的差异，以及与 SDK 会话工作目录可能不一致时的理解口径（与 Rules 一致，不写实现细节）。
7. **知识库口径**：后续设计/归档阶段须同步修正将 Skills 仅描述为「用户级」的文档表述，使之与官方双来源模型及本变更后的界面一致（本 PRD 不展开文档修改细节）。

**不在范围内**

- 不改动 Daemon、IM（飞书/微信等）侧的 Skills 管理入口或协议；
- 不涉及 Claude Code、Codex 等非 Cursor SDK 执行引擎的 Skills 配置源（若各引擎官方路径或语义不同，不在本变更范围）；
- 不改变用户级 Skills 的存储位置语义；
- 不强制统一「插件级」或其他非 project/user 来源的 Skills 展示（若存在，另议）；
- 不做 Skills 内容格式、执行语义本身的变更，仅补齐设置界面的可见性与可管理性。

## 五、验收标准

1. **项目级可见**：在主工作区 `.cursor/skills/` 存在至少一个有效 Skill 时，打开设置 **Skills** 标签页，用户能在界面中看到该项目级 Skill，且名称/内容与磁盘一致。
2. **用户级仍可见**：用户级目录下已有 Skills 时，列表中仍能正常展示，行为与变更前一致。
3. **来源可区分**：同一标签页同时存在两类 Skills 时，用户能一眼区分「项目级」与「用户级」，无需打开文件管理器核对路径。
4. **项目级可编辑**：主工作区已配置且可写时，用户可在设置内新建、修改并保存项目级 Skill，保存后再次打开列表内容已更新。
5. **项目级可删除**：用户可在设置内删除项目级 Skill，删除后列表与主工作区目录状态一致。
6. **无主工作区禁用**：未配置主工作区时，项目级 Skills 的管理操作不可用，并展示明确提示（与 Rules 标签页未配置时的体验同级）。
7. **作用域文案**：Skills 标签页说明文案涵盖用户级与项目级双来源，并说明项目级绑定主工作区；不再将 Skills 整体描述为「仅用户级」。
8. **与 Rules 心智一致**：具备主工作区的用户，在 Rules 与 Skills 两个标签页对「项目级 / 用户级」的理解与操作预期一致，不出现「Rules 能管项目级、Skills 却不能」的割裂感。
