# 巨型单体拆分产品需求文档

> **变更 ID**：`20260711203953-巨型单体拆分`
> **来源**：kb-propose
> **类型**：技术债
> **优先级**：P1（高）
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景与问题

项目工程规范要求**单个源码文件不超过 300 行**，以降低阅读成本、便于评审与并行协作。近期代码审计发现，核心运行链路中存在多处**巨型单体文件**——单文件承载 IM 收发、消息排队、Agent 编排、管理接口、通道展示等多种职责，行数远超规范上限（其中 Daemon 主进程单文件约三千余行）。

现状带来的产品侧与协作侧影响：

1. **维护成本高**：定位飞书收消息、排队合并、Agent 下发、运维指令等任一环节故障时，需在超长文件中检索，排障与回归范围难以界定。
2. **变更风险大**：多人或多次迭代修改同一巨型文件，易产生无意耦合与行为回归，影响飞书用户正常使用。
3. **规范不可持续**：若不拆分，后续功能迭代将持续违反单文件行数约束，技术债滚雪球。
4. **职责边界模糊**：Daemon 与 Electron 两侧均存在「生命周期 + 调度 + 展示」混写，与既定架构分工（Daemon 负责 IM 与 HTTP、Electron 负责 Agent 引擎与 UI）不一致，增加新人理解成本。

Daemon 目录下已抽取部分独立能力（如飞书事件处理、管理接口、定时任务、会话名解析、展示里程碑等），但**主进程单体仍未达标**，Electron 侧 Daemon 管理、飞书桥接、会话调度、斜杠指令等模块亦存在同类问题。

## 二、目标与非目标

### 目标（必须达成）

1. **满足单文件行数约束**：纳入本变更范围的源码文件，拆分后每个文件不超过 300 行（与项目 AGENTS 规范一致）。
2. **降低维护成本**：按业务能力边界组织代码，使「收消息入队」「Agent 下发」「Daemon 启停」「飞书展示」等职责可独立定位，无需在数千行文件中全文检索。
3. **行为不回归**：拆分过程中及交付后，用户可感知的端到端行为与拆分前一致——飞书消息正常收发与排队、Agent 正常响应、运维斜杠指令（含 `/restart`）可用。
4. **分批可交付**：允许分多轮实施与验收，每轮交付后系统仍可正常运行，不要求一次性改完所有巨型文件。

### 非目标（明确不做）

- **不改变**用户可见的产品功能、飞书卡片版式或 Electron 界面布局（纯内部结构优化）。
- **不新增**面向用户的新能力或新通道。
- **不在本轮全量解决**下列已知关联债（记入 backlog，后续单独立项）：
  - **T7 调度迁移未完成**：会话调度权威仍在 Daemon，斜杠指令处理仍依赖 Electron 侧周期性轮询，架构未完全统一。
  - **会话 Agent 批量下发空实现**：`dispatchSessionAgents()` 类能力尚未落地，拆分不得假装已实现。
  - **日志双写**：Daemon 写文件与 Electron 回显 stderr 的重复日志问题，本轮仅保证不恶化，统一方案另立变更。

## 三、用户与场景

### 用户

- **飞书终端用户**：通过私聊或群聊与 Agent 对话，期望消息及时入队、排队状态可见、Agent 回复与流式展示正常。
- **运维 / 开发者**：通过斜杠指令（如 `/restart`）维护 Daemon 与通道，通过日志排查收发与调度问题。
- **工程协作者**：需要在小文件、清晰模块边界下安全迭代，而不反复触碰巨型单体。

### 场景 A：应用启动与 Daemon 就绪

用户启动 Electron 应用，Daemon 子进程被拉起并完成自检。用户（或运维）可确认 Daemon 处于可服务状态，后续飞书与 HTTP 能力可用。**拆分后该路径行为与拆分前一致。**

### 场景 B：飞书收消息并入队

用户在飞书发送文本或触发 bot 事件。系统识别会话、解析发送方与会话上下文，将消息写入排队机制，并按既有规则反馈排队/合并预览（若产品已启用）。**拆分不得导致消息丢失、重复入队或静默丢弃。**

### 场景 C：Agent 调度与回复

排队消息在合适时机被投递给 Agent 引擎（Electron 侧执行），执行结果经既有通道回传飞书（含流式或终态展示）。**拆分不得中断 dispatch 链路或改变用户可见的回复时序语义。**

### 场景 D：运维斜杠指令 `/restart`

授权用户发送 `/restart`（或项目既等价指令）。系统按既有语义重启 Daemon 或相关子系统，重启后 B～C 场景仍可用。**不得因拆分导致指令无响应、误重启或重启后无法恢复飞书连接。**

## 四、业务流程

### 主流程（端到端，拆分前后语义不变）

1. **P1** 用户启动应用 → Electron 拉起 Daemon → Daemon 完成 IM/HTTP 服务就绪。
2. **P2** 飞书用户发消息 → Daemon 接收事件 → 解析会话与发送方 → **消息入队**（含合并批次、排队状态反馈若已启用）。
3. **P3** 调度逻辑判定可执行 → 将任务交给 Electron 侧 **Agent 引擎** → Agent Run 执行。
4. **P4** Agent 产出结果 → 经飞书桥接层 **流式或终态展示** 回传用户。
5. **P5** 运维发送 `/restart` → 指令被识别并执行 → 回到 **P1** 就绪态，后续 **P2～P4** 可继续。

### 关键分支

- **P2-a（排队/合并）**：多条消息短时间到达时，仍按既有合并与预览规则处理，不因拆分改变合并策略。
- **P3-a（调度权威）**：当前仍以 Daemon 为调度 SSOT；Electron 侧轮询拉取待执行项的行为在本轮拆分中**保持现状**（T7 完整迁移属 backlog）。
- **P4-a（展示失败）**：展示层异常时，用户仍应收到与拆分前同等粒度的错误提示，不得静默失败。
- **P5-a（重启中）**：重启过程中在途消息的处理策略与拆分前一致，不得新增大面积消息丢失。

### 分批交付策略（业务表述）

为控制风险，实施与验收按**业务重要性**分批次推进，每批交付后须通过本轮验收标准再进入下一批：

| 批次 | 范围（业务能力） | 业务优先级说明 |
|------|------------------|----------------|
| **第一批** | Daemon 核心主进程：IM 接入、消息排队与合并、Agent 任务下发衔接、HTTP 管理面 | 飞书用户主路径与系统心脏；优先降低最大单体风险 |
| **第二批** | Electron 侧 Daemon 生命周期管理：拉起、轮询健康、绑定、日志回显 | 保障 P1/P5 稳定，减少启停类故障排查成本 |
| **第三批** | 飞书桥接与展示：发送、CardKit、流式展示 | 保障 P4 体验，与核心收发解耦 |
| **第四批** | 会话调度与斜杠指令处理模块 | 为后续 T7 统一调度铺路；本轮**不要求**完成 T7 迁移 |

各批次具体切分边界与任务清单由 `/kb-design`、`/kb-plan` 阶段落实；本 PRD 仅约束交付顺序与验收口径。

## 五、功能需求（产品/工程约束）

### F1 单文件行数合规

- 本变更**纳入范围**的每个源码文件，交付后行数 **≤ 300**。
- 若单能力仍超限，须继续按子能力拆分，不得以注释充数规避规范。

### F2 职责边界清晰

- Daemon 侧：IM、排队、与 Agent 的任务交接、HTTP 管理接口等保持「Daemon 负责」的架构定位。
- Electron 侧：Agent 引擎、UI、Daemon 进程管理、斜杠指令消费等保持「Electron 负责」的定位。
- 拆分后的模块命名与目录组织应让协作者能由**业务能力名称**定位代码，而非仅由历史文件名。

### F3 行为等价（零用户感知变更）

- 飞书收发、入队、合并预览、Agent 回复、流式展示、`/restart` 等路径，**用户可见结果与拆分前一致**。
- 不引入新的配置项要求用户手动迁移（除非后续独立产品变更）。

### F4 关联债登记（backlog，本轮不验收）

- **T7**：调度 SSOT 与 Electron 5s 轮询指令处理的统一迁移——记录为后续架构变更，本轮拆分不得阻塞主路径交付。
- **空实现**：会话 Agent 批量下发类能力未实现——拆分不得伪造已交付。
- **日志双写**：Daemon 文件日志与 Electron stderr 回显——本轮允许维持现状，统一治理另立变更。

## 六、风险与依赖

- **风险：拆分引入行为回归**：飞书入队、Agent dispatch、重启链路任一环节异常将直接影响用户；须按批次验收，优先 Daemon 核心。
- **风险：隐性耦合**：巨型文件内可能存在未文档化的跨职责调用；设计阶段须梳理主流程依赖，避免「拆文件却改语义」。
- **依赖**：后续 `/kb-design` 须对照本 PRD 业务流程（P1～P5）标注改动点与回归范围；`/kb-plan` 按四批策略拆解任务。
- **依赖**：项目 AGENTS.md 单文件 300 行约束为硬性验收依据之一。

## 七、验收标准

1. **Daemon 启动**：应用冷启动后，Daemon 在合理时间内进入可服务状态；HTTP/IM 能力与拆分前一致，无新增启动失败或长时间不可用。
2. **飞书收消息入队**：飞书私聊与群聊（若已启用）发送消息后，消息被正确接收并进入排队机制；不出现系统性丢失、重复消费或无法入队；排队/合并预览行为（若已启用）与拆分前一致。
3. **Agent dispatch**：入队消息在调度触发后，能正常交由 Agent 引擎执行并在飞书侧收到回复（含流式或终态路径）；不得出现大面积「消息已入队但永不执行」。
4. **`/restart` 不回归**：授权用户执行 `/restart`（或项目等价指令）后，Daemon 按既有语义完成重启；重启后 **验收标准 1～3** 仍成立。
5. **单文件行数**：本变更各批次纳入范围的源码文件，每个文件行数 **≤ 300**，符合项目工程规范。
6. **非目标未破坏**：用户可见 UI/飞书卡片版式无变更；T7 完整迁移、日志双写统一、会话 Agent 批量下发空实现填补**不作为**本轮通过条件。
