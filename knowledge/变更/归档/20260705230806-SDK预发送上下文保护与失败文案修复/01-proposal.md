# SDK 预发送上下文保护与失败文案修复产品需求文档

> **变更 ID**：`20260705230806-SDK预发送上下文保护与失败文案修复`
> **来源**：kb-propose
> **类型**：缺陷修复
> **优先级**：P1（高）
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景与问题

用户在**多个飞书群**同时使用 Cursor SDK Agent。当某群有人发送较长消息后，**多个群几乎同时**收到相同的失败提示：

> ⚠️ Agent 处理失败，建议精简输入后重新发送；若仍失败请稍后重试。

用户预期：**各群会话相互隔离，一个群的异常不应连累其他群**。

经故障日志（20260705225838～20260705230040）核实：

1. **会话隔离正常**：不同群拥有独立会话，消息通知按会话正确路由，不存在「A 群失败导致 B 群报错」的代码级串扰。
2. **各群独立失败**：各群几乎同时报错，是因为各群均在处理长输入且**上下文已严重超限**（占用远超 100%），属于同类问题在同一时段并发触发，而非会话互相污染。
3. **失败提示不准确**：系统内部已检测到上下文已满（例如占用 361%～969%），但用户侧仍收到「建议精简输入」的通用兜底文案，无法判断真实原因是「上下文已满」。
4. **失败前无意义等待**：上下文已明显超限时，用户仍须等待数秒才收到失败通知，体验像「卡住后突然报错」。
5. **通道配置因素（说明性）**：部分通道若将多个群配置为共用同一工作目录，可能加剧排查难度；此为配置问题，**本次不改通道默认隔离策略**，但需在知识库中说明多群隔离与配置关系。

## 二、目标

### 必须达成（用户可感知）

1. **准确告知上下文已满**：当发送前检测到上下文已超限时，用户应收到明确、可理解的「上下文已满 / 会话过长」类提示，**不得**再退化为「建议精简输入后重试」的通用兜底句。
2. **超限即拒或快失败**：上下文占用超过 100% 时，**不应**让用户无意义等待数秒；应**提前拒绝发送**或**尽快完成上下文换新**后给出明确结果与提示。
3. **各群体验独立可预期**：任一群因上下文超限失败时，提示应基于**该群自身**的上下文状态归因，用户能区分「本会话上下文已满」与其他失败原因。

### 可选（诊断辅助）

4. **共享工作目录告警**：当检测到多个活跃会话共用同一工作目录时，在运维日志中输出警告，便于排查通道配置是否误将多群指向同一目录。

### 非目标（明确不做）

- **不修改**通道默认的「其他会话工作目录隔离」策略（当前默认已是隔离）。
- **不大范围重构** SDK Agent 执行引擎核心模块。
- **不新增**自动化单元测试（验收以场景回归与日志可复核为主）。
- **不涉及**飞书卡片布局、视觉样式变更。

## 三、用户与场景

### 用户

- **飞书群聊用户**：在多个群同时使用 Agent，发送较长需求或附带大量上下文的消息。
- **运维 / 开发者**：通过日志排查多群并发失败、通道工作目录配置是否正确。

### 场景 A：单群上下文已满

用户在某一飞书群发送较长消息。该群会话历史与工具结果已占满上下文窗口。用户应在**较短时间内**收到明确提示：本会话上下文已满，需开启新话题、精简输入或等待系统完成会话换新，**而非**模糊的「处理失败请精简输入」。

### 场景 B：多群同时处理长消息

用户在 A、B、C 三个群几乎同时或先后发送长消息。各群**独立**检测各自上下文；若某群已满，仅该群收到「上下文已满」类提示，其他未超限的群不受影响。用户理解这是各群各自的状态，而非「群与群互相干扰」。

### 场景 C：上下文换新后的失败归因

当系统因上下文过长而换新 Agent 会话后继续处理，若仍失败，失败提示应**优先反映发送前已记录的超限事实**（上下文已满），而不是因换新后会话占用显示为零而误报为「请精简输入」。

### 场景 D：运维排查多群共用目录（可选）

多个飞书群被配置为共用同一工作目录时，日志中出现可检索的警告信息，便于确认是否为通道配置导致的多群同目录，而非会话隔离失效。

## 四、功能需求

### F1 上下文超限的准确用户提示

- 发送前已判定上下文超限（占用 ≥ 100%）时，飞书失败通知须使用**专用文案**，明确表达「上下文已满 / 会话过长」及可操作建议（如开启新话题、缩短输入、稍后重试）。
- 不得因会话换新、占用统计暂时归零等原因，将上下文超限失败误报为通用「精简输入」兜底句。

### F2 超限时的快速响应

- 发送前占用已超过 100% 时，系统应**拒绝无意义的长等待**：要么立即拒绝本次发送并提示，要么触发上下文换新并在合理时间内给出明确结果。
- 用户感知上，不应再出现「已明显超限仍等待 3～7 秒才报错」的体验。

### F3 多群会话隔离的可预期性

- 各飞书群（各独立会话）的上下文检测、失败提示与处理结果**仅作用于该会话**。
- 产品行为与文案应帮助用户建立正确心智：多群同时报错通常是因为各群均遇到同类上下文问题，而非会话串扰。

### F4 共享工作目录诊断日志（可选）

- 当同一工作目录下存在多个活跃 SDK 会话时，输出 WARN 级别日志，包含足够信息供运维关联通道与会话，**不改变**用户可见行为。

- 发送前上下文保护策略与用户可见提示口径；
- 失败通知的归因规则（上下文已满 vs 其他失败）。

## 六、风险与依赖

- **风险**：过早拒绝发送可能影响「首次超限仍尝试发送」的容错路径；需在设计与实现阶段平衡「快失败」与「自动换新后继续」。
- **依赖**：后续 `/kb-design` 需细化发送前检测阈值、换新触发条件与失败文案映射；故障样本 `crash_log/20260705225838～20260705230040` 作为回归基准。

## 七、验收标准

1. **准确文案**：发送前上下文占用 ≥ 100% 且导致失败时，飞书用户收到的提示**明确包含**「上下文已满 / 会话过长」语义，**不出现**仅「建议精简输入后重新发送」的通用兜底句（除非实际上下文未超限且失败原因为其他类型）。
2. **快速响应**：发送前占用已 ≥ 100% 的场景下，从用户发消息到收到失败或换新后结果，**不应**再出现 3～7 秒的无反馈等待后突然报通用失败（以故障样本同类场景回归为准）。
3. **会话换新后归因**：触发会话换新后若仍失败，用户提示仍应能反映**发送前已知的上下文超限**，不因换新后占用显示为零而降级为通用兜底句。
4. **多群独立**：A、B 两群并发长消息时，仅实际上下文已满的群收到「上下文已满」类提示；未超限群正常处理或按自身状态提示，无跨群误报。
5. **可选日志**：多会话共用同一工作目录时，日志可检索到 WARN 告警（若本项纳入实现范围）。
6. **非目标未破坏**：通道默认工作目录隔离策略未改动；无飞书 UI 视觉变更。
