## 一、背景与问题陈述

巨型单体拆分**第一批**已完成：Daemon 侧 HTTP 管理面、编排调度衔接、展示出站等能力已从枢纽文件中拆出，飞书用户主路径（收消息、入队、调度、回复展示）行为与拆分前一致。

然而 **Daemon 枢纽文件仍承担过多职责**：除组装与接线外，仍内嵌文件队列编排、合并批次（MergeBatch）处理、通道运行时绑定（飞书/微信）、日志写入与轮转等大段逻辑，体量远超工程可读性门槛（单文件应 ≤300 行），且已在批 1 归档中登记为 **accepted_debt（R1：批 2 queue/channel/logging）**。

现状带来的产品侧与协作侧影响：

1. **定位成本高**：排查「入队异常」「合并卡行为」「通道断连」「日志缺失」等问题时，协作者需在超长枢纽文件中全文检索，排障与回归范围难以界定。
2. **变更风险大**：队列、合并、通道、日志任一能力演进，均易牵动同一巨型文件，增加无意耦合与行为回归概率，间接影响飞书/微信用户消息可靠性与运维可观测性。
3. **规范不可持续**：若不继续拆分，后续调度、队列、通道改动将持续违反单文件行数约束，技术债滚雪球。
4. **与架构分工不一致**：枢纽应收敛为「薄组装入口」，使「队列 / 合并 / 通道 / 日志」各有清晰落点，便于新同学按业务能力名称定位，而非依赖历史单文件记忆。

本变更为**工程债清偿（批 2）**：在**用户可见语义不变**前提下，将仍驻留枢纽内的队列、通道、日志能力拆至独立模块，使枢纽仅保留组装与接线职责。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 短期无直接 UI 变化 | 飞书/微信收发、排队、合并预览、Agent 回复、斜杠指令等界面与交互本轮不变 |
| 排障与修复变慢 | 队列/通道/日志故障需通读巨型枢纽，定位与验证周期长 |
| 演进易引入回归 | 合并策略、通道绑定、日志轮转等局部改动易误伤相邻路径，抬高消息丢失或静默失败风险 |
| 长期可维护性成本 | 枢纽难演进时，同类故障重复出现、修复窗口拉长，影响运维信心 |

## 三、目标与非目标

### 目标（必须达成）

1. **枢纽瘦身**：Daemon 枢纽收敛为薄组装入口，不再承载大段队列、通道、日志业务实现（目标体量约 ≤200 行量级，具体切分边界由后续设计阶段落实）。
2. **职责拆分**：将仍驻留枢纽内的 **queue**（文件队列编排、MergeBatch、相关 SSE/事件衔接）、**channel**（飞书/微信 ChannelRuntime 绑定与生命周期）、**logging**（日志写入与轮转）拆至可独立理解与评审的模块边界。
3. **行为等价**：对外 HTTP、IM 入队、dispatch、合并卡、斜杠指令及通道绑定等行为与拆分前一致，用户无感知变更。
4. **可观测性保留**：运维仍可用既有日志关键字（如 dispatch_failed、merge_action、presentation_failed 等）检索与告警，不因拆分而丢失关键诊断信息。
5. **行数合规**：拆分后纳入范围的各源码文件单文件 ≤300 行，符合项目工程规范。

### 非目标（明确不做）

- **不改** Electron 侧 `daemon-manager` 生命周期管理模块（属巨型单体拆分其他批次 backlog）。
- **不改** 飞书桥接核心（lark-core）内部结构。
- **不做** 调度并发模型改造、T7 统一调度迁移、会话 Agent 批量下发空实现填补。
- **不做** 日志双写统一（Daemon 文件日志与 Electron stderr 回显）；本轮仅保证不恶化，统一方案另立变更。
- **不在 propose 阶段** 绑定具体类名、文件路径、内部接口签名（归属 `/kb-design`）。

## 四、用户与场景

### 用户

- **飞书 / 微信终端用户（间接）**：依赖可靠入队、合并预览、通道连接与 Agent 回复；本轮不改变可见行为，但降低后续改动引入消息丢失或静默失败的概率。
- **运维 / 开发者**：需要按「队列 / 合并 / 通道 / 日志」快速定位代码与日志，缩短故障修复周期；斜杠指令（如重启类）仍可用。
- **工程协作者**：需要在合规体量、清晰模块边界下安全迭代 Daemon 枢纽周边能力。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 冷启动就绪** | 应用冷启动后 Daemon 正常 bind、HTTP/IM 能力与拆分前一致。 |
| **S2 入队与 dispatch** | 消息入队、领取、调度下发链路正常，不出现系统性「已入队永不执行」。 |
| **S3 合并卡** | 短时间多条消息到达时，合并批次与合并卡交互（含按钮/指令若已启用）与拆分前一致。 |
| **S4 通道绑定** | 飞书/微信通道启动、绑定、断连恢复等行为不退化。 |
| **S5 斜杠与运维** | 授权用户斜杠指令（含重启类）响应与拆分前一致，重启后 S1～S4 仍成立。 |
| **S6 日志可检索** | 运维用既有关键字仍可定位 dispatch、合并、展示失败等事件。 |
| **S7 结构合规** | 枢纽仅为组装接线；queue/channel/logging 各有独立可评审落点，单文件 ≤300 行。 |

## 六、验收标准

### 6.1 主路径（产品/运维可感知）

1. **冷启动**：Daemon 冷启动后正常 bind；入队、dispatch、合并卡、斜杠指令与拆分前一致。
2. **队列与合并**：入队、合并批次、合并卡展示与交互不退化；不出现系统性丢消息或重复消费。
3. **通道**：飞书/微信通道绑定与消息收发路径正常。
4. **斜杠**：授权斜杠指令（含重启类）可用；重启后主路径仍成立。

### 6.2 可观测与结构

1. 运维仍可用既有日志关键字检索（dispatch_failed、merge_action、presentation_failed 等）。
2. 枢纽仅为组装+接线，不再承载大段 queue/channel/logging 实现；各职责模块可说明「负责什么 / 不负责什么」。
3. 纳入范围单文件 ≤300 行。

### 6.3 非功能

1. 变更代码含中文注释（与项目规范一致）。
2. 不引入与拆分无关的策略默认值变更；调度并发、日志双写统一等须改策略时另开变更。

## 七、范围边界

### 在范围内

- Daemon 枢纽内 queue、channel、logging 职责拆分与结构整理。
- 对外行为回归与现契约对齐；枢纽瘦身至组装入口。
- 归档阶段同步 Daemon 工程平台知识中模块职责描述（若有失真）。

### 不在范围内

- Electron daemon-manager、lark-core 拆分。
- 调度并发改造、T7 统一调度、日志双写统一。
- 用户可见 UI/飞书卡片版式变更；新增配置项要求用户迁移。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 批 1 债务承接 | R1 已在批 1 登记为 accepted_debt，本变更为其清偿 | 对照批 1 归档范围与验收口径，避免重复拆已迁出模块 |
| 隐性行为漂移 | 拆分误改 queue/MergeBatch/channel 边界导致丢消息或合并异常 | 行为回归硬门槛；覆盖 S1～S5 |
| 日志关键字变化 | 拆分后日志落点变化导致运维检索失效 | 保留既有 diagnostic 关键字或等价映射，纳入 S6 验收 |
| 与并行变更冲突 | 其他进行中变更可能触及同一枢纽 | 设计阶段标注文件白名单与依赖，必要时串行合并 |
