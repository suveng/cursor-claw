## 一、背景与问题

Cursor Claw 支持 Cursor SDK、Claude Code、Codex、OpenCode 四引擎执行 Agent。四引擎增量接入后，系统内 **Agent 启动与调度路径未完全统一**，形成「双轨」：

| 入口类型 | 当前行为（产品可感知） |
|----------|------------------------|
| IM（飞书等） | 经 Daemon 调度，走统一网关拉起 Agent |
| 定时任务 / 工作流 / 会话内 chat new | 按引擎类型分别走各自独立启动通道 |

由此带来三类问题：

1. **资源浪费**：应用启动时，无论当前 Profile 实际使用哪些引擎，进程内会同时常驻多个 Agent 服务实例；仅使用 Cursor SDK 的用户仍被迫承载全部引擎的服务开销。
2. **路由不一致**：同一产品能力（「启动 Agent 执行任务」）在不同入口下走不同通道，增加行为差异、排障与后续演进成本。
3. **架构债务未闭环**：统一网关已是 IM 路径的权威入口，但任务、工作流、chat new 等路径尚未收敛，与「单一启动事实来源（SSOT）」的产品架构目标不一致。

**正交说明**：本变更与已归档变更 `20260711205108-Orchestrator会话路由SSOT收尾`（会话活跃与回退栈 SSOT）为**独立议题**，不合并推进。

## 二、目标与非目标

### 目标（必须达成）

1. **全路径统一网关**：所有 Agent 启动与调度（IM、定时任务、工作流、chat new）均经**同一统一网关**作为单一事实来源，不再按入口分裂为多条并行路径。
2. **按需启动非 SDK 引擎服务**：未配置或未使用的引擎，其 Agent 服务**不在应用启动时无条件拉起**；仅在对应通道/Profile 需要或首次实际启动该引擎 Agent 时才启动。
3. **仅 SDK Profile 时最小常驻**：当用户 Profile 仅启用 Cursor SDK 引擎时，进程内 Agent 服务实例数量应为 **1**（统一网关常驻，满足 Daemon IM 依赖）；不得再额外常驻其他引擎服务。
4. **行为不回归**：四引擎在 IM、任务、工作流、chat new 场景下的启动、调度、回复与失败提示等用户可见行为与现网一致。

### 非目标（明确不做）

- **不改变**飞书卡片展示、Electron 界面布局或用户指令语法（如 `/chat new`）。
- **不迁移** IM 主路径调度出 Daemon（Orchestrator 仍在 Daemon）。
- **不修改**会话活跃路由、临时会话回退栈语义（属已归档 Orchestrator 会话路由变更范围）。
- **不在本期**拆分历史超限源码文件（属其他变更范围）。

## 三、用户与场景

### 用户

- **飞书管理员 / 主用户**：通过 IM 与 Agent 对话，期望响应速度与稳定性不因后台冗余服务而下降。
- **仅 SDK Profile 用户**：只使用 Cursor SDK，期望应用启动后资源占用合理，无未使用引擎的后台负担。
- **多引擎 Profile 用户**：按需使用 CC/Codex/OpenCode，期望首次使用该引擎时正常启动，后续行为与现网一致。
- **运维 / 开发者**：需要启动路径可观测、可维护，排障时存在唯一权威入口。

### 场景 A：仅 SDK Profile 应用启动（核心优化）

用户 Profile 仅配置 Cursor SDK。应用启动后，进程内仅保留统一网关所必需的 **1 个** Agent 服务实例；用户通过 IM 发消息，Agent 正常响应。**不得**再无条件拉起未配置引擎的服务。

### 场景 B：IM 四引擎消息调度（基线不回归）

用户在飞书私聊或群聊发送消息，Profile 分别配置 SDK / CC / Codex / OpenCode。各引擎消息经 Daemon 排队、调度后，Agent 正常启动或复用长驻实例并回复。**行为与现网一致。**

### 场景 C：定时任务触发 Agent（路径收敛）

Daemon 定时任务到期，按 Profile 引擎配置触发 Agent 执行。启动请求须经统一网关，任务完成后状态与通知与现网一致。**不得**因路径收敛导致任务漏触发、重复触发或错误引擎。

### 场景 D：工作流节点触发 Agent（路径收敛）

工作流执行至 Agent 节点，按节点配置的引擎类型启动 Agent。须经统一网关，工作流继续/失败语义与现网一致。

### 场景 E：chat new 创建临时会话（路径收敛）

用户发送 `/chat new` 或等价指令创建临时会话 Agent。启动须经统一网关；临时会话运行、结束、活跃会话回退（若适用）与现网一致。

### 场景 F：多引擎 Profile 首次使用非 SDK 引擎（懒加载）

用户 Profile 配置了 CC 但未使用过。应用启动时不常驻 CC 服务；用户首次通过 IM 或任务触发 CC Agent 时，服务按需启动，随后长驻与调度行为与现网一致。

## 四、业务流程

### 主流程：任意入口 → 统一网关 → Agent 执行

1. **F1** 用户或系统发起 Agent 启动请求（IM 消息、定时任务、工作流节点、chat new 等）。
2. **F2** 系统解析目标会话、引擎类型与 Profile 配置（沿用现网规则）。
3. **F3** 请求统一经**统一网关**路由至目标引擎 Agent（不再按入口走独立直连通道）。
4. **F4** 若目标引擎服务尚未运行且当前 Profile/通道需要该引擎，**按需启动**该引擎服务；若不需要或未配置，不启动。
5. **F5** Agent 执行 Prompt / Run，流式输出与完成通知与现网一致。
6. **F6** 失败、超时、watchdog 与用户可见错误文案与现网一致。

### 关键分支

- **F4-a（仅 SDK Profile）**：F1～F6 全程仅涉及统一网关，进程内 Agent 服务实例数保持为 1。
- **F4-b（多引擎 Profile，引擎未用过）**：首次 F3 命中该引擎时触发 F4 启动；后续复用长驻语义与现网一致。
- **F4-c（引擎已长驻）**：跳过 F4 启动，直接进入 F5，行为与现网一致。

### 不变路径（显式不改）

- **IM 入站 → Daemon 排队 → Orchestrator dispatch**：主路径调度仍在 Daemon。
- **会话活跃路由与临时会话回退**：仍遵循 Daemon SSOT（前序已归档变更），本变更不改动。
- **四引擎长驻、超时 finalizer、watchdog、ContextRotation**：产品语义保持，仅收敛「如何到达 Agent」的入口路径。

## 六、验收标准

1. **仅 SDK Profile 常驻数量**：Profile 仅启用 Cursor SDK 时，应用启动后进程内 Agent 服务实例数量为 **1**（统一网关）；无额外未使用引擎服务常驻。
2. **四引擎行为回归**：Cursor SDK、Claude Code、Codex、OpenCode 在 **IM + 定时任务 + 工作流 + chat new** 四类入口下，启动、调度、回复与失败提示等行为与变更前现网一致，无功能回归。
3. **知识库同步**：`knowledge/业务域/Agent调度/03-启动与自动重连.md` §二 已更新为全路径经统一网关的架构描述，与实现一致（archive 阶段验收）。
4. **工程构建**：`npm run build` 通过。

## 七、风险与依赖

| 项 | 说明 |
|----|------|
| 依赖 | Daemon IM 调度、Orchestrator、四引擎长驻与 session-dispatcher 既有能力须保持可用 |
| 风险 | 懒加载时序若处理不当，可能导致首次启动延迟或竞态；须在 design 阶段明确边界 |
| 正交 | 与会话路由 SSOT 收尾变更无代码重叠假设，可并行排期 |
