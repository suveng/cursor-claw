# 三引擎续接终态hardening产品需求文档

> **变更 ID**：`20260712145449-三引擎续接终态hardening`
> **来源**：kb-propose
> **类型**：可靠性
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无
> **依赖**：`20260712113332-非Cursor引擎主进程续接` 已归档；与进行中「Agent标识跨重启持久化」可并行（路由持久 vs Run 终态）

## 一、背景与问题陈述

归档变更「非Cursor引擎主进程续接」已为 Claude / Codex / OpenCode 接入主进程重启后续接：活跃 Run 可落盘并在启动时尝试恢复。

但相对 Cursor 引擎体验，三引擎仍有可靠性空洞：

1. **终态不透明**：续接后缺少与 Cursor 同类的「Run 是否已结束」可理解判定；成败过度依赖各引擎 resume 本身，引擎侧已结束的 Run 可能仍被当成「续上了 / 还在跑」。
2. **依赖缺失静默**：以 Codex 为例，CLI/依赖不可用时 recover 可能早退，盘上快照滞留，且无 IM 可感知通知。
3. **失败不可分**：用户与运维难以区分「可再试」与「不可恢复」，只能凭感觉判断是否该重发或放弃。

本变更在既有续接入口上做**终态与可感知性 hardening**，消除「以为在跑 / 静默失败」的误判，而不重做 Cursor 终态探测能力本身。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 误判运行中 | 重启后续接后会话仍像在跑，实际引擎侧已结束或从未真正续上 |
| 静默失败 | CLI/依赖缺失等导致 recover 早退，无飞书/IM 提示，用户不知失败 |
| 体验割裂 | Cursor 续接有较清晰终态观感；三引擎成败不透明、通知不齐 |
| 无法决策下一步 | 失败后不清楚该重试、重发任务，还是视为不可恢复需人工介入 |
| 快照滞留观感 | 依赖缺失时活跃 Run 记录未清理，下次重启仍可能重复踩坑 |

## 三、目标与非目标

### 目标（必须达成）

1. **终态可理解**：Claude / Codex / OpenCode 在 recover 路径具备可理解的终态判定或等价探测，避免「引擎已结束仍当运行中」。
2. **依赖缺失可感知**：CLI/运行依赖缺失导致无法续接时，须有 IM 可感知通知（不得静默早退）。
3. **失败可区分**：续接失败须能区分**可重试**与**不可恢复**，便于用户/运维决定下一步。
4. **入口不冲突**：与既有 resume / recover 入口共存，不破坏已落地的主进程续接主路径。
5. **三引擎对齐口径**：三引擎在「终态可观测 + 失败可感知」上产品口径一致（允许引擎能力差异下的等价手段）。

### 非目标（明确不做）

- **不重做** Cursor 式 `getRun` 终态探测能力本身（不把 Cursor 方案原样搬到三引擎）。
- **不改** IM 入队 / 消息队列入队策略与调度主路径。
- **不做** 工作流引擎分支 Gateway 或四引擎 Port 总线大重构。
- **不扩大** 为全新跨引擎 Run 生命周期产品；本变更为既有续接上的 hardening。
- **不在 propose 阶段** 绑定实现类名、文件路径、内部接口签名（归属 `/kb-design`）。

## 四、用户与场景

### 用户

- **IM / 飞书会话用户**：重启或异常后期望知道「还在跑 / 已结束 / 续接失败」，不要静默。
- **多引擎用户**：在 Cursor 与 Claude/Codex/OpenCode 间切换时，期望续接终态观感可理解、可对齐。
- **运维 / 排障**：需区分依赖缺失、可重试失败、不可恢复失败，避免空等或盲目重发。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 重启后仍活跃** | 引擎侧 Run 仍在，续接成功；用户可继续跟进度，终态随后正常收束。 |
| **S2 引擎侧已结束** | 盘上有活跃快照但引擎已终态；系统判定已结束（或等价探测），不长期误报「运行中」。 |
| **S3 依赖缺失** | 如 Codex CLI 不可用；recover 不静默早退，IM 通知用户/会话侧可感知。 |
| **S4 可重试失败** | 瞬时错误导致续接失败；失败类型标明可重试，不与不可恢复混为一谈。 |
| **S5 不可恢复失败** | 关键依赖或会话不可恢复；明确不可恢复，避免用户空等「还会自动好」。 |
| **S6 与既有入口共存** | hardening 后既有 resume/recover 入口行为不冲突、主路径不回退到「无续接」。 |
| **S7 与路由持久并行** | 与「Agent标识跨重启持久化」并行无产品冲突：一方管路由身份，一方管 Run 终态/可感知。 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | **终态判定/等价探测**：三引擎 recover 路径须具备可理解的终态判定或等价探测，结果对产品侧可观测。 |
| R2 | **依赖缺失通知**：CLI/依赖缺失导致无法续接时，必须发出 IM 可感知通知。 |
| R3 | **失败分类**：续接失败须区分可重试 vs 不可恢复（产品语义清晰，可供通知/排障消费）。 |
| R4 | **入口兼容**：不破坏既有主进程续接与 resume 入口；hardening 为增强而非替换整条续接产品。 |
| R5 | **Cursor 无回归**：不改变 Cursor 既有续接与终态体验；不强制三引擎复刻 Cursor `getRun`。 |
| R6 | **范围克制**：不改 IM 入队；不做工作流 Gateway；不重做跨引擎生命周期总架构。 |

## 六、验收标准

### 6.1 主路径

1. **终态可观测**：三引擎在「引擎侧已结束但仍有活跃快照」场景下，不会长期维持「还在跑」的误导状态；终态或等价结论可被观测。
2. **依赖缺失有通知**：人为制造/模拟 CLI 或必要依赖缺失时，recover 路径有 IM 可感知提示，而非静默早退。
3. **失败可区分**：至少能在验收中区分一类可重试失败与一类不可恢复失败（通知文案或等价产品信号可辨）。

### 6.2 回归与边界

1. **既有续接入口不冲突**：成功续接主路径仍可用；不因 hardening 退化为「重启后必须手动重发」才继续。
2. **Cursor 无回归**：Cursor 续接/终态相关场景行为不变。
3. **非目标未扩大**：未引入 IM 入队改动、工作流 Gateway、Cursor `getRun` 原样搬迁。

### 6.3 非功能

1. 变更代码含中文注释。
2. 不引入与续接终态/可感知无关的产品策略变更；须改策略时另开变更。
3. 与「Agent标识跨重启持久化」并行时，不以本变更承担路由身份持久职责。

## 七、范围边界

### 在范围内

- Claude / Codex / OpenCode 主进程 recover 的终态判定或等价探测（产品语义）。
- 依赖缺失等不可续接场景的 IM 可感知通知。
- 续接失败的可重试 / 不可恢复区分（产品语义）。
- 与既有 resume/recover 入口的兼容与 Cursor 无回归验收。

### 不在范围内

- Cursor `getRun` 能力重做或原样移植。
- IM 入队 / 消息队列策略调整。
- 工作流引擎分支 Gateway。
- Agent 路由/标识跨重启持久化（并行变更，职责分离）。
- 全新四引擎 Run 生命周期产品或 Port 总线。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 依赖已归档续接 | `20260712113332-非Cursor引擎主进程续接` 为基线 | 依赖已满足；在既有续接上 hardening |
| 引擎能力差异 | 三引擎对「终态」可探测性不一致 | 允许等价探测；design 对齐产品口径，不臆造引擎能力 |
| 与路由持久并行 | 「Agent标识跨重启持久化」同时进行 | 职责分离：路由身份 vs Run 终态；接口边界 design 时划清 |
| 通知噪音 | 依赖缺失或终态判定过严导致过度通知 | 验收约束：关键失败可感知，非成功路径刷屏 |
| 误伤成功续接 | hardening 过严导致本可续上的 Run 被判死 | 验收硬门槛：既有成功续接入口不冲突 |
