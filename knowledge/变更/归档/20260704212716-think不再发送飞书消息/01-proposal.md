> **来源**：kb-propose
> **类型**：待确认
> **优先级**：待确认
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 背景与问题

cursor-claw 通过飞书、微信等即时通讯通道，让用户与 Cursor Agent 对话并获取运行反馈。产品演进中，与「思考过程」相关的飞书出站经历了多次策略调整：

1. **抑制思考卡片**（`20260627220000-飞书抑制tool与thinking展示`）：飞书通道不再以 CardKit 等形式展示 thinking 类过程卡片，减轻刷屏与视觉干扰。
2. **思考里程碑文本**（`20260704174846-SDK think与task事件实时通知`）：在卡片抑制后，飞书侧改为发送「正在思考…」等里程碑文本，使用户仍能感知 Agent 正在推理。
3. **过程与结论时序优化**（进行中变更 `20260704190748-IM通知消息顺序与流式推送优化`）：要求 thinking 等过程继续实时推送飞书，并与 assistant 流式答复协调「过程在上、结论在下」的呈现顺序。

当前用户反馈：**飞书侧不希望再收到任何与思考过程相关的出站消息**——无论卡片还是里程碑文本。思考过程仍应在桌面端 SDK 运行界面（日志中的思考标记）可见，供需要深入排查的用户查阅；即时通讯通道应更安静，仅保留 task、关键工具过程与最终答复等更有行动价值的信息。

经归纳，缺口在于：飞书通道对 thinking 事件仍有一条「降级但可见」的出站路径（里程碑文本），与「飞书完全静默思考过程」的诉求不符；同时与进行中 ordering 变更里「thinking 继续实时推飞书」的条款存在策略冲突，需在本变更中明确取代关系。

## 目标与非目标

### 目标

1. **飞书 thinking 完全静默**：Cursor SDK 运行期间，凡属于「思考过程」类事件，**不得**向飞书发送任何出站消息（无卡片、无里程碑文本、无等价过程通知）。
2. **桌面端可见性保留**：用户仍可在桌面 SDK 运行界面查看思考过程日志，不因飞书静默而丢失本地可观测性。
3. **其他过程通知不变**：task 里程碑、notify 级工具（如命令执行开始）等飞书过程通知**不在本变更范围**，继续按既有策略出站。
4. **与 ordering 变更协调**：明确取代进行中变更里「飞书 thinking 须实时里程碑」的条款；assistant 流式答复、task/tool 过程通知及「过程在上、结论在下」等 ordering 产品目标仍成立，在验收层面说明 thinking 不再飞书出站后 assistant 顺序如何保障。
5. **通道边界清晰**：本变更仅调整**飞书**通道对 thinking 的出站策略；微信等其他通道行为单独说明，默认不变。

### 非目标

- **不**停止飞书对 task、notify 级工具、assistant 答复等消息类型的既有出站策略（除非与 thinking 无关节的既有 bug，不在本单处理）。
- **不**改变 Agent 内部是否产生 thinking 事件或推理逻辑；仅调整**飞书用户侧是否收到** thinking 相关通知。
- **不**改造 Electron 设置界面或新增「按通道开关 thinking 通知」的用户配置（可作为后续增强）。
- **不**扩展至 Claude Code SDK、Codex SDK 等非 Cursor SDK 路径。
- **不**在本阶段定义具体模块、接口或实现方案（归属 `/kb-design`）。

## 用户故事

### 飞书私聊用户

- 作为通过飞书与 Agent 对话的用户，当 Agent 进入思考阶段时，我希望飞书会话**不再弹出**「正在思考…」等提示，避免过程信息刷屏；我仍可通过桌面端查看思考日志，需要时自行打开。
- 作为关注执行进度的用户，当 Agent 开始子任务或执行命令时，我希望飞书**继续**收到 task、命令执行等里程碑，以便知晓「在做什么」，而非「在想什么」。

### 微信与其他通道用户

- 作为微信用户，我希望本次变更**不改变**微信侧 thinking 相关呈现（若当前有则保持，若当前无则仍无），不因飞书策略调整而意外改变微信体验。

### 运维与管理员

- 作为排查「飞书消息过多」投诉的支持人员，我希望 thinking 类消息在飞书侧为零，便于区分「过程噪音」与「任务/结论」类消息。
- 作为与 ordering 变更协同的发布负责人，我希望两份变更的策略边界文档化：thinking 不再飞书出站后，assistant 与 task/tool 过程的顺序目标仍可验收。

## 功能需求

### F1 飞书 thinking 零出站

| 编号 | 需求描述 |
|------|----------|
| F1.1 | Cursor SDK 运行期间，所有归类为「思考过程」的事件，**不得**向飞书发送任何出站消息，包括但不限于 CardKit 卡片、里程碑文本、摘要气泡及与之等价的呈现形态。 |
| F1.2 | 上述静默须覆盖思考阶段的**全部**更新（含思考开始、进行中、阶段切换等），不得仅抑制首条而后续仍出站。 |
| F1.3 | 飞书通道对 thinking 的静默**不**影响同一运行内 task、notify 级工具、assistant 答复等**非 thinking** 消息的既有出站规则。 |

### F2 桌面端思考可观测性

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 思考过程仍须在桌面 SDK 运行界面（含运行日志中的思考标记）对用户可见，飞书静默不得删除或屏蔽本地日志。 |
| F2.2 | 用户无需额外配置即可在桌面端查阅当次运行的思考记录，行为与变更前本地可观测性一致或更完整。 |

### F3 通道范围与默认策略

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 本变更**仅**约束飞书通道对 thinking 的出站；**默认**微信及其他已配置通道的 thinking 呈现策略**不变**。 |
| F3.2 | 若某非飞书通道当前亦无 thinking 出站，本变更不得为其**新增** thinking 过程通知。 |
| F3.3 | 群聊、任务面板触发等等价飞书出站路径，须与私聊一致：thinking 零出站。 |

### F4 task 与 notify 级工具过程通知（范围外保持）

| 编号 | 需求描述 |
|------|----------|
| F4.1 | task 开始/进行/完成等里程碑在飞书的既有通知**继续生效**，本变更不得削弱或误伤。 |
| F4.2 | notify 级工具（如 shell 命令开始、写文件、子 Agent 派发等按分级仍应通知的工具）在飞书的过程通知**继续生效**。 |
| F4.3 | 工具调用通知分级原则不变：默认静默的只读探查类工具仍不出站。 |

### F5 与 IM 消息顺序变更的协调

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 本变更**取代**进行中变更 `20260704190748-IM通知消息顺序与流式推送优化` 中关于「飞书 thinking 须继续实时里程碑/过程推送」的条款；该变更其余目标（assistant 流式、task/tool 过程顺序、过程在上结论在下等）**仍然有效**。 |
| F5.2 | thinking 不再参与飞书出站后，参与「过程在上、结论在下」编排的飞书过程序列**仅含** task、notify 级工具等仍出站的过程；assistant 答复首条飞书可见呈现的时机须与**剩余**过程序列协调，不得因 thinking 已静默而出现「结论先于 task/tool 过程」的颠倒。 |
| F5.3 | 无 task/tool 等飞书过程、仅有思考与最终答复的短问答：飞书侧用户**不应**看到思考提示，assistant 答复可按既有流式/短任务规则及时呈现，**不得**为已不存在的 thinking 飞书占位而引入不合理延迟。 |
| F5.4 | 含 task 或 notify 级工具的长任务：飞书会话中仍须先呈现这些过程通知，再呈现 assistant 答复首条可见内容（与 ordering 变更 F1/F8 对非 thinking 过程的意图一致）。 |

## 边界与例外

1. **仅思考、无 task/tool、有答复**：飞书不出现思考提示；assistant 答复按短任务/流式规则呈现，不因「无过程可排」而错误等待 thinking 飞书占位。
2. **思考与 task 交织**：飞书仅展示 task 等非 thinking 过程；思考阶段不产生任何飞书消息，task 里程碑仍按发生顺序呈现。
3. **运行失败/停止**：三态与失败提示语义不变；thinking 静默不得导致「长时间无任何飞书反馈」而使用户误判卡死——task/tool 或处理中态仍应提供必要信号。
4. **隐私**：若思考内容含敏感信息，飞书零出站有利于隐私；桌面端日志策略遵循既有规范，本变更不扩大 IM 暴露面。
5. **非 Cursor SDK**：其他引擎路径不在本次范围。

## 验收标准

1. **飞书 thinking 零消息**：在 Cursor SDK 路径、飞书私聊场景，模拟含明显思考阶段的运行（含多段思考更新），飞书会话中**不得**出现任何思考类卡片、里程碑文本或等价过程通知；桌面端运行日志中仍可看到思考记录。
2. **task 通知仍出站**：同场景或独立场景下，触发含子 task 里程碑的运行，飞书**仍须**按既有策略收到 task 相关过程通知，且不受本变更误伤。
3. **notify 级工具仍出站**：模拟含 shell 开始、写文件等应通知工具的 run，飞书**仍须**收到对应过程通知（含用户关心的描述信息），与变更前 notify 级行为一致。
4. **静默类工具仍静默**：read、glob 等默认静默工具仍不出站，本变更不得复活。
5. **微信默认不变**：若环境已配置微信，对含 thinking 的运行抽检：微信侧 thinking 相关呈现与变更前一致（有则仍有、无仍无），无因飞书策略调整而产生的非预期变化。
6. **与 ordering 协调—有 task/tool 时长任务**：在飞书侧，当存在 task 或 notify 级工具过程且最终将产出 assistant 答复时，用户会话中须**先**看到 task/tool 过程序列，**后**看到 assistant 答复首条可见内容；thinking 不参与该序列，且不得因 thinking 曾发生而导致 assistant 抢先于 task/tool 过程。
7. **与 ordering 协调—纯思考短问答**：无 task/tool 等飞书过程、仅有思考与答复的短问答，飞书无思考提示，assistant 首条可见内容时延与变更前同场景相比无明显劣化。
8. **群聊与任务面板**：飞书群聊或任务面板触发路径各至少 1 个场景验证 thinking 零出站，且 task/tool 行为符合上述 2～3 项。
9. **回归—无重复 assistant**：本变更不得引入 assistant 答复重复发送等 ordering 变更已约束的回归（与进行中变更验收 E10/F8.3 意图一致）。
