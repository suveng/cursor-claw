> **来源**：kb-propose
> **类型**：可靠性
> **优先级**：P0
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无
> **父债**：`20260711232817-dispatch失败重入队与ack策略`

## 一、背景与问题陈述

归档变更「dispatch失败重入队与ack策略」已闭环 **IM Orchestrator** 主路径：launch / 交给执行失败时，任务可释放回队、有限重试，耗尽后可感知停试再确认移除。

但通过 **HTTP dispatch** 旁路（含 MCP、工作流等经该入口触发的 Agent 任务）仍沿用旧语义：**失败即确认移除**；执行侧 **busy** 时也不释放回队。用户侧表现为任务静默丢失，只能手动重发。

本变更补齐该旁路与 IM 主路径的**可靠性策略对称**，消除「同一产品、两条入口、两种丢任务行为」的空洞。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 任务静默丢失 | 经 HTTP/MCP/工作流触发的 Agent 任务在调度失败后从待办消失，无自动再试 |
| 必须手动重发 | 要恢复同一任务，只能再次调用入口或重发原文；系统不替用户保留待办 |
| 与 IM 体验割裂 | 同一用户在飞书发任务失败可重试；经 HTTP 旁路失败则丢，可靠性观感不一致 |
| busy 吞任务 | 执行侧忙碌时任务被确认移除或不释放，错过后续可调度窗口 |
| 排障困难 | 日志可见失败，但待办已空，无法从队列视角确认「本该再试的那条」 |

## 三、目标与非目标

### 目标（必须达成）

1. **策略对齐**：HTTP dispatch 失败路径与 IM launch 失败策略语义一致——可释放回队、有限重试、耗尽后可感知停试再确认移除。
2. **失败可恢复**：瞬时或可恢复失败时，用户无需手动重发即可在策略窗口内再次被调度。
3. **耗尽可感知**：重试耗尽或放弃时，不得静默丢弃；用户/调用方可感知「已停止自动重试」。
4. **busy 不吞任务**：执行侧忙碌时不得以「确认移除」吞掉任务；任务须仍可在后续窗口再调度。
5. **成功路径不变**：成功交给执行后仍最终确认移除，不因本变更引入成功任务重复轰炸。

### 非目标（明确不做）

- **不改** IM 卡片 UI、消息样式与交互视觉。
- **不拆** file-queue / 文件队列整体架构或做存储形态大翻修。
- **不改** 对外 HTTP 契约形状（路径、字段结构、状态码形状以现网为准）；仅对齐**失败/忙碌时的队列与重试行为**。
- **不做** 引擎 Port 总线或四引擎 Run 生命周期抽象（属相邻/其他变更范围）。
- **不在 propose 阶段** 绑定实现类名、文件路径、内部接口签名（归属 `/kb-design`）。

## 四、用户与场景

### 用户

- **HTTP/MCP/工作流调用方**：期望「调度失败 ≠ 任务作废」，与 IM 主用户同等可靠性。
- **飞书主用户（间接）**：经工作流或 MCP 触发的任务最终仍可能落回 IM 会话语境，不应因入口不同而丢失。
- **运维**：需区分「还在重试」「busy 待再调度」「已停试需介入」。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 瞬时调度失败** | HTTP dispatch 失败后任务释放回队，在有限策略内自动再试，无需手动重发。 |
| **S2 重试耗尽** | 持续失败达到上限后停止自动重试；调用方/用户可感知停试；再确认移除符合「不静默」规则。 |
| **S3 busy 可再调度** | 执行侧 busy 时任务不确认移除、不吞没；恢复容量后可再次领取调度。 |
| **S4 成功最终 ack** | 成功交给执行后确认移除与现网一致，不重复执行轰炸。 |
| **S5 与 IM 语义一致** | 同一类失败/忙碌条件下，HTTP 旁路与 IM launch 的「释放 / 重试 / 停试 / ack」产品语义对齐（次数与间隔默认值可在设计阶段与 IM 对齐，本期以语义一致为硬门槛）。 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | **失败可释放回队**：HTTP dispatch / 交给执行失败时，默认不得永久确认移除；须释放回可再领取状态（或等价待重试态）。 |
| R2 | **有限重试**：具备与 IM 主路径对齐的有限重试策略（次数与/或时间窗及放弃条件）；禁止无限重试打满待办。 |
| R3 | **耗尽可感知**：重试耗尽或策略放弃后，须有可感知的停试结果（调用方可区分失败终态；不要求改 IM 卡片 UI）。 |
| R4 | **busy 不吞任务**：busy 时不得确认移除导致任务丢失；任务须可在后续窗口再调度。 |
| R5 | **成功最终 ack**：成功路径仍最终确认移除，行为与现网成功预期一致。 |
| R6 | **契约形状不变**：对外 HTTP 请求/响应形状不因本变更而 breaking；仅行为对齐可靠性语义。 |
| R7 | **与父债闭环**：父债 IM 主路径已闭环；本变更关闭 HTTP 旁路剩余空洞；知识库中相关「HTTP 失败即丢」限制须在归档阶段更新。 |

## 六、验收标准

### 6.1 主路径

1. **失败可重试**：人为制造可恢复的 HTTP dispatch 失败后，同一任务在无需手动重发的前提下，能在策略窗口内再次进入调度或仍处于可重试待办。
2. **耗尽可感知**：持续失败至上限后，系统停止自动重试，且调用方/观测侧可感知「已停试」（不得出现「已 ack 且无任何失败终态痕迹」的静默丢失）。
3. **成功最终 ack**：正常成功路径下，任务最终确认移除，且不会因本变更被重复执行多次。
4. **busy 可再调度**：busy 场景下任务不被确认移除吞没；容量恢复后可再次被调度。

### 6.2 对齐与边界

1. 与 IM launch 失败策略在「释放 / 有限重试 / 耗尽停试再 ack / busy 不吞」语义上一致；仅有 IM 闭环、HTTP 仍失败即 ack，视为本变更未完成。
2. 验收不要求 IM 卡片视觉变更；不要求改对外 HTTP 契约字段形状。

### 6.3 非功能

1. 不引入 file-queue 整体重写作为本期必达项。
2. 工程规范：变更代码含中文注释；单文件不超过 300 行（超限须拆分，属实现阶段约束）。

## 七、范围边界

### 在范围内

- HTTP dispatch 旁路在失败与 busy 下的队列释放、有限重试、耗尽停试与最终 ack 的产品语义对齐。
- 经该旁路触发的 MCP / 工作流任务的同等可靠性体验。
- 与父债 IM 策略的语义一致性验收。
- 知识库中 HTTP 旁路「失败即丢」类限制的更新（archive 阶段）。

### 不在范围内

- IM 卡片 UI / 交互改版。
- file-queue 整体拆分或存储引擎替换。
- 对外 HTTP 契约形状变更（新增/删除字段、改路径等）。
- 引擎 Port 总线、四引擎 RunLifecycle 抽象。
- 新 IM 通道接入或通道视觉改造。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 父债默认值差异 | IM 侧重试次数/间隔若与 HTTP 旁路历史行为不同，对齐时可能改变旁路吞吐观感 | 以「语义一致」为硬门槛；默认值在设计阶段对照父债定稿并写清验收 |
| 重复执行 | 释放回队与成功 ack 边界不清可能导致双跑 | 验收强调 S4；设计明确「何谓成功交给执行」 |
| 契约误解 | 「行为对齐」被误读为可改响应形状 | 非目标与 R6 明确禁止 breaking 形状变更 |
| 毒消息占队 | 重试过宽占满待办 | 强制有限重试与放弃条件 |

## 九、知识库影响初评

| 文档 | 影响 |
|------|------|
| Daemon / 消息队列与路由（若记载 HTTP dispatch ack 策略） | 高：须补齐旁路与 IM 对齐后的失败/busy 语义 |
| 父债归档「dispatch失败重入队与ack策略」相关限制 | 中：标明 HTTP 旁路债务由本变更清偿 |
| Agent 调度 / HTTP 控制面概览（若有「失败即 ack」描述） | 中：同步更新为对齐后行为 |

初评结论：本变更为**父债 HTTP 旁路可靠性对齐**；知识库以调度/队列策略描述为主，细节在 `/kb-design` 与 archive 定稿。
