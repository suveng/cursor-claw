## 一、背景与问题陈述

消息队列承担 IM 入队、领取（claim）、确认移除（ack）、失败释放回队（release）与持久化等职责，是可靠投递底座。当前实现集中于单一模块，体量远超可读性门槛，后续在重试、路由、释放回队等路径上演进时：

- **评审成本高**：小改动需通读整块逻辑，易漏相邻语义。
- **回归面大**：claim / ack / release / 持久化交织，局部修复易牵动无关路径。
- **可靠性演进受阻**：失败重入队等能力已落在同一底座；继续在臃肿单体上叠加，会拉长丢消息 / 错误 ack 类故障的修复与验证周期。

本变更为**工程债清偿**：按职责拆分内部模块，**对外行为不变**，为后续可靠性改动提供可评审、可回归的结构基础。

## 二、用户可见症状

| 症状 | 典型表现 |
|------|----------|
| 短期无直接 UI | 用户侧界面与交互本轮不变 |
| 排障与修复变慢 | 队列故障需通读大块逻辑，定位与验证周期长 |
| 演进易引入回归 | 重试 / 路由改动易误伤 ack 或 release，抬高丢消息或错误确认风险 |
| 长期可靠性成本 | 底座难演进时，同类故障重复出现、修复窗口拉长 |

## 三、目标与非目标

### 目标（必须达成）

1. **按职责拆分**：按 claim、ack、release、持久化等职责拆成可独立理解与评审的模块边界。
2. **对外行为不变**：入队、领取、确认移除、失败释放回队等对外语义与现契约一致。
3. **行数合规**：拆分后单文件 ≤300 行。
4. **保留现有语义**：已落地的 release / ack（含失败重入队相关）在拆分后完整保留。
5. **降低演进风险**：后续重试 / 路由改动可落在明确职责模块内，缩短评审与回归范围。

### 非目标（明确不做）

- **不改** 队列文件格式与持久化语义（以现网为准）。
- **不改** IM 协议与通道接入形态。
- **不做** 跨进程 / 分布式队列或存储引擎替换。
- **不借拆分之机** 改变重试次数、ack 时机等产品策略。
- **不在 propose 阶段** 绑定实现类名、文件路径、内部接口签名（归属 `/kb-design`）。

## 四、用户与场景

### 用户

- **IM / 调度侧用户（间接）**：依赖可靠入队与正确 ack/release；本轮不改变可见行为，但降低后续改动引入丢消息的概率。
- **研发与运维**：需要可评审、可定位的队列模块边界，缩短故障修复与回归周期。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 行为回归** | 拆分前后，入队 / claim / ack / release 序列与现契约一致。 |
| **S2 失败释放保留** | 失败重入队路径下，release 后仍可再领取；语义不退化。 |
| **S3 成功 ack 保留** | 成功路径仍最终确认移除，不重复投递、不漏 ack。 |
| **S4 结构合规** | 拆分后各文件体量合规，职责边界可独立评审。 |
| **S5 与上游依赖** | 在「HTTP dispatch失败重入队对齐」之后再改同一底座；可与斜杠收尾并行。 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | **职责拆分**：按 claim / ack / release / 持久化拆分，边界清晰可评审。 |
| R2 | **行为不变**：对外队列行为与现契约一致。 |
| R3 | **语义保留**：现有 release / ack（含失败重入队）完整保留并回归覆盖。 |

## 六、验收标准

### 6.1 主路径

1. **行为回归**：入队、claim、成功 ack、失败 release 回队可再领取，与拆分前契约一致。
2. **release / ack 保留**：失败重入队与成功最终 ack 不退化；不静默丢消息、不错误确认移除。
3. **格式兼容**：现有持久化数据拆分后仍可正常读写，无格式迁移。

### 6.2 结构与边界

1. 单文件 ≤300 行；职责模块可说明「负责什么 / 不负责什么」。
2. 不要求 UI、IM 协议或分布式队列能力变更。

### 6.3 非功能

1. 变更代码含中文注释。
2. 不引入与拆分无关的策略默认值变更；须改策略时另开变更。

## 七、范围边界

### 在范围内

- 消息队列内部按职责拆分与结构整理。
- 对外行为回归与现契约对齐；现有 release / ack 语义保留。
- 归档阶段同步知识库中队列模块结构描述（若有）。

### 不在范围内

- 队列文件格式语义变更或存储引擎替换。
- IM 协议 / 通道视觉与接入改造。
- 跨进程分布式队列；重试 / ack 时机等策略调整；UI / Figma。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 与重入队并行冲突 | 「HTTP dispatch失败重入队对齐」可能改同一底座 | **宜在其后**推进，避免并行改同一文件 |
| 隐性行为漂移 | 拆分误改边界导致丢消息或双 ack | 行为回归硬门槛；对照契约验收 S1–S3 |
| 过度拆分 | 模块过碎增加导航成本 | 按职责拆、够合规即可 |
| 斜杠收尾并行 | 无硬代码依赖，可并行 | 保持各自范围 |
