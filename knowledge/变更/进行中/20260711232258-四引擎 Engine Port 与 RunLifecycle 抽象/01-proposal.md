# 四引擎 Engine Port 与 RunLifecycle 抽象产品需求文档

> **来源**：kb-propose
> **类型**：技术债
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景与问题陈述

Cursor Claw 支持四种 Agent 执行引擎（Cursor、Claude Code、Codex、OpenCode），分别承担 IM 入站任务、定时任务与工作流等场景下的 Agent 运行。当前四引擎在「启动、调度、停止、流式输出、看门狗、收尾、失败通知」等能力上**各自平行实现**，仅少量公共能力（如启动守卫、部分上下文用量统计）被复用。

这种平行结构带来两类产品可见问题：

1. **飞书通知不一致**：同一类运行结果（成功完成、用户取消、超时、调度失败、进程异常退出等），在不同引擎或不同触发路径下，用户有时能收到飞书 IM 提示，有时静默无消息；偶发重复或语义不清的通知。
2. **失败归因与出口不统一**：部分失败路径会标记「已通知」从而跳过后续提醒；部分路径在调度尚未真正进入运行态即失败，却未向用户发送 IM；部分收尾路径不经统一格式化即结束，导致用户侧体验断裂。
3. **运维与排障成本高**：Daemon 侧调度失败与 Electron 侧运行失败的通知对称性不足；引擎间行为差异需逐引擎对照，难以用统一验收矩阵验证。

根因在于：四引擎缺少统一的**引擎能力契约**与共享的 **Run 生命周期**状态机，各引擎对「何时通知、通知什么、何种情况视为已通知/已中止/已过期」的约定不一致。

**已选方案**：方案 B — 定义统一 Agent 引擎能力契约，并共享 Run 生命周期状态机（守卫 → 流式 → 看门狗 → 收尾 → 通知）；各引擎仅保留适配层，将引擎特有事件转为统一运行事件。不采用方案 A（渐进收敛、不建统一契约）与方案 C（单独 Notify 总线、生命周期仍分散）。

## 二、用户与运维可见症状

| 症状 | 典型表现 |
|------|----------|
| 通知漏发 | 任务已失败或已取消，飞书无系统提示；或仅部分引擎/场景有提示 |
| 通知静默丢弃 | 并发或锁冲突时，运行结束但用户未收到任何说明 |
| 调度失败无 IM | Daemon 侧未能将任务交给引擎执行时，用户侧无对称的失败通知 |
| 收尾体验不一致 | 成功完成时，有的引擎有格式化的 assistant 收尾，有的早退或仅内部日志 |
| 重复或语义混乱 | 同一 Run 的失败/取消被多次通知，或「已通知」「已中止」「已过期」标记导致后续合法通知被跳过 |
| 引擎间体验割裂 | 切换引擎后，用户对「任务结束我会收到什么」缺乏稳定预期 |

## 三、目标与非目标

### 目标（必须达成）

1. **统一引擎能力契约**：四引擎在启动、调度、停止、流式、看门狗、收尾等能力上遵循同一套产品级契约，对外行为可对照验收。
2. **共享 Run 生命周期**：一次 Agent 运行经历守卫 → 流式 → 看门狗 → 收尾 → 通知的明确阶段；各引擎通过适配层接入，不各自维护平行收尾逻辑。
3. **统一失败归因与通知出口**：失败、取消、超时、调度失败等场景有统一的归因规则与 IM 通知策略；「已通知 / 已中止 / 已过期」等契约在四引擎间语义一致。
4. **Daemon 调度失败对称性**：Daemon 无法在 Electron 侧成功 dispatch 时，用户应获得与运行期失败对等的、可理解的飞书通知（纳入验收范围）。
5. **可分期交付但架构目标明确**：允许分阶段落地各引擎适配，但终态为统一 Port + 共享 RunLifecycle，而非长期维持四份平行实现。

### 非目标（明确不做）

- **不采用**方案 A（仅渐进修补、不建立统一契约）或方案 C（独立 Notify 总线、生命周期仍分散）。
- **不改变**飞书卡片 UI、消息样式、菜单与交互设计。
- **不在 propose 阶段**确定类名、文件路径、接口签名等技术实现细节（归属 `/kb-design`）。
- **不迁移** IM 主路径调度权（仍由 Daemon Orchestrator 负责）。
- **不拆分**与本次 Run 生命周期无关的历史超大文件（属其他变更范围）。

## 四、用户与场景

### 用户

- **飞书主用户 / 管理员**：通过 IM 下发任务，期望任务开始、进行、结束或失败时获得一致、可理解的系统反馈。
- **运维 / 开发者**：需要跨引擎对照日志与通知行为，快速判断「是调度问题还是运行问题、用户是否应已收到 IM」。
- **多引擎切换用户**：在同一工作区内切换 Cursor / Claude / Codex / OpenCode 时，期望结束态通知语义一致。

### 场景矩阵（引擎 × 触发路径）

以下场景均需在四引擎上具备**可对照**的产品行为（细节在 design 阶段展开，此处定义验收维度）：

| 场景 | 简述 |
|------|------|
| **S1 成功完成** | Agent 正常跑完，用户收到符合通道规则的收尾消息（含 assistant 正文或约定 plain 收尾） |
| **S2 用户取消** | 用户主动停止，收到明确的取消/已停止类通知，且不重复骚扰 |
| **S3 超时 / 看门狗** | 运行超时或看门狗触发终止，用户收到可理解的超时/终止说明 |
| **S4 运行期失败** | 引擎执行中出错，用户收到失败归因清晰的 IM，且不会因「已通知」标记错误跳过 |
| **S5 Daemon dispatch 失败** | Daemon 未能将消息交给 Electron 引擎执行（引擎未就绪、拒绝、通信失败等），用户收到对称的失败 IM |
| **S6 stale / aborted** | 会话已过期、已被中止或 Run 已非当前活跃时，系统不发送误导性通知，必要时给出一次合理解释 |
| **S7 Electron 重启** | 应用重启后，进行中的 Run 按既有续接/失败规则处理，结束态通知仍符合统一契约 |
| **S8 并发 / 锁冲突** | 同一会话并发调度或资源锁冲突时，不静默丢弃用户应知的失败或跳过说明 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | 定义统一的 **Agent 引擎能力契约**，覆盖启动、调度、停止、流式输出、看门狗、收尾六类能力；四引擎必须通过适配层满足该契约，禁止在适配层外平行实现完整生命周期。 |
| R2 | 定义共享 **Run 生命周期**状态机：守卫 → 流式 → 看门狗 → 收尾 → 通知；各引擎将原生事件映射为统一运行事件后接入该状态机。 |
| R3 | 统一 **失败归因**规则：运行期失败、调度失败、用户取消、超时、stale/aborted 等须落入有限枚举，并驱动通知决策。 |
| R4 | 统一 **通知出口**策略：何种终态必须通知、何种可静默、何种仅通知一次；`errorNotified` / `aborted` / `stale` 等契约在四引擎间语义一致。 |
| R5 | **Daemon dispatch 失败**须纳入与运行期失败对称的 IM 通知路径，用户可感知「任务未能开始执行」与「执行中失败」的区别（文案可不同，但均不得无故静默）。 |
| R6 | 各引擎 **适配层**仅负责引擎特有协议与统一运行事件的双向转换；业务侧（Daemon、Presentation、飞书通道）不感知引擎内部差异。 |
| R7 | 成功完成路径须经统一收尾阶段，保证飞书 assistant 收尾或约定 plain 收尾与过程里程碑行为与现网多引擎契约对齐（见消息桥接知识库）。 |
| R8 | 变更完成后，Agent 调度领域知识库（06～10）与消息桥接飞书通道文档须可回溯本契约，消除「某引擎特殊、无文档」的灰色地带。 |

## 六、验收标准

验收以 **引擎 × 场景** 矩阵为主，要求可手工或自动化回归，且不依赖实现细节表述。

### 6.1 矩阵总表

对 **Cursor / Claude / Codex / OpenCode** 四引擎，分别验证：

| 场景 | 验收要点 |
|------|----------|
| 成功完成 | 用户收到一次符合通道规则的收尾消息；无重复收尾轰炸 |
| 运行失败 | 用户收到失败说明；同一 Run 不因错误标记重复通知或错误跳过 |
| 用户取消 | 用户收到取消/已停止说明；与失败、成功可区分 |
| 超时 / 看门狗 | 用户收到超时或终止说明；不出现无提示的僵死 Run |
| Daemon dispatch 失败 | 调度未进入运行态时，用户仍收到对称失败 IM（四引擎均须覆盖） |
| 通知对称性 | 同一 chat、同一触发路径下，换引擎后终态通知「有无」与「语义类别」一致，不出现某引擎系统性漏发 |
| stale / aborted | 过期或已中止 Run 不发送误导性成功/失败卡；若需提示则仅一次且语义正确 |
| Electron 重启 | 重启后续接或失败路径的终态通知仍满足上述各行（在现网续接策略允许范围内） |

### 6.2 跨引擎一致性

1. 任意两引擎在 S1～S6 场景下，用户侧「是否收到 IM」决策一致（除非产品有书面例外并在知识库登记）。
2. 运维可通过统一维度（Run 阶段、归因类别、是否已通知）对照四引擎行为，无需四套心智模型。

### 6.3 非功能

1. 不回归 IM 主路径调度（仍经 Daemon Orchestrator）。
2. 不改变飞书卡片视觉与菜单。
3. 工程规范：变更代码含中文注释；单文件不超过 300 行（超限须拆分，属实现阶段约束）。

## 七、范围边界

### 在范围内

- Electron 侧四引擎执行与收尾行为统一。
- Daemon Orchestrator 与 Electron 之间的 dispatch 失败通知对称性。
- 飞书 IM 终态与关键失败路径的通知一致性（沿用现有 post/md、plain assistant 等通道规则，不 redesign UI）。
- Agent 调度知识库 06～10、消息桥接 02-飞书通道 的同步更新（archive 阶段）。

### 不在范围内

- 飞书卡片样式、新菜单、新斜杠指令语法。
- 微信或其他 IM 通道（除非现有代码已共用同一出口且被本次契约自然覆盖）。
- Daemon 重启后的全量会话持久化（若与 Run 生命周期交叉，在 design 中划界，不在本期强制）。
- 新引擎接入（仅规范既有四引擎）。
- 方案 A / 方案 C 的替代架构。

## 八、风险与分期

### 主要风险

| 风险 | 说明 | 缓解方向 |
|------|------|----------|
| 迁移范围大 | 四引擎平行代码量大，一次性切换易回归 | 按引擎或按生命周期阶段分期，但保持 Port 架构目标不变 |
| 行为变更感知 | 统一契约可能改变某引擎「偶然」的静默行为 | 以本 PRD 矩阵做前后对照；灰度或单引擎先行 |
| 与 Presentation 耦合 | 过程里程碑与收尾路径跨 Daemon/Electron | design 阶段明确边界，避免双写通知 |
| 续接与重启 | Electron 重启后续接逻辑与统一 finalize 可能冲突 | 单独列出 S7 验收，design 中标注续接特例 |

### 建议分期（产品视角，非实施顺序承诺）

1. **一期**：统一 Run 生命周期骨架 + 统一通知出口与失败归因契约；先覆盖 dispatch 失败对称性（用户痛点最集中）。
2. **二期**：Cursor / Claude 引擎适配层落地并过矩阵验收。
3. **三期**：Codex / OpenCode 适配层落地并过全矩阵验收。
4. **四期**：知识库收尾、删除平行遗留路径文档与代码（与 archive 联动）。
