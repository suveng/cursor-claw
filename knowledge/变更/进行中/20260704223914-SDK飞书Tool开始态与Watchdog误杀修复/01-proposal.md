> **类型**：Bug 修复
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无

## 背景与问题

cursor-claw 通过飞书等即时通讯通道，让用户与 Cursor Agent 对话并执行自动化任务。运行期间，系统会向用户推送过程通知，帮助用户理解 Agent 正在做什么；同时，长时间无响应的运行会由看门狗（watchdog）在合理 idle 后主动收尾，避免用户无限等待。

近期已归档变更 `20260704212706-SDK开始态飞书通知携带描述`（v1.13.5）补强了 SDK **task 运行事件**路径上 shell 开始态命令摘要、task 事件描述携带，以及飞书 thinking 零出站等能力。用户在实际使用中仍反馈以下**新发现缺口**：

### 1. Task 工具（子 Agent 派发）开始态信息不足

当 Agent 通过 **Task 工具**（工具调用名为 task，用于派发子 Agent）启动子任务时，飞书过程通知仍常见「task：已开始」「子任务进行中…」等**泛化文案**，**未展示**工具参数中 `description` 字段所描述的具体任务目的（如「正在搜索相关代码」「正在检查终端状态」）。

这与已归档变更所覆盖的 SDK **task 事件**（运行里程碑映射）是**不同路径**：事件侧已能携带描述，但 **tool_call 开始态**仍未贯通，导致用户看到子 Agent 已启动却无从判断在做什么。

### 2. Shell 工具开始态仍有无信息占位

部分场景下，shell 命令开始执行时，飞书仍出现「shell: started」等**裸占位**或无实质说明的开始态文案，用户无法从通知中判断即将执行何种命令。v1.13.5 已在部分路径落地命令摘要，但存在**未覆盖或回归**的呈现分支，需在本次变更中统一验收并补齐。

### 3. 思考（think）过程飞书推送需回归确认

用户期望飞书**不再**单独推送思考过程通知。已归档变更声称 thinking 零出站；若线上仍出现「正在思考」类里程碑或等价提示，须在本次变更中**明确废止并回归验证**，避免与正文、子任务、工具开始态叠加造成噪音。

### 4. Watchdog 与平台取消状态的竞态误杀（2026-07-04 22:35 日志）

用户在一次长 idle 运行中观察到异常收尾：

- 运行长时间无活动（约 420 秒 draining + grace）后，看门狗判定超时并进入取消流程；
- 几乎同时收到运行流的 **CANCELLED** 状态，系统将看门狗从取消态**恢复为运行中**（活动恢复）；
- 随后仍触发**超时失败收尾**：用户收到超时失败通知，并写入崩溃归档（sdk_timeout）；
- 末次工具为 task 已完成，运行实际已被平台取消，属于**看门狗主动取消与终端 CANCELLED 状态竞态**导致的误杀，而非真实 hung run。

用户期望：看门狗主动取消后，终端 CANCELLED 状态事件**不应复活**看门狗或**重复触发**超时归档；长时 idle 取消与平台取消状态须协调，避免误报超时失败与不必要的 crash 记录。

## 目标与非目标

### 目标

1. **Task 工具开始态可读**：Agent 通过 Task 工具派发子 Agent 时，飞书开始态过程通知须携带 `description` 中的**任务描述摘要**，使用户能判断子 Agent 正在执行何种工作。
2. **Shell 开始态全路径一致**：shell 命令开始执行时，飞书开始态须展示**可理解的命令摘要**或明确降级说明，不得再出现无信息占位（如裸「shell: started」）；与 v1.13.5 能力对齐并回归验证。
3. **飞书 thinking 零出站**：飞书通道不向用户单独推送思考过程通知；若仍有残留，本次须彻底废止并通过回归验收。
4. **看门狗与取消状态协调**：看门狗因长 idle 主动取消后，平台 CANCELLED 状态不得将看门狗错误恢复为运行中，不得重复触发超时失败通知与 sdk_timeout 类崩溃归档。
5. **用户感知一致**：上述修复不得破坏工具通知分级、消息顺序、完成/失败态展示等既有体验；桌面端思考日志等可观测性保留。

### 非目标

- 不扩展至 Claude Code SDK、Codex SDK、OpenCode SDK 等其他执行引擎；本次仅针对 **Cursor SDK** 运行路径。
- 不改造 Electron 设置界面、飞书凭据配置等桌面端 UI。
- 不重做 v1.13.5 已归档的 SDK **task 事件**映射逻辑，除非验收发现回归。
- 不在本阶段为终端用户提供自定义开始态文案格式或看门狗阈值配置。
- 不全面改版所有工具类型的完成态、失败态呈现（但须保证不退化）。

## 用户故事

### 飞书私聊用户

- 作为通过飞书与 Agent 对话的用户，当 Agent 派发子 Agent（Task 工具）时，我希望在开始通知里看到**这一步在做什么**（来自任务描述），而不是只看到「task 已开始」。
- 作为等待命令执行的用户，当 Agent 开始跑 shell 时，我希望开始通知里**始终**能看到命令摘要或明确说明「命令暂不可展示」，而不是裸「shell: started」。
- 作为长任务用户，我希望飞书**不再**弹出「正在思考」类提示，同时子任务与命令开始态仍足够清晰。
- 作为经历长时间等待的用户，当运行因 idle 被系统取消时，我希望收到**与真实结局一致**的反馈（平台取消或合理超时），而不是在已被取消后仍收到超时失败与崩溃归档。

### 运维与管理员

- 作为排查「用户不知道子 Agent 在做什么」投诉的支持人员，我希望 Task 工具开始态已含描述摘要，便于区分正常派发与异常卡住。
- 作为分析 sdk_timeout 崩溃日志的管理员，我希望误杀类竞态不再产生误导性超时归档，便于聚焦真实 hung run。

## 功能需求

### F1 Task 工具（子 Agent 派发）开始态携带描述

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 当 Cursor SDK 运行中 Agent **开始调用** Task 工具（子 Agent 派发）且该操作属于应向用户通知的过程时，飞书侧开始态过程通知须包含**任务描述摘要**（来源于工具参数中的 description 或等价用户向信息）。 |
| F1.2 | 描述应简洁可读；过长描述须摘要为短句并保留核心意图；不得退化为仅「task 已开始」「子任务进行中…」等无信息泛化句。 |
| F1.3 | 多个 Task 工具连续派发时，各条开始态通知应能区分不同子任务（描述或序号可读），用户能分辨当前启动的是哪一步。 |
| F1.4 | Task 工具开始态与后续进行中、完成类里程碑语义衔接自然，避免同一描述在短时间内重复刷屏。 |
| F1.5 | 当 description 缺失或不可解析时，开始态须使用**不低于当前体验**的业务兜底（如步骤序号 + 简短动作说明），不得长期固定为无信息量文案。 |

### F2 Shell 工具开始态命令摘要（回归与补齐）

| 编号 | 需求描述 |
|------|----------|
| F2.1 | shell 命令开始执行时，飞书开始态须包含**可理解的命令摘要**，使用户能判断正在执行何种操作。 |
| F2.2 | 飞书文本里程碑、卡片抑制降级等不同呈现路径下，开始态信息应**同等可理解**；不得因呈现形式切换而退化为裸「shell: started」等占位。 |
| F2.3 | 无法解析具体命令时，须使用明确降级文案（如「命令执行已开始，但具体命令暂不可展示」），不得仅显示工具名 + started。 |
| F2.4 | 命令执行完成或失败阶段的既有展示能力不得因本次补强而退化。 |

### F3 飞书通道收敛思考（think）过程推送

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 飞书通道**不再**向用户单独推送思考（think）类过程通知；若 v1.13.5 后仍有残留，本次须彻底废止。 |
| F3.2 | 收敛思考推送不得导致飞书用户在运行开始后长时间完全无任何可见反馈；仍应能通过处理中态、正文首包、子任务或关键工具开始态等既有机制感知 Agent 在工作。 |
| F3.3 | 飞书 thinking 零出站不得删除或削弱桌面 SDK 运行界面中的思考日志可见性。 |

### F4 看门狗与平台取消状态协调

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 看门狗因长 idle（含 draining、grace 阶段）判定应取消运行并进入取消流程后，后续收到的**平台 CANCELLED** 状态不得将看门狗错误恢复为「运行中」，避免取消流程被逆转。 |
| F4.2 | 当运行已被看门狗主动取消或平台已宣告 CANCELLED 时，**不得再触发**超时失败收尾、超时失败用户通知及 sdk_timeout 类崩溃归档。 |
| F4.3 | 用户最终收到的结束反馈须与真实结局一致：平台取消、看门狗 idle 取消、真实超时等场景应可区分或可理解，不得出现「已取消却仍报超时失败」的矛盾体验。 |
| F4.4 | 正常 hung run 的真实超时保护能力须保留：非竞态场景下，长时无响应仍应能合理收尾并通知用户。 |

### F5 与既有分级、消息顺序协调

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 开始态补强须遵守工具调用通知分级：只读探查类工具默认仍不推送；仅对已通知白名单内的操作增强开始态文案。 |
| F5.2 | 与助手正文、task/tool 过程、处理中/完成/失败三态等既有信号协调，避免同一语义在短时间内重复推送。 |
| F5.3 | 用户主动停止或运行失败时，进行中的开始态相关展示应停止更新，并与结束反馈一致。 |

## 边界与例外

1. **极短子任务或极短命令**：若 Task 或 shell 在极短时间内结束，开始态可与完成态按策略合并呈现，但用户仍应能获知「执行了什么」。
2. **描述或命令不可用**：采用安全兜底摘要，并满足 F1.5、F2.3 的最低可读性要求；含敏感信息须脱敏。
3. **平台限流**：可缩短摘要或延迟非关键开始态，但须在运行结束或限流解除后保证用户仍能获知宏观结果。
4. **看门狗阈值**：本次不开放用户可配置 idle 阈值；仅修复取消与 CANCELLED 竞态导致的误杀与误归档。
5. **非 Cursor SDK 路径**：不在本次范围。

## 验收标准

1. **Task 工具开始态带描述（飞书私聊）**：模拟 Agent 通过 Task 工具派发至少 2 个可区分 description 的子 Agent，飞书用户应在各**开始态**过程通知中看到对应任务描述摘要，而非「task：已开始」「子任务进行中…」等泛化句。
2. **Task 工具与 task 事件不混淆回归**：在同时存在 task 事件与 Task 工具调用的运行中，开始态描述均可读，且不因本次修复导致 task 事件路径描述退化。
3. **shell 开始态无裸占位（飞书私聊）**：模拟 Agent 开始执行至少 3 条不同 shell 命令，飞书开始态均须含命令摘要或 F2.3 明确降级句，**不得**出现裸「shell: started」或无信息占位。
4. **shell 文本里程碑路径一致**：在飞书对工具类通知走文本里程碑呈现的场景下，上述开始态仍须包含命令摘要或明确降级说明，与能展示摘要的其他呈现方式信息等价。
5. **飞书不再推送 think（回归）**：在 Cursor SDK 路径上触发含思考阶段的运行，飞书用户**不应**再收到独立的思考过程通知（含「正在思考」类里程碑）；运行开始后 10 秒内仍应有处理中态、正文首包、子任务或关键工具开始态等至少一种可见反馈。
6. **看门狗取消后不因 CANCELLED 复活**：复现或模拟「长 idle 后看门狗进入取消 + 随后收到 stream CANCELLED」场景，看门狗**不得**被错误恢复为运行中，**不得**再触发超时失败通知与 sdk_timeout 崩溃归档。
7. **真实超时仍有效**：在非竞态的 hung run 场景（无平台 CANCELLED 干扰），长时无响应仍应能由看门狗合理收尾并通知用户，不得因本次修复而丧失超时保护。
8. **分级不被破坏**：对 read、glob 等默认静默的只读探查类工具，飞书侧仍不应出现开始态过程通知；对 shell、Task 工具等白名单操作，开始态增强正常生效。
9. **完成/失败不退化**：同一次 shell 或 Task 工具调用在完成或失败后，用户仍能获取与变更前相当或更优的结果与描述信息。
10. **桌面端思考日志**：飞书 thinking 零消息场景下，桌面 SDK 运行日志中仍可查阅当次运行的思考记录。
