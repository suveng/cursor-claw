# SDK think 与 task 事件实时通知产品需求文档

> **变更 ID**：`20260704174846-SDK think与task事件实时通知`
> **来源**：kb-propose
> **类型**：体验优化
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 背景与问题

cursor-claw 通过飞书、微信等即时通讯通道，以及任务面板等入口，让用户与 Cursor Agent 对话并执行自动化任务。

在既往「Cursor SDK 执行引擎事件流消费」能力落地后，系统已能全路径接收 Agent 运行期间的标准化事件流。但用户在实际使用中仍普遍反馈：**发消息后长时间看不到任何过程反馈，仿佛 Agent 处理完毕后才一次性回复**；等待期间缺乏「正在思考」「子任务推进」等可感知信号，体验接近沉默等待。

经归纳，当前感知缺口主要集中在两类过程信息上：

1. **思考过程（think）**：Agent 进入推理、规划阶段时，用户侧未能及时、稳定地看到对应提示；部分通道或场景下过程信息被抑制或延迟到运行临近结束才集中出现。
2. **任务/子任务里程碑（task）**：Agent 启动子任务、切换阶段、完成子步骤等里程碑事件，对用户侧几乎无可理解的可见通知，用户无法判断 Agent 正在做什么、进展到哪一步。

上述缺口与用户对「实时对话」的预期相悖，也削弱了长任务、多步任务场景下的信任感与可控感。本次变更聚焦：**在 Cursor SDK 运行路径上，将 think 与 task 两类过程事件尽早、稳定地转化为用户可感知的通知**，并与既有助手正文流式、处理中三态等呈现协调，避免以牺牲整体可见性为代价。

## 目标与非目标

### 目标

1. **think 过程及时可见**：Agent 进入思考阶段后，用户应在合理时延内（通常数秒内）在所用通道看到可理解的「正在思考」类提示，而非等到运行结束才出现或完全缺失。
2. **task 里程碑及时可见**：子任务启动、进行中、完成等用户可理解的状态变化，应及时转化为过程通知，让用户感知 Agent 正在执行的具体步骤与进展。
3. **与正文流式协调**：过程通知的增强不得导致短任务首包反馈明显退化；助手正文流式输出与过程通知的时序关系应清晰、可预期，避免用户误以为系统无响应。
4. **通道一致可感知**：飞书、微信、群聊等不同通道按各自能力呈现，但遵循一致的产品原则——运行期间应有持续、可理解的过程信号，而非长时间完全沉默。
5. **与既有状态反馈协调**：与「处理中 / 完成 / 失败」三态、停止操作、失败提示等既有反馈机制配合，避免重复、刷屏或语义冲突。

### 非目标

- 不扩展至 Claude Code SDK、Codex SDK、OpenCode SDK 等其他执行引擎（除非后续单独立项）；本次仅针对 **Cursor SDK** 运行路径。
- 不向终端用户暴露原始事件类型名称、内部错误堆栈或实现细节；过程展示仍遵循「用户可理解」的呈现策略。
- 不改造 Electron 设置界面、通道凭据配置等桌面端 UI（除非仅为展示过程状态所必需且与既有呈现一致）。
- 不追求对每一次极短思考片段都单独推送（避免无意义刷屏）；具体节流与合并策略由产品原则约束，细节在设计阶段确定。
- 不替代助手正文流式输出；过程通知是补充可见性，不是用过程提示代替最终回答。

## 用户故事

### 即时通讯用户

- 作为通过飞书私聊与 Agent 对话的用户，我在发送一条需要多步推理的消息后，希望几秒内就能看到「正在思考」或等价提示，而不是盯着空白界面等待数十秒。
- 作为在微信中与 Agent 交互的用户，当 Agent 拆分为多个子任务执行时，我希望能看到子任务启动与完成的里程碑提示，从而判断 Agent 没有卡住、仍在推进。
- 作为在群聊中 @ Agent 的用户，我希望过程通知遵循群聊既有策略（如不打扰他人、适度聚合），但仍能让我在合理时间内感知 Agent 已开始处理我的请求。

### 任务面板用户

- 作为通过任务面板触发 Agent 的用户，我希望任务执行期间的思考与子任务进展，与 IM 通道一样能及时反映在任务状态或关联消息中，不因入口不同而缺失过程信息。
- 作为查看历史任务的用户，我希望过程通知与最终结果在时序上可追溯，便于理解 Agent 是如何一步步完成任务的。

### 运维与管理员

- 作为排查用户投诉「Agent 没反应」的支持人员，我希望用户侧已收到足够的过程信号（思考、子任务里程碑），便于区分「系统无响应」与「Agent 正在长耗时执行」。
- 作为负责版本发布的管理员，我希望过程通知增强不会显著增加通道消息频率或触发平台限流，长任务场景下仍保持可接受的推送节奏。

## 功能需求

### F1 think 过程及时可见通知

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 当 Cursor SDK 运行进入思考阶段时，系统须在**事件到达后尽快**（通常数秒内）向用户侧发出可理解的思考过程提示，不得默认等到运行结束才批量呈现。 |
| F1.2 | 思考过程提示的文案与呈现形式须符合既有产品策略（如「正在思考…」、阶段性摘要等），用户无需了解内部事件名称即可理解 Agent 正在推理。 |
| F1.3 | 在通道能力允许的场景下，思考提示应支持适时更新（如思考阶段延续或内容变化），而非仅发送一次后长期无变化；在通道不支持频繁更新的场景下，应至少保证**首次可见**不显著滞后。 |
| F1.4 | 若产品策略对特定通道或场景选择抑制部分思考细节，仍须保证用户能感知「Agent 已进入处理/思考」，而非完全沉默。 |

### F2 task / 子任务里程碑及时可见通知

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 当 Agent 启动子任务、子代理或等价任务单元时，用户侧应收到可理解的通知（如「正在执行：…」），表明 Agent 已展开具体工作步骤。 |
| F2.2 | 子任务进入进行中、完成、失败等用户可理解的状态时，应及时推送对应里程碑提示；完成类提示应简洁，避免与最终助手正文重复冗长。 |
| F2.3 | 多个子任务连续发生时，通知节奏应可读：用户能分辨当前进行到第几步，又不过度刷屏；必要时可对短时间内的同类里程碑做合理聚合，但**首个子任务启动**不得明显延迟。 |
| F2.4 | 任务面板入口触发的运行，子任务里程碑的可见性与 IM 通道遵循同一产品原则，不因入口不同而完全缺失。 |

### F3 与 assistant 正文流式的时序关系

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 过程通知（think、task）与助手正文流式输出可同时存在，但时序须符合用户直觉：运行开始后应尽快出现**至少一种**可见反馈（过程提示或正文首包），不得长时间两者皆无。 |
| F3.2 | 短任务（常见单轮问答、轻量操作）的首包反馈时延不得因本次增强而明显退化；若正文很快到达，过程提示可与正文协调呈现或按策略省略冗余提示。 |
| F3.3 | 长任务场景下，在正文尚未产出或产出稀疏的阶段，think 与 task 过程通知应填补可见性空白，让用户持续感知进展。 |
| F3.4 | 运行结束时，过程提示与最终正文、结束态（完成/失败）的衔接应自然，避免用户收到大量过程消息后仍不清楚任务是否已结束。 |

### F4 通道差异与降级

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 飞书、微信、群聊等通道按既有产品策略与平台能力呈现过程通知；各通道在呈现形式上可不同，但**及时可感知**原则一致。 |
| F4.2 | 当某通道不支持某种呈现能力（如消息内频繁更新、富文本等）时，应降级为通道可实现的等价通知（如单条提示、状态卡片、简短文本），而非静默丢弃过程信息。 |
| F4.3 | 群聊场景须兼顾不打扰其他成员：过程通知遵循群聊既有抑制或聚合规则，但触发者仍应在合理时间内知晓 Agent 已开始处理。 |
| F4.4 | 通道异常、发送失败时，过程通知的丢失或重试策略与既有消息投递策略一致，不单独引入不可恢复的状态。 |

### F5 与既有「处理中」三态、停止、失败提示的协调

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 过程通知须与「处理中 / 完成 / 失败」三态反馈协调：三态表示运行级宏观状态，think/task 通知表示过程级细粒度进展，二者语义不冲突、不重复刷屏。 |
| F5.2 | 用户主动停止运行时，进行中的过程通知应停止更新，并尽快呈现与停止操作一致的结束反馈。 |
| F5.3 | 运行失败时，过程通知不应掩盖失败原因；失败提示仍按既有策略优先呈现，过程历史可作为辅助上下文。 |
| F5.4 | 同一次运行内，相同语义的重复通知应被合理抑制（如同一思考阶段反复推送相同文案），在「及时」与「不骚扰」之间取得平衡。 |

## 边界与例外

1. **极短运行**：若 Agent 在极短时间内完成且无实质思考或子任务拆分，系统可按策略省略部分过程通知，但须满足 F3.2 短任务首包不退化。
2. **用户不可见的内部步骤**：仅服务于内部编排、不对用户有意义的中间步骤，可不单独通知，但不应导致用户侧长时间无任何过程或正文反馈。
3. **通道限流与平台约束**：当外部平台触发频率限制时，过程通知可降级或聚合，但须在限流解除或运行结束后保证用户仍能获知最终结果与宏观状态。
4. **与其他引擎并存**：非 Cursor SDK 路径的行为不在本次范围；若用户混用多引擎，仅 Cursor SDK 路径享受本次增强。
5. **隐私与敏感内容**：思考过程若含不宜直接展示的内容，按既有呈现策略做摘要或抑制，但仍须满足 F1.4 最低可见性要求。

## 验收标准

1. **think 及时性**：在 Cursor SDK 路径上，模拟进入思考阶段且正文尚未产出的运行，用户于所用通道在 **10 秒内**（从用户发消息或运行可感知启动起计）应看到思考类过程提示或等价可见反馈，不得直至运行结束仍完全无过程信号。
2. **task 里程碑可见**：模拟含至少 2 个子任务里程碑的运行，用户应能依次看到子任务启动（或进行中）与完成类可理解提示，且**首个子任务相关通知**不晚于该子任务实际开始后的合理时延（通常 10 秒内）。
3. **短任务不退化**：对典型单轮短问答，从用户发消息到收到首条可见助手内容（正文或合规的过程+正文组合）的时延，与变更前同场景相比**无明显劣化**（主观可接受、无新增「长时间完全空白」案例）。
4. **长任务过程填充**：对耗时超过 30 秒且正文稀疏的运行，用户在等待期间应至少收到 2 次以上过程类可见更新（think 或 task 里程碑，或二者合计），而非仅最终一次性回复。
5. **三态协调**：运行期间「处理中」态与过程通知并存时，用户能区分「仍在运行」与「已结束」；停止与失败场景下，不出现过程通知无限更新或与结束态矛盾的情况。
6. **多通道抽检**：飞书私聊、微信（若已配置）、任务面板入口各至少 1 个场景通过上述 1～5 项；群聊场景验证过程通知符合群聊策略且触发者仍可感知启动。
7. **不刷屏**：单次运行内，无连续 5 条以上语义完全相同的过程通知（除非通道策略要求独立消息且无法合并）。
