# Cursor SDK执行引擎长任务支持产品需求文档

> **变更 ID**：`20260701202638-CursorSDK执行引擎长任务支持`
> **来源**：kb-propose
> **类型**：需求
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 背景

cursor-claw 通过飞书/微信等 IM 通道，以及任务面板、工作流三条路径触发 Cursor 执行引擎完成用户请求。其中一部分请求属于"长任务"：例如需要连续多步骤执行的深入调研、跨多轮次的长对话、或执行过程中需要较长时间等待用户回复确认才能继续的场景。

当前系统对这类长任务的"扛压"能力不足：应用版本更新自动重启、进程意外崩溃等情况发生时，正在进行中的长任务或长对话会被直接中断，且没有机制自动恢复——用户只能重新发起一次全新的对话或任务，此前的沟通背景、执行进度全部丢失。此外，系统内部用于判断任务"是否卡住"的机制也可能在长任务的正常长耗时或长等待场景下发生误判，将本应继续执行的任务强制提前终止。

团队希望优化 Cursor 执行引擎，使其在面对长任务时更具韧性：既不因为应用自身的重启/崩溃而丢失任务，也不因为超时误判而错误打断正常的长任务。

## 目标

1. 应用主进程重启（含版本更新触发的重启）或意外崩溃恢复后，此前正在进行中的长任务/长对话可以自动续接，用户无需重新发起
2. 续接后系统能将后续执行结果正确推送回原来的 IM 会话或任务面板，用户感受与未发生中断基本一致
3. 长任务在合理的长耗时、长等待场景下不会被系统误判为"异常卡住"而强制终止
4. 当极端情况下确实无法自动续接时，系统能给出用户可理解的明确提示，而不是让任务静默消失

## 非目标

- 不改变用户发起对话/任务的入口与交互方式
- 不涉及界面/视觉改版，不新增可见的配置页面
- 不改变 Claude Code SDK、Codex SDK、OpenCode SDK 三条执行引擎现有的续接能力（这三者已具备各自的续接机制，不在本次范围内）
- 不追求对超出合理时限的极端长任务无限期保活，超长时限场景的处理策略留待后续评估
- 不改变工作流 YAML 定义格式与节点间既有的上下文传递规则

## 用户故事

**最终用户视角**：

- 作为通过飞书/微信与 Agent 长对话的用户，当应用发生更新重启或临时故障后，我希望能继续之前未完成的对话，而不是收到"会话已失效，请重新开始"的提示
- 作为发起一个需要长时间执行的任务（如深入调研、长链路多步骤操作）的用户，我希望任务在正常执行或等待我确认的过程中不会被系统无故中断
- 作为在长任务执行期间因故等待较长时间才回复的用户，我希望回复后任务能继续正常推进，而不是发现任务早已被系统判定超时取消

**管理员/运维视角**：

- 作为负责维护该应用的管理员，我希望应用发布新版本触发重启后，用户手中正在跑的长任务能够平滑续接，减少版本升级对用户体验的影响
- 作为运维人员，我希望进程崩溃后恢复时，能够清楚知道哪些任务成功续接、哪些未能续接，而不是无从判断任务状态

## 验收标准

1. 在一个长对话/长任务正在进行中时，主动重启应用主进程，之后用户在原 IM 会话/任务面板中可以继续该对话或任务，无需重新发起，且能正常收到后续执行结果
2. 长任务运行期间，即使经历较长时间的连续执行或等待用户回复的空闲窗口，任务不会被系统误判为异常并提前强制终止
3. 应用因崩溃等非正常方式退出后重新启动，此前进行中的长任务能够恢复并将结果正确推送回原会话；确实无法恢复时，用户能收到明确、可理解的提示，而非任务无声消失
4. 续接成功后的对话/任务上下文与中断前保持一致，用户看到的历史沟通内容和任务进展不丢失、不错乱
5. 短任务（正常一问一答、快速执行完成的任务）的现有行为和体验不受本次优化影响
