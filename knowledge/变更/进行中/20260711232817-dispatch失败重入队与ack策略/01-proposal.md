# dispatch失败重入队与ack策略产品需求文档

> **变更 ID**：`20260711232817-dispatch失败重入队与ack策略`
> **来源**：kb-propose
> **类型**：建议「可靠性」（待闸门确认）
> **优先级**：建议 P0（待闸门确认）
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景与问题陈述

Cursor Claw 通过 IM（飞书等）接入用户任务：消息进入排队后，由本机编排进程领取并交给 Agent 执行。知识库已登记的产品债 **R3** 指出：当「交给 Agent 执行」这一步失败时，系统仍会把该条消息从队列中确认移除；任务因此消失，用户只能手动在 IM 里重新发送同一诉求，才能再次排队。

这与用户对「排队任务」的朴素预期冲突——**调度失败 ≠ 用户放弃该任务**。失败后任务应从队列「消失」变为「可恢复」：要么自动再次排队等待重试，要么在可控策略下保留并允许有限次重试，而不是静默丢失。

相邻进行中变更「四引擎 Engine Port 与 RunLifecycle 抽象」已覆盖 **dispatch 失败时的对称 IM 通知**（让用户知道「任务没能开始」），但**明确不覆盖**队列恢复 / 重新入队。本提案专门解决后半段产品债：**失败后任务不丢、可自动或可控重试**。

## 二、用户与运维可见症状

| 症状 | 典型表现 |
|------|----------|
| 任务无故消失 | 用户发了一条任务，系统短暂处理后队列里再也找不到；用户以为已失败结束，实际是调度失败后被确认移除 |
| 必须手动重发 | 要重新跑同一任务，只能在 IM 里再发一遍原文；无「系统替我再试一次」的体验 |
| 与通知割裂 | 即使未来能收到「调度失败」的 IM 提示，若队列侧仍 ack 丢弃，用户仍需手动重发；「告知失败」与「保留任务」未闭环 |
| 偶发抖动放大损失 | 本机 Agent 侧短暂未就绪、通信抖动等瞬时失败，一次失败即永久丢任务，可靠性观感差 |
| 运维难复现 | 日志可见调度失败，但队列已空，无法从「待办队列」视角回溯「当时该重试的那条」 |

## 三、目标与非目标

### 目标（必须达成）

1. **失败不丢任务**：dispatch / 交给执行侧失败时，默认不得以「确认移除」导致用户任务从待办队列永久消失（除非产品明确允许的放弃路径）。
2. **可自动或可控重试**：失败后支持重新入队或等价保留，并具备可理解的重试策略（次数、间隔、放弃条件等由设计阶段细化；本期须在产品上可验收「会再试 / 会停试」）。
3. **与失败通知闭环**：与「调度失败 IM 通知」能力对齐——用户既知道失败，又不必依赖手动重发才能恢复排队（通知本身由相邻变更负责，本变更负责队列侧恢复语义）。
4. **策略可说明**：运维与用户侧能区分「还在重试」「已放弃并需人工介入」；放弃时不得静默（至少与通知契约一致）。

### 非目标（明确不做）

- **不替代**「四引擎 Engine Port 与 RunLifecycle 抽象」中的统一失败通知与 Run 生命周期；本变更不重做通知总线，只补齐队列 ack / 重入队产品语义。
- **不改**飞书卡片 UI、消息样式、菜单与交互视觉。
- **不在本期**做 file-queue / 文件队列的整体性能重写或存储形态大翻修；仅围绕失败后的 ack 与重入队策略做可靠性闭环。
- **不在 propose 阶段**确定实现类名、文件路径、接口签名等技术细节（归属 `/kb-design`）。
- **不扩大**为全通道产品 redesign；微信等通道若与飞书共用同一队列编排，以「同一队列策略自然覆盖」为界，不单独开通道视觉改造。

## 四、用户与场景

### 用户

- **飞书主用户**：发任务后期望「失败了还能再试」，而不是「失败了任务没了、只能自己再发」。
- **管理员 / 运维**：需要判断某次调度失败是瞬时可恢复还是应停止重试并介入；避免队列被毒消息打满或无限重试。

### 场景

| 场景 | 简述 |
|------|------|
| **S1 瞬时调度失败** | 执行侧短暂未就绪或通信抖动导致 dispatch 失败；系统应保留任务并在策略内自动重试，用户最终可无需手动重发即进入执行（或在重试窗口内恢复）。 |
| **S2 持续不可用** | 执行侧持续不可达，重试耗尽或达到放弃条件；任务不得无限空转；用户须能感知「已停止自动重试」，且任务处置符合「不静默丢弃」的产品规则（保留待人工 / 明确失败终态等，由设计细化）。 |
| **S3 与失败通知并存** | 发生调度失败时，用户可收到失败类 IM（由相邻变更保障）；本变更保障队列侧仍可恢复或可控保留，二者不互相替代。 |
| **S4 成功路径不变** | 正常领取并成功交给执行后，确认移除与现网一致，不因本变更导致成功任务重复执行轰炸。 |
| **S5 用户主动放弃（若有）** | 若产品提供「取消 / 不再重试」入口，放弃后不再自动重入队；本期若无独立入口，至少不得把「系统 ack 丢弃」伪装成用户放弃。 |

## 五、功能需求

| 编号 | 需求描述 |
|------|----------|
| R1 | **失败默认不 ack 丢弃**：dispatch / 交给执行失败时，不得将消息从待办队列永久确认移除（除非落入明确的放弃策略）。 |
| R2 | **重入队或等价保留**：失败后的消息须重新进入可被再次领取的状态，或处于等价的「待重试」保留态，直至成功交给执行、用户放弃、或策略判定放弃。 |
| R3 | **可控重试策略**：须定义有限重试（次数与/或时间窗）及放弃条件；避免无限重试打满队列或掩盖真实故障。 |
| R4 | **成功路径保持一次确认**：成功交给执行后的确认移除行为与现网产品预期一致，不引入重复执行。 |
| R5 | **与通知语义分工清晰**：本变更负责「任务还在不在队列 / 会不会再试」；对称失败 IM 由相邻 Engine Port 变更负责；两边验收可对照，但实现与范围不互相吞并。 |
| R6 | **可观测**：运维可区分「调度失败且已安排重试」「重试耗尽 / 已放弃」；关键日志或状态对排障可见（表述保持产品级，不绑定具体字段名）。 |
| R7 | **知识库债闭环**：变更完成后，Daemon 概览与消息桥接概览中 R3「失败须手动重发」类限制须更新为新行为或明确剩余边界。 |

## 六、验收标准

### 6.1 主路径

1. **瞬时失败可恢复**：人为制造一次可恢复的调度失败后，同一用户任务在无需手动重发 IM 的前提下，能在策略窗口内再次进入执行或仍处于可重试待办（以实际可观察的队列/执行结果验收）。
2. **不再「失败即消失」**：调度失败后，待办侧不得出现「消息已确认移除且无任何重试/保留痕迹」的旧行为（对照知识库 R3 旧债）。
3. **重试有上限**：持续失败时，系统在有限次或有限时间后停止自动重试，且用户侧对「已停止自动重试」可感知（与通知契约对齐，不要求本变更单独改卡片 UI）。
4. **成功不重复轰炸**：正常成功路径下，同一条任务不会因本变更被重复领取执行多次。

### 6.2 与相邻变更边界

1. 即使 Engine Port 变更已提供 dispatch 失败 IM，本变更仍须独立满足「失败不丢、可重试」；仅有通知、无队列恢复，视为本变更未完成。
2. 本变更验收不要求飞书卡片视觉变更；若验收依赖文案，沿用现有通道能力即可。

### 6.3 非功能

1. 不引入对 file-queue 的整体性能重写作为本期必达项。
2. 工程规范：变更代码含中文注释；单文件不超过 300 行（超限须拆分，属实现阶段约束）。

## 七、范围边界

### 在范围内

- Daemon 编排侧：dispatch / 交给执行失败后的 ack 与重入队（或等价保留）产品策略。
- 有限重试与放弃条件的产品规则及可观测性。
- 与「调度失败 IM 通知」的闭环对齐（通知实现不在本变更强制范围内）。
- 知识库中 R3 相关限制描述的更新（archive 阶段）。

### 不在范围内

- 统一四引擎 Run 生命周期与通知出口（相邻变更）。
- 飞书卡片 UI / 交互改版。
- file-queue 整体性能重写、存储引擎替换。
- 新 IM 通道接入或微信专属视觉改造。
- 用户手动「重发按钮」类新交互（若设计阶段发现需要，另立变更或扩 scope，不在本期默认范围）。

## 八、风险与依赖

| 风险 / 依赖 | 说明 | 缓解方向 |
|-------------|------|----------|
| 与 Engine Port 并行 | 通知与重入队分属两变更，可能交付不同步 | 验收矩阵分开；本变更以「队列不丢」为硬门槛，通知可先依赖相邻变更或临时降级文案 |
| 毒消息 / 无限失败 | 重试策略过宽会占满待办 | 强制有限重试与放弃条件；设计阶段定默认值 |
| 重复执行 | 重入队与成功 ack 边界不清可能导致双跑 | 验收强调 S4；设计阶段明确「何谓成功交给执行」 |
| 用户感知缺口 | 仅重试无说明时用户仍困惑 | 依赖对称失败通知；本变更保证任务仍在 |

## 九、知识库影响初评

| 文档 | 影响 |
|------|------|
| Daemon 守护进程概览（§九 已知限制 R3） | 高：须改写「dispatch 失败 ack 不 re-queue」 |
| 消息桥接概览（§九 限制「须手动重发」） | 高：与 R3 同步更新 |
| 消息队列与路由 | 中：补充失败后 ack / 重入队产品规则 |
| Agent 调度相关（若涉及 dispatch 失败终态） | 低～中：与相邻变更交叉处划界即可 |

初评结论：本变更为**可靠性产品债闭环**；知识库以 Daemon / 消息桥接概览 R3 为主，细节在 `/kb-design` 与 archive 定稿。
