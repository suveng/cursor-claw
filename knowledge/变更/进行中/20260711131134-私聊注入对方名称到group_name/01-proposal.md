# 私聊注入对方名称到 group_name 产品需求文档

> **来源**：kb-propose
> **类型**：Feature
> **优先级**：P2
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景与问题

群聊场景下，发给 agent 的提示词/上下文**首行**已可注入 `group_name: <群名>`，便于 agent 识别当前对话所在群。

私聊场景下，飞书会话**没有可用的群名**；用户希望同样在提示词首行注入对方显示名，使 agent 能识别「正在与谁对话」。若开通该能力需要通讯录相关权限，应通过设置页既有的「一键创建应用 / 扫码更新权限」自动带上，**不另开**手工申请路径。

本变更承接已归档能力「Agent注入群聊名提示词」的产品语义，将同等格式扩展到私聊，且不改变群聊既有行为。

## 二、目标与非目标

### 目标

1. **私聊可识别对方**：用户在飞书私聊与机器人对话时，agent 提示词首行出现 `group_name: <对方名称>`（与群聊同一格式）。
2. **无名称时可预期**：拿不到对方名称时，不注入无效占位，行为与群聊约定一致（省略该行，或不写无效占位）。
3. **权限随扫码开通**：获取用户名所需权限纳入扫码创建/更新清单，管理员扫码即可开通，无需飞书后台额外菜单配置。

### 非目标

- **不改**群聊注入语义与既有群名行为。
- **不改** agent 执行引擎、会话隔离、IM 发送协议或其他通道契约。
- **不要求**用户在飞书开放平台后台另行手工勾选/申请权限菜单。
- **不涉及**新页面或视觉改版（沿用既有设置页扫码流程）。

## 三、用户与场景

### 用户

- **飞书私聊用户**：与机器人一对一对话，期望 agent 知道对方是谁。
- **应用管理员**：通过设置页「一键创建应用」或「扫码更新权限」开通/更新飞书应用权限。

### 场景 A：私聊有对方名称

用户在飞书私聊向机器人发消息。系统能取得对方显示名时，组装后的 agent 提示词/上下文**首行**为 `group_name: <对方名称>`，其后为原有内容。

### 场景 B：私聊无对方名称

因权限未开通、名称暂不可用等原因拿不到对方名称时，不注入无效占位：要么省略该行，要么与群聊「无群名」约定一致的可预期降级，**不得**写入无意义占位文案。

### 场景 C：管理员扫码开通权限

管理员在设置页发起「一键创建应用」或「扫码更新权限」。扫码清单中已包含获取用户名所需权限；用户完成扫码授权后即可开通，无需另走手工申请。

### 场景 D：群聊回归（不破坏）

群聊仍按既有约定注入 `group_name: <群名>`；本变更不改变群聊首行语义与无群名降级行为。

## 四、功能需求

### F1 私聊首行注入对方名称

- 飞书**私聊**场景下，发给 agent 的提示词/上下文最前面插入一行：`group_name: <对方名称>`。
- 格式与群聊一致：键名为 `group_name`，值为对方显示名；仅首行插入。
- 「对方名称」指私聊对端用户的显示名（飞书侧用户可见名称）；私聊无会话群名时须用对方用户名，不得用空群名冒充。

### F2 无对方名称时的可预期降级

- 无法取得对方名称时，行为与群聊「无群名」约定一致：省略该行，或不写无效占位。
- 不得注入误导性占位（如随意字符串、错误提示充当名称等）。

### F3 权限纳入扫码创建/更新清单

- 若本能力依赖通讯录/获取用户名相关权限，须纳入设置页「一键创建应用」与「扫码更新权限」的权限清单。
- 管理员扫码即可开通；不另开手工申请路径，不要求飞书后台额外菜单配置。

## 五、非功能需求

| 编号 | 描述 |
|------|------|
| NF1 | 注入仅影响提示词/上下文组装的首行内容，不改变用户可见的飞书消息气泡样式。 |
| NF2 | 权限开通路径与既有扫码体验一致，不新增独立申请入口。 |
| NF3 | 群聊回归：有群名/无群名行为与变更前一致。 |

## 六、验收标准

1. **私聊有名**：飞书私聊且能取得对方显示名时，组装后的 agent 提示词/上下文**首行**为 `group_name: <对方名称>`，其后为原有内容。
2. **私聊无名**：无法取得对方名称时，不注入无效占位（省略该行或与群聊无群名约定一致），行为可预期。
3. **扫码含权限**：设置页「一键创建应用」或「扫码更新权限」的权限清单含获取用户名所需权限，用户扫码可开通。
4. **群聊不破坏**（回归）：群聊有群名时仍为首行 `group_name: <群名>`；无群名时降级与既有约定一致。
